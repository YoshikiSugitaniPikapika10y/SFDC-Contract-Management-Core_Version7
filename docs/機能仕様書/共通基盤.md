# 共通基盤機能仕様書

## 1. 共通基盤の目的と適用範囲

### 1.1 共通基盤が管理する事項

本書は、Core だけでも Accounting ON のときだけでもない共通の仕組みの正本である。Core の業務結果の正は `仕様書_Core.md`、Accounting ON のときの仕訳結果の正は `仕様書_Accounting.md` である。日付算法、契約横断の画面、権限、操作ログの正は本書である。

本章が正とするのは次である。

- 権限セットとカスタム権限の識別子、割当単位、できること
- カスタム画面はシステム権限で動き、操作可否はカスタム権限で止めること
- 標準 UI で書いてはいけないオブジェクト
- 画面（Dynamic Actions、LWC のカスタム権限、コード）とサーバ入口の両方で止めること
- 参照の共有（`Loop_01`）と全件（`Loop_02`）
- 日付算法（旧称 `日付仕様.md`。節番号は同一）
- 契約横断の画面（旧称 `docs/横断画面.md`。節番号は同一）
- 操作ログ（Core 第2.5節と同義。本文は第12章）

操作キー、行ロック、版比較の正は Core 第4.3.12節・第7.9.7節・第11.6節である。Accounting 方針の中身は Accounting の当該節である。

### 1.2 Core・Accountingとの責任分界

| 対象 | 正本 |
| --- | --- |
| Core だけ（OFF でも成立する業務結果） | `仕様書_Core.md` |
| Accounting ON のときの仕訳結果 | `仕様書_Accounting.md` |
| 日付算法 | 本書の日付（旧称 `日付仕様.md`。節番号は同一） |

### 1.3 共通原則

- カスタム画面の Apex はシステム権限である。プロファイルのオブジェクト Edit では業務操作を止めない。止めるのはカスタム権限である。
- 業務権限は画面表示とサーバ入口の両方で見る。出して押せてサーバだけ落とす、権限の無いボタンをグレーの常時表示にする、はしない。
- 操作の単位はボタンではない。自明に同じ人がやる処理は1権限にまとめる。顧客が分けたいもの（受注と差し戻し、確定と取消、Lock と Unlock、見積書の発行と送付）は分ける。人物セット（営業一式など）はパッケージに同梱せず、権限セットグループは顧客が組む。
- イレギュラー権限は `101` から採番する。復旧は 101・102、移行は 103・104。操作ログの閲覧は 105。03〜21 の業務操作を代替しない。システム管理者にも常時は付けない。画面に業務ボタンは置かない。

### 1.4 制約の実装方針

- カスタム権限がある操作は、Dynamic Actions または LWC の `@salesforce/customPermission` で入口を隠し、同一のカスタム権限を Apex の `FeatureManagement.checkPermission` で拒否する。
- トランザクションオブジェクトは、通常の権限セット（01〜21）に Edit／Delete を付けない。標準編集、API、Data Loader からの直書きは Trigger でも拒否する。正規のカスタム画面だけが書く。例外は第3.6節の 101〜104。
- 動的追加項目を扱う `ContractService__c`、`ContractHistory__c`、`ContractProduct__c` は、通常は標準編集ボタンを出さない。102 または 104 が付いているときだけ出してよい。
- 一覧に出す行は、`Loop_01` なら共有、`Loop_02` ならパッケージオブジェクト全件、にカスタム画面も揃える。レコードページだけ共有、LWC は全件、にはしない。

## 3. 権限とセキュリティ

権限体系の正本は本章である。旧識別子 `Contract_04_Can_Create_Estimate` 等は、本表の `Loop_*` へ置き換える。

### 3.1 権限体系

接頭辞は `Loop_`。通常はゼロ埋め2桁 `01`〜`21`。イレギュラーは `101` から。権限セットとカスタム権限は番号を揃える。カスタム権限が無い行は、オブジェクト権限だけで制御する（参照、請求アカウント、会計マスタ、操作ログ）。`Loop_101` は字面では `Loop_10` と `Loop_11` のあいだに並ぶ。

操作権限（03〜21、101〜104）は、参照の `Loop_01_Read` または `Loop_02_ReadAll` と併用する。19 と 21 も含む。01 と 02 はどちらか一方である。103／104 が持つ View All は Data Loader と標準リスト向けである。カスタム画面の一覧は第3.7節どおり 01／02 のままである。105 は操作ログの閲覧だけであり、01／02 と併用しない。常時は付けない。

請求の作業系（10〜17）は閲覧を含む。`Loop_09` を別途付けなくてよい。09 は閲覧専用である。

横断のメニュー専用権限は置かない。開けるのは 18。見積メニューは 04 または 05 または 06。請求メニューは 09〜17 のいずれか。仕訳メニューは Accounting ON かつ 09〜17 のいずれか。無いメニューと無い操作ボタンは出さない。

パッケージは人物向けのまとめセットを同梱しない。旧 `Contract_Sales` / `Contract_Ops` は使わない。

### 3.5 ロック済みレコードの操作権限

仕訳の手動 Lock は 16、Unlock は 17 である。閲覧（09）、未確定編集（10）、確定（11）、101〜104 では実行しない。Lock 済みでも仕訳メモと、仕訳ロック除外にある追加項目は 10 で直せる。仕訳行の金額、科目、日付、借貸の**更新**は 101〜104 を問わず直さない。104 の新規作成と削除は第3.6節。Accounting OFF では Lock／Unlock の入口を持たない。

確定済み・取消済み請求の項目ロックは Core 第7.9節である。101 は請求書と請求明細の項目更新だけを通す。確定後の請求情報編集（追加項目はロック除外のみ）と入出金メモは 10 である。確定・取消・入金の登録／取消は 11・15・13 のままである。

### 3.6 イレギュラー（101〜104）

## 12. 操作ログ

（Core 第2.5節と同義である。本節へ本文を移した。結果は変えていない。）


操作ログは、誰がいつ何をしたかの時系列である。冪等と同時実行の正は業務操作キー、行ロック、版比較である（第4.3.12節・第7.9.7節・第11.6節）。操作ログはそれを置き換えない。同じキーで原因レコードと仕訳を辿ることは今どおりである。操作ログへも、キーがある操作はそのキーを書く。

用途は時系列だけである。横断の操作一覧は持たない。サポート用のジャンプ導線も持たない。製品の LWC、関連リスト、アプリのナビ、グローバル検索、レポートには出さない。付ける人だけ、標準のリスト（「すべてのタブ」）か SOQL で見る。権限は `Loop_105_ViewOperationLog`（`共通基盤.md`第3章）。バックアップと保持期間はパッケージで持たず、Salesforce 標準を顧客に任せる。仕訳の整合性突合は `SPEC-006` のまま MVP 対象外である。

OWD は Private。階層による共有は OFF。Lookup は持たない（関連リストを出さない）。カスタムの実行者項目は持たない。実行者・日時は `CreatedBy` / `CreatedDate`。

1行は、成功した1回の書き込みである。失敗は原因操作と同じトランザクションで消える。同じ業務操作キーの再試行は2行目を作らない。キーが空の操作は、成功のたび1行である。インストール、アップグレード、シードは書かない。

作成の許可は `ContractOperationLogService.write` の静的フラグだけである。ユーザー判定はしない。フラグなしの insert（画面、API、Data Loader、匿名 Apex の直書き）は拒否する。システム管理者と 101〜104 でも同じ。`write` を Execute Anonymous から呼べばフラグが立つので通る。CreatedBy はその人である。更新は常に拒否する。削除は 104 だけ通す。Trigger は `Loop_104_Can_MigrateAll` のときだけ削除を通す。103 と 105 では不可である。104 に操作ログの Read、Delete、View All Records、Modify All Records を付ける。Create と Edit は付けない。タブはオブジェクトタブ `ContractOperationLog__c`（表示名「契約操作ログ」）である。105 だけ Available。アプリナビには出さない。製品 LWC は出さない。付ける人だけ、標準のリスト（「すべてのタブ」）か SOQL で見る。`Contract_Operation_Log` は作らない。操作ログ自身の削除は操作ログに書かない。ごみ箱は Salesforce 標準である。空にするまで容量に残る。第3.4節の業務レコード集合に含めない。103 の削除対象外である。104 の全部 CRUD にも載せない。

## 1. 共通原則

### 1.1 月は暦月ではなくサイクルで数える

契約期間における「1か月」は、開始日から1か月後の前日までの1区間である。Nか月は、この1サイクルをN回積み上げる。

```apex
public static Date endOfMonthlyPeriod(Date periodStart) {
    return periodStart.addMonths(1).addDays(-1);
}
```

次のサイクルは、直前サイクル終了日の翌日から始める。

```apex
Date currentStart = firstStart;
for (Integer i = 0; i < cycles; i++) {
    Date currentEnd = endOfMonthlyPeriod(currentStart);
    currentStart = currentEnd.addDays(1);
}
```

`開始日.addMonths(N).addDays(-1)`による一発計算は使用しない。Salesforceの月加算は存在しない日を月末へ頭打ちするため、月末開始ではサイクルの起点が前へ移る。この移動をドリフトと呼び、仕様として許容する。

見積有効期限と支払条件の入金予定日は、このサイクル算法を使わない。見積有効期限は第2.6節、入金予定日は第5章。

2025年1月31日開始の例は次のとおりである。

| サイクル | 開始日 | 終了日 |
| ---: | --- | --- |
| 1 | 2025/1/31 | 2025/2/27 |
| 2 | 2025/2/28 | 2025/3/27 |
| 3 | 2025/3/28 | 2025/4/27 |
| 12 | 2025/12/28 | 2026/1/27 |

うるう年に1月31日から開始した場合は2月29日を通るため、以後の起点は29日になる。「常に28日へ寄る」とは限らない。

### 1.2 刻む算法は共通化する

契約期間、見積商品、契約期間明細、請求明細および契約日アンカー方式の仕訳バケットは、同じサイクル算法を使用する。請求明細の売上計上バケット数`RecognitionBucketCount__c`も、月次計上ではこの刻みの件数である。Accounting第3.2節。

- Apexの正本は`MonthlyBillingPeriodUtil.cls`
- LWCの画面用再実装は`estimateLineItemUtils.js`
- どちらかを変更する場合は、同じ変更で両方とテストを更新する
- JavaScriptで`new Date("YYYY-MM-DD")`を使用せず、年月日をローカル日付として分解する

例：1/31 → 2/28 → 3/31

### 1.4 日割りしない

見積、請求および仕訳で日数按分を行わず、日割り設定も持たない。

- 継続課金は1サイクル単位で金額を持つ
- 1か月未満の仕訳バケットも1バケットとして扱う
- Newの初回端数相当額は、一回課金明細として利用者が金額を指定する
- Changeの継続課金イベントはサイクル境界に置く

## 2. 契約・見積の日付

### 2.1 見積商品の提供期間

- 継続課金の提供終了日は、その明細の提供開始日起点のサイクル境界に一致させる
- Newで継続課金開始日を入力し終了日が空の場合は、組織設定の既定サイクル数目の終了日を初期設定する。既に終了日があれば上書きしない
- 画面で境界からずれた終了日を入力した場合は短い側の境界へ寄せる
- サーバ保存時は自動補正せず、境界不一致をエラーにする
- 一回課金は開始日・終了日を必須とし、開始日より前の終了日を拒否するが、同日を許し、サイクル境界への一致は要求しない

### 2.2 見積種別ごとの継続課金ヘッダー

| 見積種別・内容 | 期間開始日 | 切替日 | 期間終了日 |
| --- | --- | --- | --- |
| New・継続課金あり | 見積商品の最早開始日 | 期間開始日 | 見積商品の最遅終了日 |
| New・一回課金のみ | 未設定 | 未設定 | 未設定 |
| Term Change・継続課金イベントあり | 有効な継続課金明細から算出 | 最初の継続課金イベント日 | 有効な継続課金明細から算出 |
| Term Change・一回課金追加だけ | Latest Orderedを維持 | 未設定 | Latest Orderedを維持 |
| Spot Change | 未設定 | 未設定 | 未設定 |
| Renew | 継承した継続課金明細から算出 | 期間開始日 | 継承した継続課金明細から算出 |
| Cancel | Latest Orderedの期間終了日の翌日 | 同日 | 同日 |

Cancelの同一日付3項目は管理上の解約日であり、その日をサービス提供期間として扱わない。直前Versionの期間終了日が最終利用日である。

### 2.3 Changeの切替日

継続課金を変更するChangeの課金イベント日は、変更対象となる元明細のサイクル境界に一致させる。1つのChangeに複数の変更日を持てるが、契約履歴の切替日は最初の継続課金イベント日だけを表す。

一回課金Type=Newだけを追加するChangeは継続課金イベントを持たないため、一回課金の提供期間をサイクル境界へ合わせない。

### 2.4 RenewとCancel

- Renewの開始日はLatest Orderedの期間終了日の翌日
- Renewの終了日の初期値は、Renew開始日から組織設定の既定サイクル数を積み上げて求める。利用者が終了日を変えた場合は入力値を正とする
- Cancelの解約日はLatest Orderedの期間終了日の翌日
- Cancel受注後の契約サービス終了日は解約日を表示するが、最終利用日は直前Versionの期間終了日

### 2.6 見積日と有効期限

見積日と有効期限は帳票の日付である。契約期間のサイクル、請求日、入金予定日、仕訳計上日には使わない。画面と保存の可否はCore第4.10節。

ウィザードが見積書セクションを出し、見積日が空で開いたときの初期値は次とする。

| 項目 | 初期値 |
| --- | --- |
| 見積日 | 組織タイムゾーンの今日 |
| 有効期限 | 見積日に暦月Nを加算した日 |

Nは組織内1件の見積有効期間である。単位は暦月。シード1。範囲1～12。入口はCore第11.6節の組織設定。保持体は現行の`ContractDocumentSetting__c`。無い、0、範囲外または小数なら1へ落とさずエラーにする。既存の見積は設定変更で書き換えない。

算法はSalesforceの月加算そのものである。`見積日.addMonths(N)`。存在しない日は月末へ頭打ちする。第1.1節のサイクル（`addMonths(1).addDays(-1)`の積み上げ）は使わない。stickyも使わない。

<strong style="color:#1a5276;">ToBe</strong>
手続き <span style="background:#fdebd0;padding:0 6px;border-radius:3px;">既存</span> <code>ContractDocumentSettingService.requireEstimateValidMonths</code>、<code>estimateWizardState.applyEstimateDocumentDefaults</code>
／ Apexのサイクル関数は使わない。
</div>

| 見積日 | N | 有効期限 |
| --- | ---: | --- |
| 2025/1/15 | 1 | 2025/2/15 |
| 2025/1/31 | 1 | 2025/2/28 |
| 2024/1/31 | 1 | 2024/2/29 |
| 2025/1/31 | 12 | 2026/1/31 |

見積日を変えたとき、利用者が有効期限をまだ触っていなければ同じ算法で付け直す。触ったあとは追従しない。見積日を空にしたとき、未編集の有効期限も空にする。

ウィザードは組織設定のNを読む。保存時にサーバが見積日や有効期限の空欄を埋めない。発行操作でも見積日・発行日・有効期限を自動設定しない。見積PDF本文も空なら空のまま出す。ファイル名の`{yyyyMMdd}`だけCore第11.3.2節（発行日未設定なら今日）。

自動RenewはApexで見積日と有効期限を書かない。コピー定義のFrom数式で置く。同じ作成では先に書いた見積日を読めないため、両方とも今日基準とする。例は`TODAY()`と`ADDMONTHS(TODAY(), N)`。前回履歴の見積日に足さない。数式のNと組織設定のNは分かれうる。パッケージは同期しない。

## 3. 契約期間明細と請求サービス期間

### 3.1 継続課金

継続課金の見積商品期間をサイクル単位へ分割し、各サイクルを契約期間明細として生成する。Changeでも切替日を新しいサイクル起点にせず、元明細の開始日から続くサイクル境界へ合わせる。

### 3.2 一回課金

一回課金は提供開始日から提供終了日までを1本として生成し、月次サイクルへ分割しない。月次計上を選択した場合の仕訳バケットだけは第6章に従う。

### 4.2 請求日ルール

請求アカウントは、次のいずれか1方式と必要な値を保持する。項目API名、保存値、方式ごとの必須／空欄はCore第7.2節。月末の保存値は`MonthEnd`であり、31日指定ではない。

| 方式 | 保存値 | 計算 |
| --- | --- | --- |
| 基準日と同日 | `SameDay` | 請求基準日をそのまま使用 |
| 基準日以後の指定日 | `OnOrAfterSpecifiedDay` | 基準日以後で最初に到来する1～28日または月末 |
| 基準月から指定月数前後 | `MonthOffset` | 基準日の暦月を0として-12～12か月移動した月の1～28日または月末 |
| 基準日から指定日数を加減 | `DayOffset` | 基準日に-365～365日を加算 |

29日・30日・31日を指定して存在しない月だけ月末へ寄せる方式は使用しない。旧`BillingDayOfMonth__c`と`AdjustInvoiceDateToBusinessDay__c`は持たない。既存レコードの自動載せ替えはしない。

算出後の請求日は、補正なし・前営業日・翌営業日のいずれかで補正できる。営業日は組織の既定営業時間と休日設定に従う。補正は自動生成時だけ適用し、手動変更した請求日へ再適用しない。

| 方式 | 保存値 | 計算 |
| --- | --- | --- |
| 請求月から指定月数後 | `MonthOffset` | 請求日の暦月を0として0～12か月後の1～28日または月末 |
| 請求日から指定日数後 | `DayOffset` | 請求日に0～365日を加算 |

算出後は補正なし・前営業日・翌営業日を選択できる。補正後を含め、入金予定日が請求日より前になる設定は拒否する。

## 6. 売上計上日

### 6.1 一括計上と検収終了日

一括計上の請求明細は`AcceptanceEndDate__c`を必須で持ち、生成時にサービス期間終了日を初期設定する。月次計上明細はこの項目を持たない。Accounting ON/OFFを問わず値は持つ。

- 標準UIの表示はCore第7.6節。Accounting ONの請求ボードだけに出し、OFFでは出さない。請求明細レコードページからは出さない
- Accounting ONでは確定前後とも請求ボードから変更できるが、空欄にはできない
- 確定時に空欄なら初期値を補い直さず、請求確定全体をエラーにする
- 確定後変更では金額、請求日、宛名、税率その他の対外内容を変更しない
- Accounting ONでは`ACCEPTANCE_DATE_CHANGED`を起動し、旧仕訳を処理して新しい日付で再生成する
- Accounting OFFで過去の関連仕訳が1件以上残る場合は、画面外更新を含む変更を拒否する。標準機能ではAccountingをONへ戻せない。残りの判定はAccounting第1.1節（Current）に従う
- Accounting OFFで過去の関連仕訳がなければ、画面外更新で日付だけ変えられるが仕訳イベントは起動しない。標準画面からは起動しない
- Accounting OFFで検収日を業務として残したい場合は請求書のメモ`Memo__c`を使う

### 6.2 月次計上バケット

組織の会計方針`GlAccountingPolicy__c.MonthlyBucketMethod__c`で自動・契約日アンカー・暦月を選択する。

| 方式 | 分割 |
| --- | --- |
| 契約日アンカー | 第1章のサイクル算法。最終バケットだけサービス期間終了日で閉じる |
| 暦月 | サービス期間が触れる暦月ごと。初回はサービス期間開始日、最終回は終了日で閉じる |
| 自動 | サイクルを積み上げて終了日の翌日に一致すれば契約日アンカー、跨げば暦月 |

自動判定で「終了日が月末だから一致」といった補正をしない。stickyも使用しない。

### 6.3 月次計上日

`GlAccountingPolicy__c.MonthlyRecognitionDatePosition__c`で、各バケットの開始日・終了日・終了日所属月の月末から選択する。ただし最終バケットはサービス期間終了日を使用し、期間外の月末へ延長しない。

月次バケット方式、月次計上日位置および端数寄せ先は組織の導入時会計方針とし、最初の請求確定後は変更できない。設定世代と請求別スナップショットを持たず、固定した設定と公開後に意味変更しない共通算法から同じバケット・配分を再現する。

## 7. 請求入出金と仕訳日

### 7.1 請求入出金日

請求入出金日は組織タイムゾーンの操作日を初期値とするが、利用者は実際の現預金移動日へ変更できる。請求日より前の日付も許可し、自動で請求日へ補正しない。

Invoice目的で入出金日が請求日より前の場合は、入出金日の現預金段階と請求日の振替段階を同じトランザクションで生成する。入出金日が請求日と同日なら通常日Invoiceとして扱う。

### 7.2 手動仕訳日

手動仕訳は利用者が入力した日付を計上日として使用する。組織タイムゾーンの操作日を初期値にできるが、保存した入力日を別の日付へ置き換えない。

### 7.3 取消基準日と実際の逆仕訳日

請求取消、請求入出金の登録・取消、検収終了日変更および手動仕訳取消では、ロック済み関連仕訳が1件以上ある場合、AccountingのON/OFFを問わず利用者が取消基準日を1つ入力する。初期値は組織タイムゾーンの操作日とする。未入力ならエラーにし、操作日を黙って使わない。未ロック仕訳だけなら日付を設定しない。

各ロック済み元仕訳の実際の逆仕訳日は次で決める。

```text
実際の逆仕訳日 = max(取消基準日, 元仕訳日)
```

入力した取消基準日を、元仕訳日より前だからといってエラーにはしない。同じ操作から複数の実際の逆仕訳日が生じることを許す。実行前に、論理削除件数、逆仕訳件数、実際の逆仕訳日ごとの件数および将来日付の有無を表示する。

<div style="border:1px solid #5dade2;border-left:6px solid #1a5276;background:#eaf2f8;padding:8px 12px;margin:10px 0;font-size:0.92em;line-height:1.55;">
<strong style="color:#1a5276;">ToBe</strong>
<span style="background:#fdebd0;padding:0 6px;border-radius:3px;">既存</span> <code>AccountingDiffService.applyForInvoice</code>内の逆仕訳日。空なら操作日で埋めない。
</div>

取消基準日を元取引日以降へ入力制限しない。同じ取消操作から複数の実際の逆仕訳日が生じることを許す。入力した取消基準日を、元より前だからといってエラーにはしない。

必要な仕訳の計上日が空なら、操作日や確定日で埋めず、仕訳を未生成のまま残さず、原因操作全体をエラーにする。計上日項目は`BillingDate`、`PaymentDate`、`RecognitionDate`、`ManualDate`、`ReversalDate`の5定義だけとし、確定日・受注日・提供開始日・提供終了日・検収終了日をカタログキーにしない。検収終了日は一括計上の`RecognitionDate`入力として請求明細に残す。

# 契約横断画面

（旧称 `docs/横断画面.md`。本部の節番号は旧横断画面.mdと同一である。コードおよび他文書の「横断画面.md 第X節」は本部を指す。結果は変えていない。）


本書は契約横断画面の画面仕様の正本である。Core第9章およびAccounting第11.6節から参照する。個別操作の業務結果の正は `仕様書_Core.md` 第4章〜第8章および `仕様書_Accounting.md` である。本書はそれを契約横断で実行する画面を定める。入口のアプリケーション、タブ、横断を開ける権限は `Loop_18_CrossWork` / `Loop_18_Can_CrossWork`（`共通基盤.md`第3章）。

## 1. 位置づけ

契約横断画面は、契約サービスをまたいで見積・請求・仕訳を探し、同じ画面のまま操作する画面である。見るだけにはしない。

契約サービス配下の契約履歴（見積操作ハブ・ハイライト）と請求ボードが、1つ目の方法である。横断は、同じ操作を契約サービスをまたいで行う2つ目の方法である。レコードページへ都度遷移せず、同じ画面のまま連続できる。横断だけの新しい操作は置かない。操作ログの横断一覧は置かない。操作ログは `仕様書_Core.md` 第2.5節。

誰がこの画面で残りを片づけるかは、組織が決める。営業支援が発行・送付・受注・登録の全部を見る会社もあれば、自動更新など一部だけ代行する会社もある。製品は「営業の机」「経理の机」を指定しない。見える行と右のボタンは、既存のレコードアクセスと操作権限に従う。担当者用の専用キューは持たない。

提供価値は次の2つである。

1. 契約サービス／契約履歴／請求のレコードページへ都度遷移しなくてよい
2. 契約をまたいで並べるため、漏れ・ずれ・期限超過を見つけやすい

使い方は、左で探し、右で操作する。左は一覧（表示）。右は選んだ1件の作業面（表・編集・ボタン）。左の1クリックは、契約履歴や請求ボードへ入り込むことの代替である。ボタンを左に並べて連打する画面ではない。

### 横断だからできる業務

この画面は、契約をまたいで残りを見つけ、その場で1件ずつ操作する机である。見るだけにはしない。レポートや経営分析の代わりにはしない。集計したい数字はレポートで見る。

操作しても、一覧を取り直すまで行は消えない。一段落したかは、一覧を取り直して残りが無いかで見る。入力必須のカスタム項目は、Enforce をオンにした入力規則で止める。この画面の残り探しには出さない。差し戻しはイレギュラーなので、想定業務にしない。受注したあとの本線は請求である。

更新の折衝や、アップセル・ダウンセルの進み具合といった更新状況のリアルは、更新商談の役目である。操作ではないし、見たいときはレポートで足りる。

#### 今期末・更新期限の見積を送り、受注する

今期末に閉じる商談の見積と、更新期限が近い更新見積を、出さない・送らない・受注しないまま残さない。送ったのに期限まで返事（受注）が来ていないものも含む。更新の発行・送付・受注は見積一覧で行う。

受注は、専任の権限を持つ担当が任されていることが多い。契約履歴を1件ずつ開かず、この画面で残りを見て、その場で受注まで終わらせられるのがメリットである。発行・送付のあと、受注処理を横断でクイックに完結する。

見積一覧を、完了予定日で絞る。新規や変更は今期末に閉じる商談。更新は更新商談の完了予定日（いまの契約の終わりが近い）。まだ送っていないもの、自動更新で作られた見積もここで拾う。見るのは、完了予定日が今期末または更新期限に近いか、PDFがあるか、送ったか、まだ受注していないか。

出ていなければ右で発行する。送っていなければ右で送る。送済みでまだ受注していなければ、右で再送するか、返事が来ていれば右で受注する。数量・単価・期間を直すときは、契約履歴名のリンクから既存のウィザードへ。

1件は、右で発行・送付・受注できれば終わり。全体は、一覧を取り直して、今期末または更新期限が近い未受注の見積が無ければ終わり。自動更新の見積も同じ。

#### 受注一覧は置かない

更新期限が近いのに更新商談が無い、次 Version の契約履歴が無い、といった検知はレポートで足りる。横断の受注一覧でも検知はできるが、次の操作は商談の `+見積` であり、この画面の右では終わらない。見つけても操作できない一覧は置かない。

差し戻し、受注済みのカスタム項目、契約サービスを編集する、は1つ目の方法（契約履歴／契約サービス）で行う。見積がある更新・解約は見積一覧で発行・送付・受注する。

更新商談の一覧メニューも、同じ理由で横断には出さない。入口は商談の `+見積` のままである。見積ウィザードを横断の右に埋め込まない判断（商品明細は幅が足りない）と、ここで揃える。

#### 未確定を差額ゼロにして確定する

未確定の請求を1件ずつ確定する。確定しないと仕訳は切られない。

請求一覧を未確定で絞る。グループ見出しの見積税抜と請求合計を比べ、差額を見る。差額が残っていれば右で端数を合わせる。切れ方が違うなら分けて移す。日付や税率だけなら請求情報を直す。差額がゼロなら右で1件ずつ確定する。確定できるかは、その版の請求全体で見る。宛先が未決なことはここでは拾わない。検収日は確定したあとでも直せるので、確定を待つ理由にしない。

1件は確定できれば終わり。全体は、一覧を取り直して未確定が無ければ終わり。

#### 確定済みで、まだ送っていない請求を送る

確定した請求を、請求日になったら送る。請求日を過ぎてまだ送っていない漏れも、ここで送る。遅延の督促（入金予定日超過の再送）とは別である。

請求一覧を、確定済みかつ未送付で絞る。見るのは請求日と今日である。請求日が今日以前なら右で送る。送る前に請求書の送付方法を確認する。請求日がまだ来ていなければ、まだ送らない。発行が先に要るなら右で発行してから送る。送付設定が`使わない`組織では、この業務は出さない。`PDFのみ`なら発行までである。

1件は送れたとき（`PDFのみ`なら発行できたとき）終わり。全体は、一覧を取り直して、請求日を迎えた未送付が無ければ終わり。

#### 請求書番号・請求アカウントで探して、入金消込する

届いた入金を、請求書番号や請求アカウントで探して、すぐ消込する。遅延の督促とは別の、日常の消込作業である。

請求一覧で請求書番号（請求名。部分一致）または請求アカウント（ルックアップ）を探す。取引先でもルックアップで1件選んで探せる。対象の請求を右に出し、入金する。1回の入金で複数の請求へ分けない。請求書ごと。

1件は入金できれば終わり。全体は、探した入金の消し込みが終わっていれば終わり。入金しても回収が完了しないものは、手動仕訳や原因の直しへ残る。

#### 期限が過ぎた未消込を再送し、入金する

入金予定日を過ぎて、まだ回収しきれていない確定済み請求を再送し、入金する。

請求一覧を遅延で絞る。今日と入金予定日、回収が完了しているかを見る。遅延のまま未完了なら右で再送する。入金が来ていれば右で入金する。日付が来ただけでは消込もタグも変わらない。

1件は再送できたとき、または入金して回収が完了したとき終わり。全体は、一覧を取り直して遅延が無ければ終わり。入金しても完了しないものは、次の原因の直しへ残る。

#### 手動仕訳が要りそうなものをタグで拾い、漏らさない

入金したのに売掛が残る、手数料などで未充当の入金が残る、閉じるはずの前受が残る、といった請求を逃さない。タグが付いていること自体は異常とは限らない。未入金の売掛残りは普通である。ロックしてよいか、今月の進み具合か、には使わない。会計を使っていない組織では出さない。

請求一覧で、会計タグと回収の状態を組み合わせて絞る。操作するのは次である。売掛残りかつ回収完了。未充当の入金残り。終局なのに前受残り。右の請求で原因を直す。入金の誤り、手動仕訳の登録、取消、検収日である。仕訳の金額は触らない。タグは確定・入金・取消のときに付け替わる。

1件は、直したあと、その組み合わせに当てはまらなくなれば終わり。全体は、一覧を取り直してその組み合わせが無ければ終わり。提供中の前受残りを、ここで消そうとはしない。

#### 一括の検収終了日が近い請求を見て、直す

検収終了日を正しく置くのは必須である。一括計上は提供終了日が既定で入るので、空では止まらない。予定と違うこともシステムは知りようがない。経理が、日付が近づいた請求を見てメンテする。

会計を使っていない組織では出さない。空欄探しではない。左を明細行にはしない。

請求一覧の行に、月次計上／一括計上の印を出す。1枚に両方の明細が混ざるなら、両方の印を出す。一括明細の検収終了日の最小を「次の検収」とする。次の検収が近い請求を絞る。右の既存の検収入力で直す。複数の一括明細がある請求は、右で明細を見て直す。自動では直さない。合っていれば触らない。

1件は、直したとき、または予定どおりだと確認したとき終わり。全体は、一覧を取り直して、次の検収が近い一括の請求が無ければ終わり。

#### 今月の仕訳を、確認用と突き合わせてロックする

今月分の未ロック仕訳を、1行ずつ目で確かめてロックする。先に請求一覧で、その月に立つべき確定と入金が足りているかを見る。足りない仕訳はここには出ない。

足りてから仕訳一覧を、計上日が作業対象月（既定は先月）・まだロックしていない、で絞る。1行が1仕訳。各行の確認用（数式）とメモを見る。明細の税抜や税、期間、月次なら何回目か、一括なら検収日が、その仕訳の金額・日付と事実どおりかを目検する。合っていれば一番左をチェックしてロックする（第2.3節）。来月以降は残す。合わない行（未充当、手数料、手動、逆仕訳、回数のずれ）は、右の請求で原因を直してからロックする。仕訳の金額は触らない。締めは翌月に入ってから行うことが多い。一覧の既定期間は先月である。メモは左の行で残せる。

1件はロックできれば終わり。全体は、一覧を取り直して、作業対象月の未ロックが空なら終わり。

## 2. 原則

### 2.1 既存操作と同じ結果

横断で実行する操作の業務結果は、契約サービス配下の契約履歴および請求ボードと同一である。条件、拒否、権限、同期処理、操作キー、版比較も同じ。横断用に結果を変えない。横断専用のApex結果は持たない。既存手続きを呼ぶ。

ボタンを押したあとの画面と手順も、特段の理由がなければ、契約履歴の見積操作ハブまたは請求ボードと同じである。横断用に微妙に違うUIを置かない。同じコンポーネントを使う。使えないときだけ、見た目と手順が同じ別実装にしてよい。特段の理由は本文に書く（仕訳のLock／Unlockの左チェックと保存、仕訳メモの左編集、仕訳追加項目の列モード、ウィザードを埋め込まない、第2.2節の置かない操作）。

「実施する」とは、横断の一覧に留まったまま、既存と同じ操作を同じ条件で実行することである。左の行から契約サービス／契約履歴へ遷移してハブやボードを開くだけは、実施に入らない。仕訳のLockとUnlockは、左の行選択から実行してよい。結果は請求ボード仕訳タブのLock／Unlockと同じである。

### 2.2 提供する操作

右に置く操作は、第1節の業務を1件終わらせるために、契約履歴または請求ボードが既に持つ操作だけである。横断だけの新しい操作は置かない。配下に無い入口（商談の `+見積`）は置かない。

右にも置かない（1つ目の方法で行う）。

- 見積ウィザードの商品明細編集と、それを開く本体編集・コピー
- 差し戻し、受注済みのカスタム項目、契約サービスを編集する（第1節）
- 受注直後の請求に戻す（差し戻しと同じイレギュラー。想定業務にしない）
- 見積の Archive（発行・送付・受注が第1節の終わり方。不採用はレコードページ）

請求ボードの分割・端数・請求情報・反映・確定・発行・送付・入金・入金編集・取消・検収・手動仕訳・Lockは、第1節の請求／仕訳の業務に必要なので右に置く。仕訳一覧のLockとUnlockは請求ボード仕訳タブと同じ操作である。新しい操作ではない。仕訳追加項目の列モードは左の表示切替であり、新しい操作ではない。商品明細の数量・単価・期間は右で参照する。直すときはレコードリンクへ。

### 2.3 一括はしない

複数件を選んでまとめて実行する操作は持たない。発行・送付・確定・入金その他は、すべて1件ずつボタンを押す。目検を経ない実行はさせない。

例外は仕訳のLockとUnlockだけである。仕訳一覧の一番左で行をチェックし、表の上の保存で実行できる。一括選択とクリアもできる。対象は今のページのチェック可能行だけである。ページを送ったらチェックは消える。取得済み500件を一括では選ばない。見積・請求の一括発行・一括送付は持たない（Core第4.8節・第7.10節）。Core第7.10節の「横断の発行・送付は持たない」は、一括を指す。個別の発行・プレビュー・送付は横断に置く。

処理は既存と同じ同期である。裏では回さない。キューに載せない。

### 2.4 左は探す、右は操作する

画面いっぱいのLWCである。ポップアップにしない。

一覧は3つだけである。見積、請求、仕訳。受注一覧と更新商談一覧は置かない（第1節）。

右の作業面の名は次とする。見積一覧は見積書タイル。請求一覧と仕訳一覧は請求書タイル。カードという呼びは使わない。

| | 左 | 右 |
| --- | --- | --- |
| 役割 | 探す。表示だけ | 操作する |
| 置くもの | 一覧。状態はアイコンのみ（押して実行しない） | 表・編集・ボタン |
| 置かないもの | ボタン、明細表 | レコードページそのもの |

仕訳一覧の左だけ例外とする。一番左にチェックボックスを置き、一括選択とクリアもできる。表の上に保存を1つ置く。LockとUnlockとメモは同じボタンである。Lockフィルタが未Lockならチェックも保存も青。Lock済みならチェックも保存も赤。青はLock、赤はUnlock。選んだ行を、ボードと同じ確認のあとLockまたはUnlockできる。Unlockは理由必須（Accounting第9.5節）。チェックが無くメモの変更も追加項目の変更も無ければ実行できない。LockまたはUnlockに成功したら、いまのフィルタで左を取り直す。右に出している請求書タイルも取り直す。メモ／追加項目だけの保存では左を取り直さない。Lock／Unlockが拒否されたら追加項目も書かない。

これ以外に、仕訳一覧だけ左上のさりげない切替を置く。特段の理由は、追加項目を確認用と並べて列で見ないと目検できないことである。切替ONでは右ペインを閉じ、表を全幅にする。既存列は残し、その右へカスタム列を出す。インライン編集。保存は今の1つ（メモ・追加項目・Lock／Unlock）。このモードでは行クリックで右タイルを開かない。請求書名リンクは可。取消・取消済の追加項目は参照。同じ文の全行一括は持たない。切替OFFは今どおり。請求一覧の左は完全に参照のみ。請求書のメモ列も見ることだけ。追加項目のカスタム列は請求一覧左に足さない。Accounting OFFでは仕訳一覧をメニューに出さない。

行のどこをクリックしても右へ出す。名前列のレコードリンク（商談名、契約履歴名、請求アカウント。仕訳一覧は請求書名も）だけは別タブのレコードページへ行き、右は開かない。未選択の右は空でよい。

左は最後にサーバが返した行である。開く・リロード・フィルタ変更で取り直す。グループ化・ソート・ページ送りでは取り直さない。開いたあとの自動再取得、ポーリングはしない。自分の成功による左の更新もしない。例外は仕訳のLock成功とUnlock成功だけである。いまのフィルタで左を取り直す。右を開くとき・ボタンを押すときはサーバの今を読む。拒否は既存と同じ条件で右に出す。LockとUnlock以外では左の行は消さない。詳細は「取得」。

請求の行が増える・入れ替わる操作のうち、第1節の業務に要るもの（別の請求へ分ける、確定済み取消）は横断で行う。成功後は右の当該Versionグループだけ取り直す。左の一覧全体はリロードしない。受注直後に戻すは右に置かない（第2.2節）。

Accounting OFFでは仕訳一覧、会計タグ、検収の残り探しを出さない。権限の出し分けは既存のハブ／ボードと同じである。出しているのに条件不足なら、押しても実行しない。グレーの常時表示にはしない。

BIは作らない。レポート、グラフ、ピボット、独自数式、任意SOQL、保存済みビュー、列の自由追加、CSVダウンロードは持たない。

一覧・列・フィルタは第1節の業務を満たす。足りなければ足す。業務の説明は第1節が正である。

左は表示だけ。状態はアイコンだけ（未送付・送付済み・発行あり、など。押して実行はしない）。**行のどこをクリックしても**右へ出す。3一覧とも同じ。表・編集・ボタンは右だけ。仕訳一覧の左チェック・メモ編集・保存は第2.3節・第2.4節。列モードONでは行クリックで右を開かない。チェックとメモ欄・追加項目欄のクリックは右を開かない。レコードリンクと同じ。入力欄にフォーカスがあるときは矢印を奪わない。

右は横断の作業面だけで、商談・契約履歴・請求のレコードページではない。名前が出ている列とグループ見出しはSalesforceのレコードリンク（別タブ）。対象は商談名、契約履歴名、請求アカウント。仕訳一覧は請求書名も。リンクをクリックしたときは右を開かず別タブ。行の他の場所は右。

一覧の視認（左）と、操作時の拡大（右）を分ける。左の1クリックは、契約サービス／履歴へ遷移してハブを開く代わり。右で送付先・税抜・見出しを数秒見てから押す。終わったら左の次。行に送付ボタンを並べて無目検で連打する、ではない。

| --- | --- | --- |
| 見積一覧 | 1行＝1 Estimate（契約履歴）。明細なし | 見積書タイル（見出し・見積商品テーブル・ボタン） |

#### 左の形（決定）

表。3一覧とも同じ。行の他の場所をクリックすると右へ。商談名・契約履歴名・請求アカウント（仕訳は請求書名も）はレコードリンク。明細は出さない。見積は1行＝1 Estimate。候補カードにはしない。

列が揃う。待ち行列のスキャンと矢印の上／下が自然。ソートは最大2項目。列の出し分けはしない。

右にフォーカスがあるときも、矢印の上／下で左の表の前行／次行へ送る。3一覧とも同じ。今のページの先頭で上、または末尾で下を押したら、左を前／次のページに切り替え、そのページの末尾または先頭の行を選ぶ。右もその行にする。最初のページの先頭で上、最後のページの末尾で下は、動かない。左／右の矢印は行送りに使わない。見積の別案へ飛ばない。別案は左の表を見てクリックする。グループ見出しと合計行には止まらない。入力欄・送付プレビューの本文・仕訳のメモにフォーカスがあるときは矢印を奪わない。

#### 左の列・グループ・ソート・フィルタ（決定）

BIは作らない。レポート、グラフ、ピボット、独自数式、任意SOQL、保存済みビュー、列の自由追加は持たない。見積一覧と請求一覧の左にカスタム項目の列は出さない。仕訳一覧だけ、第2.4節の列モードで既存列の右へ出す（Core第11.4.4節）。見積商品の列は出さない。

- パッケージ標準項目の列は固定（表示／非表示しない。順番も入れ替えない）
- グルーピング項目もパッケージ固定。左端に並ぶ。一覧ごとにセットは別。件数は3に固定しない（だいたい4。仕訳は計上日軸なのでセットが違う）
- グルーピング項目の順番だけ入れ替えられる
- 規定のグルーピング項目は、グループ化をOFFにもONにもできる。ONの数は0〜全部。3つだけ、ではない
- グループ化OFFのときは、その項目は左端の通常列として残る（消さない）
- グルーピング項目は固定列に重ねない。同じ項目を2列にしない
- ソートは最大2項目。グループ列でも、グループでない列でも指定できる。第一（左）が優先。第一が同じ行の中で第二（右）が効く。グループ化ONなら、その2段ソートは1つ上の親グループの中。全部OFFなら表全体。各キーは昇順／降順。画面のソートは、サーバが返した行の並べ替えである

- フィルタに使える項目はパッケージ固定。値の指定だけ。項目を増やさない。フィルタの値を変えたらサーバから取り直す（「取得」）
- 文字の一致: 請求名（`Invoice__c.Name`。請求番号。第1節の請求書番号と同じ）だけ部分一致。空は掛けない。取引先・請求アカウント・契約サービス・仕訳の請求はルックアップで1件選ぶ。名前の部分一致では探さない

**小計・合計（決定）**

グループ項目ごとに合計のトグルを置く。グループ化のON/OFFとは別。既定はOFF。ONにした段だけ、そのグループの末尾に合計行を出す。3一覧とも同じ。

合計行は数値・通貨列だけ足す（見積税抜、請求の税抜、仕訳の金額）。日付・名前・アイコンは空。行に背景色（パッケージ固定の1色）。

数字は取得した行のそのグループ全行。今のページの部分合計は出さない。グループがページをまたぐときは、最終データ行があるページにだけ合計行を出す。途中ページには出さない。上限で切れているときの合計は取得分だけである。

グループ化OFFの項目に合計は出ない。グループ化をOFFにしたらその段の合計行も消える。画面を閉じたらトグルも既定OFFに戻る。

合計行はデータ行ではない。件数に含めない。クリックしても右を開かない。矢印でも止まらない。取得上限の内側。

請求の契約履歴見出し（見積税抜・請求合計・差額）はトグルと別で、契約履歴グループONのとき常時。確定目検用。トグルONならその段に税抜の合計行も出る。グループOFFなら差額は行に繰り返す（第5節 請求一覧）。

見積で契約サービス段をONにすると別案の税抜が足される。嘘になりうる。止めない。利用者がトグルする。

画面を閉じたらパッケージの既定フィルタ・既定グループ・既定ソートに戻す（その場だけ）。

左にリロードボタンを置く。意味は「同じフィルタでサーバの今を取り直す」。開いたあとの自動再取得、ポーリングはしない。自分の成功による左の更新もしない。例外は仕訳のLock成功とUnlock成功（上表）。メモだけの保存では取り直さない。アイコンの自動更新はしない。サーバから左を取り直すとき、保存していない仕訳メモは捨てる。確認は出さない。グループ化・ソート・ページ送りでは取り直さないので、その場の未保存メモは残る。

1ページのデータ行: 見積・請求は20件。仕訳は50件。グループ見出しと合計行は件数に含めない。

- ページ番号のクリックで送ったときは、右で開いている行が今のページに無くても、右は維持する

一番左はチェック。Lockのアイコン列は置かない。チェックのクリックは右を開かない。一括選択とクリアは第2.3節。対象は今のページのチェック可能行だけ。ページを送ったらチェックは消える。Lockフィルタは未LockかLock済みだけ。空にできない。すべて、は置かない。未Lockならチェックできる行は未Lockだけ。Lock済みならチェックできる行はLock済みだけ。未Lockのときチェックは青、保存も青。Lock済みのときチェックは赤、保存も赤。色はパッケージ固定。表の上に保存を1つ。ラベルは保存のまま。直したメモと追加項目を書き、チェックした行があれば未LockならLock、Lock済みならUnlockする。Lockはボードと同じ確認。Unlockはボードと同じ確認と理由（Accounting第9.5節）。チェックが無くメモの変更も追加項目の変更も無ければ実行できない。権限が無ければ、チェックしてのLock／Unlockはボードと同じ拒否。チェックがある保存でLock／Unlockが拒否されたら、メモも追加項目も書かない。画面の直した文はそのまま残る。メモ／追加項目だけの保存（チェックなし）はLock／Unlock権限を要しない。LockまたはUnlockに成功したら、いまのフィルタで左を取り直す。既定が未LockならLockした行は山から消える。Lock済みフィルタならUnlockした行は山から消える。右の請求書タイルも取り直す。メモ／追加項目だけの保存では左を取り直さない。Unlockは右の請求書タイルでも1件ずつできる。

メモは左のセルで直す。Lock済みでも可。追加項目は列モードのセルで直す。未Lockは出している追加項目。Lock後は仕訳ロック除外にある項目だけ。取消・取消済は参照。保存は表の上の1つ（上段）。ボードの行保存は操作キー・行ロック・版比較を使わない。後から保存した文が残る。一括で同じ文は書かない。メモ欄・追加項目欄にフォーカスがあるときは右を開かない。矢印も奪わない。右の請求書タイルでも同じメモを直せる。開く・リロード・フィルタ変更で左を取り直すときは、保存していないメモと追加項目は捨てる。確認は出さない。残したい文は先に保存する。

会計タグは列にもフィルタにも出さない。タグは請求の事実であり、仕訳のLockしてよいかの軸ではない（第1節）。タグで拾うのは請求一覧。仕訳の全行に同じ請求のタグが付くと、売掛残りの売上仕訳まで「触るな」に見える。行をクリックした右の請求書タイルには、契約履歴の請求ボードと同じ True のタグラベルを出す（操作31）。

**確認用**

左の列。仕訳の数式を読む。文面は転記済み（`SPEC-098`／`CHANGE-247`。Accounting第9.1.1節）。会計タグへ入れない。メモへ自動転記しない。

実装: 表示と作業を分けると、動かす操作UIは原則右の1件だけになる。左は読むだけなので、行ごとの発行・送付の状態機械を持たない。同期待ちは右の1操作だけ。左は止めない。仕訳一覧だけ、チェックとメモ編集と保存が左にある（第2.4節）。列モードの切替とカスタム列も左（第2.4節）。

左の取得は「取得」に従う。グループ化・ソート・ページでは取り直さない。

右を開くとき・ボタンを押すときはサーバの今を読む。誰かがArchiveした、すでにOrdered、版が変わった、などは今と同じ拒否を右に出す。左の行は消さない。左をクリックしなくても、右にフォーカスがあるとき矢印の上／下で左の表の前行／次行へ送れる。ページの端はページネーションへ（「左の形」）。左／右の矢印は行送りに使わない。入力欄・送付プレビューの本文にフォーカスがあるときは矢印を奪わない。右は選んだIDの最新を取り直す。

複数人: 左をライブに同期しないので、制御はかなり単純になる。一覧を行ロックしない。衝突は右の1件の操作時だけ（今の操作キー・版比較）。2人が同じ件を右に出していても、後から押したほうが今と同じエラー。リアルタイム共同編集にはならない。

成功後の取り直し: 左は触れない（リロードボタンまで）。例外は仕訳のLock成功とUnlock成功である。いまのフィルタで左を取り直す。右は成功結果をその作業面に出す。受注成功後も左の行は残る。次にその行を右へ出すか矢印で戻ると、右がエラー（もうEstimateではない）。一覧から消すのはリロードしたとき。Lockした仕訳は、未Lockフィルタなら取り直しで消える。Unlockした仕訳は、Lock済みフィルタなら取り直しで消える。メモ／追加項目だけの保存では左を取り直さない。

### 仕訳一覧

経理の仕訳確認は、複数請求の仕訳を計上日で並べて流す。請求書単位で見るのは請求一覧の右の請求書タイル。請求でのグループ化はOFFからONできる。既定はグループなし・計上日順。1ページは50件。

導線: 左で先月の未Lockを計上日順に確認する → 確認用と金額が合えば一番左をチェックし、表の上の青の保存を押す。合わなければ行をクリック → 右にその請求書タイル（仕訳。クリックした行を選択状態）→ 原因を直してから保存。成功したら左を取り直す。未Lockフィルタならその行は消える。Unlockする日はLock済みフィルタ（チェックと保存は赤）。理由はボードと同じ。成功したら左を取り直す。矢印の上／下で次の仕訳へ。ページの端は次／前のページ。同じ請求なら右は維持。メモは左のセルで直し、同じ保存で書く。追加項目の列モードは第2.4節。ONでは行クリックで右を開かない。列モードONでは右を出さず、追加項目を既存列の右で直す。行クリックは右を開かない。請求書名リンクは可。
