## 記載ルール

台帳の書き方だけを定める。着手条件と完了判定は`開発ルール.md`を正とする。

- IDは `SPEC-001` / `CHANGE-001` / `UPDATE-001` / `BUG-001` / `TEST-001`。採番は`要対応.md`と`対応済.md`を通して一意。次番号は両ファイルの最大+1
- 登録日と更新日は `YYYY-MM-DD`。ステータスや内容を変えたら更新日も変える
- 完了したら`対応済.md`へ移す。削除しない。完了行は戻さない。章立てや地図を直すときも、対応済のIDを要対応へ再掲しない。あとから出た差分は新しいCHANGEにする。テスト担保だけの差分は新しいTEST（`開発ルール.md`第3.3節）
- SPECは規模を付ける。CHANGE / UPDATE / BUG / TESTには付けない
- 「Push する内容」はチケットではない。採番しない。未 push のローカル commit の控えである。行は表（判定／ID／一言）。未 push の commit と ID で対応する（`開発ルール.md`第12.13節）。`docs/機能仕様書/` は表に出さない。`!push`がワークツリーの最新を必ず送る。開発ルール・要対応・対応済・機能仕様書を直したらその場でローカル commit する（第3.5節）。判定は`大丈夫`／`怪しい`／`絶対だめ`（顧客依存＝パッケージ標準ではない変更）。`ContractTestDataFactory`の導入先だけなら判定`大丈夫`・ID`ContractTestDataFactory`・一言`導入先差し替え`。空は判定`（なし）`の1行だけ。同じ ID を二重に積まない
- 「テストカバー」はチケットではない。着手順に使わない。成功可否とカバー率は別列。中身はApexの一言。総合点で CHANGE も TEST も自動で切らない。TEST化は`!TEST発掘`（第12.15節）
- TESTの内容は作業範囲の一文。確認待ちの commit メッセージと「Push する内容」の一言も同じにする。Org 成功・カバー75%超・地図最新化は Goal であり内容に書かなくてよい（第3.1.1節）
- 「専用Apex行が無いテストクラス」はメモ。チケットではない。採番しない

### コード量の構成（2026-08-31時点）

空行を除く行数。クラス別ではない。

安心度は1〜3。高いほどよい。3厚い、1薄い。orgで仕様の結果まで見ていれば厚い。Jestのゲートは画面専用なら中、画面全体や保存結果は見ない。MECE度は1〜3。高いほどよい。仕様の一文を漏れなくダブりなく Assertion してカバーできているか。合計行には付けない。

- 安心度
  - **3**: 厚い。orgで仕様の結果まで見ている
  - **2**: 中。一部は結果、ゲートや通過が混ざる
  - **1**: 薄い。画面全体や保存結果を見ない、または呼べただけ
- MECE度
  - **3**: 本線の仕様文を漏れなく、同じ一文をダブらせず Assertion している
  - **2**: 漏れかダブりの片方がある
  - **1**: 漏れもダブりも大きい。または呼べただけでカバーしているつもり

行が多いことと安心は別である。同じ一文を何本も、または呼べただけ、だと MECE度は下がって安心は増えない。見積Apexは請求Apexと同じくサーバは見ている。Create／Save／Validationが重なり通過テストも長いので、安心3でも MECE度1になる。

量の主は見積・請求の Apex クラス別テストである。横断シナリオは全体の約2%。整理・補充の候補を見るなら MECE度が低い見積・請求の Apex。シナリオと Jest の画面ゲートは先に削らない。

- 対象テスト: 専用`*Test.cls`。無ければ `※ 要追加` または `※ 明確に不要`
- 中身: そのApexが何をするか一言
- 成功可否: `成功`、または `失敗 XxxTest.method`（複数は読点）。スタックは書かない
- カバー率: Salesforce が出すその Apex の行カバー（0〜100）。失敗していても値はそのまま
- 本線の多さ: そのクラスが抱える業務手続きの多さ。1〜3。高いほど本線が多い
  - **3**: 本線が多い
  - **2**: 普通
  - **1**: 少ない
- Assertion: 1〜3。高いほどよい。実装が仕様と違ったらテストが赤になるか
  - **3**: 仕様の結果を値で見る。例: 請求を確定したあと、取引状態が「確定」であることを `assertEquals` する。確定なのに「下書き」のままだとテストが落ちる
  - **2**: 一部の経路は3、残りは1
  - **1**: 呼べて例外が無ければ合格。例: 確定メソッドを呼んで `assertEquals(null, エラー)` だけ。取引状態が「下書き」のままでも緑。カバー率だけ上がる
- MECE度: コード量の構成と同じ。1〜3。高いほどよい
- 汎用度: 1〜3。高いほどよい。クライアント単位でテストを変えなくてよいか。顧客依存は DataFactory などへ逃がせているか
  - **3**: クライアント単位で変える必要がない。変わる場所は DataFactory 等へ逃がせている
  - **2**: 少し修正が必要
  - **1**: 顧客依存が多い
- 総合点: 成功している行だけ 1〜5。高いほどよい。失敗している行は空。掛け算はしない。Assertion・MECE度・カバー・汎用度を見て付ける
  - **5**: 申し分なし。仕様の結果まで見ていて、漏れもダブりも少なく、カバーも足りる
  - **4**: 結果は見ている。カバーか MECE か経路の一部に隙がある
  - **3**: 半分。一部は結果、残りは通過。カバーは中程度。または MECE が2
  - **2**: 本線が多いのにカバーが低い、Assertion が低い、または MECE が低い
  - **1**: だめ。呼べただけ。MECE 1。または本線が多いのにカバーが低く、結果も見ていない

## Push する内容

未 push のローカル commit の控えである。チケット表ではない。採番しない。書き方は`開発ルール.md`第3.5節・第12.13節。

`docs/機能仕様書/` は表に出さない。`!push`がワークツリーの最新を必ず送る。

ローカル commit したら、判定・ID・一言を表へ1行足す。`!push`が送ったら空にする（判定`（なし）`の1行だけ残す）。

判定は顧客依存（パッケージ標準ではない変更）について付ける。

| 判定     | 意味                                                                                                      |
| -------- | --------------------------------------------------------------------------------------------------------- |
| 大丈夫   | パッケージ標準の修正。または唯一の例外`ContractTestDataFactory`の導入先差し替えだけ                       |
| 怪しい   | 顧客依存かどうか判別できない。混在、導入先の値が製品に混ざっている疑い                                    |
| 絶対だめ | パッケージ標準ではない顧客資材。retrieve、顧客CMDT行、プロファイル、他クラスへのテナント値、第3.6節の禁止 |
