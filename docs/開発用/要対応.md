## チケットの種類

| 種類   | 意味                                                                                                                                            |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| SPEC   | 仕様を決める検討。決まっていない論点                                                                                                            |
| CHANGE | 決定事項。仕様は決まっており、実装または追随する。規模が大きくても、やると決めたものはここへ置く                                                |
| UPDATE | 候補。やるかどうかは未決定。ROIがわからないか、膨大な時間がかかるため、決定まではしていない。仕様も確定しない。やることに決めたら`CHANGE`へ移す |
| BUG    | 不具合の修正                                                                                                                                    |
| TEST   | テストクラスの過剰の整理、テストクラスの追加など。実際の機能や仕様に影響を一切及ぼさない。担保を充実するためのチケット                          |
| DESIGN | 見た目だけ。余白・字・シェル・ボタン族。業務結果と仕様本文は変えない。正本は`画面見た目.md`。機能仕様書へ転記しない                             |

`CHANGE`と`UPDATE`の違いは着手時期ではない。決めたか、まだ決めていないかである。

テスト拡充の行き先は次。カバー率表は地図であり着手順ではない（「テストカバー」）。

| テストで起きること                             | 切るもの                                                                             |
| ---------------------------------------------- | ------------------------------------------------------------------------------------ |
| 本文が明瞭で実装が反している                   | BUG                                                                                  |
| 本文が明瞭で実装が追いついていない             | CHANGE                                                                               |
| 本文が不明・誤り・矛盾・文書間食い違い         | SPEC                                                                                 |
| 製品は本文どおりでテストだけが本文と違う／余剰 | TEST                                                                                 |
| 見た目だけが`画面見た目.md`に追いついていない  | DESIGN。本文が区画・操作・固定文言を既に書いていれば CHANGE または BUG               |
| カバーを足して安心を増やす、専用テストの追加   | TEST。横断シナリオの方針は`SPEC-049`。クラス単位は地図の行とTEST表（完了`SPEC-105`） |

## 記載ルール

台帳の書き方だけを定める。着手条件と完了判定は`開発ルール.md`を正とする。

- IDは `SPEC-001` / `CHANGE-001` / `UPDATE-001` / `BUG-001` / `TEST-001` / `DESIGN-001`。採番は`要対応.md`と`対応済.md`を通して一意。次番号は両ファイルの最大+1
- 登録日と更新日は `YYYY-MM-DD`。ステータスや内容を変えたら更新日も変える
- 完了したら`対応済.md`へ移す。削除しない。完了行は戻さない。章立てや地図を直すときも、対応済のIDを要対応へ再掲しない。あとから出た差分は新しいCHANGEにする。見た目だけの差分は新しいDESIGN。テスト担保だけの差分は新しいTEST（`開発ルール.md`第3.3節）
- SPECは規模を付ける。CHANGE / UPDATE / BUG / TEST / DESIGNには付けない
- 「Push する内容」はチケットではない。採番しない。未 push のローカル commit の控えである。行は表（判定／ID／一言）。未 push の commit と ID で対応する（`開発ルール.md`第12.13節）。`docs/機能仕様書/` は表に出さない。`!push`がワークツリーの最新を必ず送る。開発ルール・要対応・対応済・機能仕様書・画面見た目を直したらその場でローカル commit する（第3.5節）。判定は`大丈夫`／`怪しい`／`絶対だめ`（顧客依存＝パッケージ標準ではない変更）。`ContractTestDataFactory`の導入先だけなら判定`大丈夫`・ID`ContractTestDataFactory`・一言`導入先差し替え`。空は判定`（なし）`の1行だけ。同じ ID を二重に積まない
- 「テストカバー」はチケットではない。着手順に使わない。成功可否とカバー率は別列。中身はApex／LWCの一言。総合点で CHANGE も TEST も DESIGN も自動で切らない。TEST化は`!TEST発掘`（第12.15節）。Jestを切るときは信号の後ろに`Jest`。Jestの成功は安心としない
- TESTの内容は作業範囲の一文。確認待ちの commit メッセージと「Push する内容」の一言も同じにする。Org 成功・カバー75%超・地図最新化は Goal であり内容に書かなくてよい（第3.1.1節）
- 「専用Apex行が無いテストクラス」はメモ。チケットではない。採番しない

| 規模 | 意味                                                                                                       |
| ---- | ---------------------------------------------------------------------------------------------------------- |
| 小   | 表示、仕様の書き方、誤解防止。推奨がほぼ自明で、メリデメなくやった方がよい                                 |
| 中   | 検討やメリデメ判定など決定を要する。論点は1件に閉じ、後続の仕様変更は限定される                            |
| 大   | 検討やメリデメ判定など決定を要する。対象が広く、後続の識別子・保持体・権限・共通方式または処理本線が変わる |
| 特大 | 利用者が「これは特大」と言ったときだけ付ける。検討順の最後。AIは特大に上げない                             |

- 対象テスト: 専用`*Test.cls`。無ければ `※ 要追加` または `※ 明確に不要`
- 中身: そのApexが何をするか一言
- 成功可否: `成功`、または `失敗 XxxTest.method`（複数は読点）。スタックは書かない
- カバー率: Salesforce が出すその Apex の行カバー（0〜100）。失敗していても値はそのまま
- 本線の多さ: そのクラスが抱える業務手続きの多さ。1〜3。高いほど本線が多い
  - **3**: 本線が多い
  - **2**: 普通
  - **1**: 少ない
- Assertion: 1〜3。高いほどよい。実装が仕様と違ったらテストが赤になるか
  - **3**: 仕様の結果を値で見る。例: 請求を確定したあと、取引状態が「確定」であることを `assertEquals` する。確定なのに「下書き」のままだとテストが落ちる
  - **2**: 一部の経路は3、残りは1
  - **1**: 呼べて例外が無ければ合格。例: 確定メソッドを呼んで `assertEquals(null, エラー)` だけ。取引状態が「下書き」のままでも緑。カバー率だけ上がる
- MECE度: コード量の構成と同じ。1〜3。高いほどよい
- 汎用度: 1〜3。高いほどよい。クライアント単位でテストを変えなくてよいか。顧客依存は DataFactory などへ逃がせているか
  - **3**: クライアント単位で変える必要がない。変わる場所は DataFactory 等へ逃がせている
  - **2**: 少し修正が必要
  - **1**: 顧客依存が多い
- 総合点: 成功している行だけ 1〜5。高いほどよい。失敗している行は空。掛け算はしない。Assertion・MECE度・カバー・汎用度を見て付ける
  - **5**: 申し分なし。仕様の結果まで見ていて、漏れもダブりも少なく、カバーも足りる
  - **4**: 結果は見ている。カバーか MECE か経路の一部に隙がある
  - **3**: 半分。一部は結果、残りは通過。カバーは中程度。または MECE が2
  - **2**: 本線が多いのにカバーが低い、Assertion が低い、または MECE が低い
  - **1**: だめ。呼べただけ。MECE 1。または本線が多いのにカバーが低く、結果も見ていない
