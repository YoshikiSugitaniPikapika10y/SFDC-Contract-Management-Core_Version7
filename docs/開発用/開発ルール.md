# 開発ルール

作成日: 2026-08-28
更新日: 2026-08-31

AIと人が同じ手順で、漏れなく・正確に作業するための正本である。速さより正確さを取る。

業務ルールの正は仕様書の本文である。本書は「何をどの順で触るか」だけを定める。本書を読んでも仕様本文の結果は変わらない。

最悪の失敗は、仕様の細目を読まずにチケットや現行コードから解釈して実装することである。書いていないことを補わない。書いてある例外・禁止・条件を飛ばさない。

## 0. 信号

信号は先頭が `!` のトークンだけである。文中の「実装」「完了」「BUG」「push」などは信号ではない。メッセージ先頭の正規名だけが指令になる。`/` は使わない（Cursorのスラッシュコマンドと競合する）。

正規名は **`!`＋種類＋動詞** で揃える。種類は `CHANGE` / `BUG` / `SPEC` / `TEST`。動詞は `実装` / `検討` / `転記` / `発掘` / `並替` / `比較`。種類が一つに決まっているものは種類を省略する（`!完了` `!精査` `!push` `!ORG比較` `!GITHUB比較`）。

`!` が無ければ第12節を起動しない。ID・文書・章は信号の後ろに書く（例: `!CHANGE実装 CHANGE-011`）。

`× N`（半角 `x N` も可）を信号の後ろに書いたら、**その信号の1回分の単位を最大N件まで繰り返す**。例: `!完了 CHANGE × 5`、`!CHANGE実装 × 3`、`!SPEC転記 × 2`。候補がN件に満たなければ、ある分だけ実施し、足りない分はSKIPする。足りない分のチケットや作業を作らない。未達をエラーにしない。`× N`が無ければ従来どおり1件（並替・比較など表全体が単位の信号は1回）。単一IDだけを指定したときはその1件のみ（`× N`は付けても追加候補を足さない）。

| 正規 | 対象 | すること | しないこと | 節 |
| --- | --- | --- | --- | --- |
| `!CHANGE実装` | CHANGE。ID指定でBUGも可 | CHANGE表の次の1件（`× N`で最大N件）を仕様どおり実装し、確認待ちまで。残が無ければそのチケット範囲をローカル commit | UPDATE、SPEC、TESTの実装、勝手に完了、指定なしでBUGを取ること、候補不足分の捏造、push | 第12.1節 |
| `!BUG実装` | BUG | BUG表の次の1件（`× N`で最大N件）を仕様どおり直し、確認待ちまで。残が無ければそのチケット範囲をローカル commit | CHANGE、UPDATE、SPEC、TESTの実装、勝手に完了、候補不足分の捏造、push | 第12.10節 |
| `!TEST実装` | TEST | TEST表の次の1件（`× N`で最大N件）をテストだけ直す。デフォルト Org で対象テストが成功し、対象Apexの行カバーが75%を超える。地図の該当行を最新化して確認待ち。残が無ければ Goal をメッセージに入れてローカル commit | 製品コード・仕様本文、CHANGE、BUG、UPDATE、SPECの実装、勝手に完了、push、retrieve | 第12.14節 |
| `!SPEC検討` | SPEC | 表の次の未決SPECを本文まで読み、選択肢と推奨だけ出す（`× N`で最大N件） | 実装、本文確定、CHANGE作成、選択の採用、指定なしで特大を取ること、特大の検討を提案すること | 第12.7節 |
| `!SPEC転記` | SPECの確認待ち | 備考の決定を仕様本文へ落とし、CHANGEを切り、SPECを対応済へ移す（`× N`で最大N件）。触ったファイルをローカル commit | 実装、決定のやり直し、push | 第12.12節 |
| `!SPEC発掘` | 仕様本文 | 不明瞭・誤り・矛盾・文書間食い違い・削除候補をSPEC化（`× N`で最大N件） | 実装、本文修正、CHANGE/BUGを切ること | 第12.2節 |
| `!CHANGE発掘` | 仕様本文 | 明瞭な仕様の未追随をCHANGE化（`× N`で最大N件） | 実装、本文修正、BUGを切ること、仕様の発明 | 第12.8節 |
| `!BUG発掘` | 標準画面の操作 | 明瞭な仕様違反をBUG化（`× N`で最大N件） | 修正、仕様の発明 | 第12.4節 |
| `!TEST発掘` | 要対応のテストカバー | 地図から優先が高いものから取り、TEST表へ切る（`× N`で最大N件）。取り方は第12.15節。内容にGoalを書く | 実装、製品・仕様本文の修正、CHANGE/BUGを切ること、特大方針（`SPEC-049`／`SPEC-105`）を始めること、地図に無い行の捏造、表の出現順で機械的に取ること | 第12.15節 |
| `!精査` | 対応済 | 完了行を1件（`× N`で最大N件）、本文とコードで判定。差分は新CHANGE | 完了行の復活、実装 | 第12.3節 |
| `!CHANGE並替` | CHANGE表 | 着手順に並べ直す（表全体1回。`× N`の余りはSKIP） | 実装、本文・ステータス変更 | 第12.5節 |
| `!BUG並替` | BUG表 | 着手順に並べ直す（表全体1回。`× N`の余りはSKIP） | 実装、本文・ステータス変更 | 第12.11節 |
| `!SPEC並替` | SPEC表 | 標準仕様を先、異常系を後、特大を末尾に並べ直す（表全体1回。`× N`の余りはSKIP） | 実装、本文・ステータス変更 | 第12.9節 |
| `!完了` | CHANGE/BUG/TESTの確認待ち。`CHANGE`／`BUG`／`TEST`指定可 | 種類指定があればその表だけ。残が無い1件（`× N`で最大N件）を`対応済.md`へ移す。仕様とずれていればその場修正せず、差分を新しいBUG／TEST／CHANGEに切ったうえで元を対応済にする。仕様がおかしい・不明瞭ならSPECも切る。台帳だけ第3.5節でローカル commit | 実装、残がある行の完了、SPECの確認待ちを完了にすること、ずれのその場修正、製品コードの commit、push | 第12.6節 |
| `!push` | 未 push のローカル commit と `docs/機能仕様書/` | 第12.13節のゲートを満たせば、仕様書の最新を含めて「Push する内容」を空にしてから送る。仕様書は一覧に出さない。欠けたら送らない。止められたら原因（開発ルールかそれ以外）と次にすることを返す | 仕様とコードの突き合わせ、実装、force push、リモート URL の変更、`絶対だめ`の送信、ゲート未満の送信 | 第12.13節 |
| `!ORG比較` | デフォルト接続の Sandbox とワークツリーの `force-app` | パッケージが持つ識別子だけを資材別に表で返す。ワークツリーのみ（未配備）と両方の中身のずれを出す。docs は見ない | 実装、commit、push、チケット化、`force-app` への retrieve、パッケージに無い Org 資材を本表に出すこと | 第12.16節 |
| `!GITHUB比較` | 追跡リモートとワークツリー | パッケージ資材に加え、機能仕様書・開発ルール・要対応・対応済を資材別に表で返す。片方だけもある。「Push する内容」と未 push commit の ID 対応、載せてよい未 commit の有無を返す | 実装、commit、push、Org への接続、`docs/Old` を本表に出すこと | 第12.17節 |

UPDATEに信号は無い。触らない。種別なしの旧`!発掘`・旧`!並替`は無い。種類を付けた発掘・並替を使う。`!CHANGE実装`の指定なしはCHANGEだけである。BUGを表順で直すのは`!BUG実装`である。TESTを表順で直すのは`!TEST実装`である。TESTを切るのは`!TEST発掘`である。

文中の「つぎ」「次」「検討」「SPEC」は信号ではない。SPEC検討の開始はメッセージ先頭の`!SPEC検討`（旧`!SPEC`）だけである。

## 1. 正本と読む順

| 対象 | 場所 | 使うとき |
| --- | --- | --- |
| 作業手順 | 本ファイル | 毎回。最初に読む。信号は第0節。手順は第12節 |
| 未完了チケット | `docs/開発用/要対応.md` | 何をやるか。CHANGE表の行順が着手順。BUG表の行順がBUGの着手順。TEST表の行順がTESTの着手順。SPEC表の行順が検討順。「テストカバー」は地図。「Push する内容」は末尾の未 push 控え |
| 完了チケット | `docs/開発用/対応済.md` | 復活させない。採番の重複確認。差分は新しいCHANGE |

| Accounting仕様 | `docs/機能仕様書/仕様書_Accounting.md` | 仕訳（Accounting ON のとき） |

| クライアント設定 | `docs/機能仕様書/ユーザ設定.md` | 導入順、必須／任意、単位、変更可否と影響。値の意味は Core／Accounting／共通基盤 |
| 実装 | `SFDC-Contract-Management-Core_Version7/force-app` | コードとメタデータ |

権限の正本は`docs/機能仕様書/共通基盤.md`第3章・第10.4節である。日付算法は同書の日付部（旧称`日付仕様.md`。節番号は同一。コードの「日付仕様 第X節」は同義）。契約横断の画面は同書の契約横断部（旧称`docs/横断画面.md`。節番号は同一。コードの「横断画面.md 第X節」は同義）。操作ログの本文は同書第12章（Core 第2.5節と同義）。操作キー・行ロック・版比較の正は Core 第4.3.12節・第7.9.7節・第11.6節。実装の権限付け替えは`CHANGE-270`。

リポジトリ直下の`force-app`は空のスタブである。見ない。

次は根拠にしない。読まない。直さない。

- `docs/Old/`
- `仕訳機能_正式仕様_QA確定版.md`
- Accountingの旧宣言メタデータ（`GlJournalTemplate__c`等）。再定義が終わるまで現行仕様として読まない。ToBe枠には再定義後の識別子だけを書く

### 1.1 何を読むか

読む範囲は次に限る。

- チケットが書いた節番号の本文全部
- その本文が明示参照する節の本文全部
- 日付が絡むなら`共通基盤.md`の日付部の該当章（「日付仕様 第X節」は同義）

見出し、チケット要約、「隣の節」への拡大、記憶、類似機能からの類推はしない。例外、禁止、赤字、条件を飛ばさない。指定なしの全書通読はしない。

### 1.2 本文と備考と地図

業務結果の正は、Core / Accounting / 共通基盤の節本文である。日付算法の正は共通基盤の日付部（旧称`日付仕様.md`）。契約横断の画面の正は共通基盤の契約横断部（旧称`docs/横断画面.md`）。個別操作の業務結果はCore／Accounting。導入順・必須／任意・単位・変更可否と影響の正は`ユーザ設定.md`である。値の意味を本書から補わない。

- チケット備考は範囲と残作業である。備考から業務結果を補わない。備考にしか無い結果は第3.4節
- ToBe枠と`仕様:`コメントは地図である。本文と地図が食い違い、結果が変わるなら第3.4節。結果が変わらない地図のずれは、利用者が決めたあとで地図だけ直す
- 現行コードと前回の実装から仕様を推測しない
- チケットが古く本文が明瞭なら本文を正とし、備考へ差を1行書く
- 本文に無い結果は利用者に返す。本文を勝手に直さない

CoreとAccountingと共通基盤が、それぞれ明瞭でも結果が違うときは、近い方に合わせない。第3.4節へ進む。

## 2. チケットの種類と着手条件

種類とステータスの語彙は`要対応.md`を正とする。ここでは着手してよいかだけを定める。

| 種類 | AIがしてよいこと | してはいけないこと |
| --- | --- | --- |
| SPEC | 利用者と詰めて選択結果を備考へ残す。転記はあとで`!SPEC転記` | 実装する。選択直後に仕様本文やCHANGEを書く。仕様が決まる前に識別子を仮置きする |
| CHANGE | 仕様どおり実装または追随する | 仕様に無い結果を足す。範囲外のリファクタ |
| UPDATE | 触らない。質問されても仕様を確定しない | CHANGEへ独断で移す。実装する |
| BUG | 仕様の一文に実装を合わせる | 仕様を黙って変える。仕様が不明瞭・誤り・矛盾なら第3.4節 |
| TEST | テストの追加・削除・整理だけ。機能と仕様は変えない | 製品Apex／LWC／メタ／仕様本文を触ること。テストで仕様を発明すること |

`要対応.md`の未決SPECが対象にしている識別子（権限、横断画面、設定入口、保持体など）は、そのSPECが決まるまで仮置きしない。

## 3. 1作業の進め方

同時に進めるCHANGEは1件である。BUGも1件である。TESTも1件である。ただし信号に`× N`があるときは最大N件まで連続してよい（第0節）。表の上から取る。利用者が別IDを指定したらそれだけをやる。CHANGEの表順は`!CHANGE実装`、BUGの表順は`!BUG実装`、TESTの表順は`!TEST実装`である。

orgへのデプロイと実行確認は、利用者が組織を指定したときだけ行う。指定が無ければファイルとテストの編集までを確認待ちにしてよい。**例外は`!TEST実装`である。** デフォルト Org（CLIの default username。利用者が別組織を書いたらそちら）で対象テストを回し、第3.1.1節の Goal を満たす。

利用者が組織を指定している `!CHANGE実装` / `!BUG実装` は、チケット範囲のテストをデフォルト Org で回してから確認待ちにする。失敗したら確認待ちにしない。製品の仕様違反なら直すか BUG を切る。導入先の値なら`ContractTestDataFactory`だけ直す。retrieve しない。全件 RunLocalTests は利用者が書いたときだけ。

Git の正はパッケージ（`force-app`）である。Org は配備先である。retrieve の置き場と取り込み可否は第3.6節。

### 3.1 実装（CHANGE / BUG）

1. 第1.1節の範囲で本文を読む。日付が絡むなら`共通基盤.md`の日付部の該当章を先に読む（「日付仕様 第X節」は同義）
2. 実装してよい結果を本文から取り出す。チケットが古く本文が明瞭なら本文を正とし、備考へ差を1行書く。仕様が空・不明瞭・誤り・矛盾、文書間の食い違い、削ってよい記載、備考にしか無い結果、または本文に無い判断なら第3.4節。実装を続けない
3. コードを触る前に、実装する結果を仕様本文の引用で1〜3行書く。引用できないならまだ読めていない。実装に入らない
4. `対応済.md`の「新設するコード」と、対象節のToBe枠で識別子を固定する。名前を実装時に変えない
5. その識別子の範囲だけを実装する。隣接クラスは、呼出または拒否を接続するために必要な行だけ直す。同じ業務結果がApexとLWCの両方にあるときは両方直す（日付は第8節）
6. 手続き・項目・入力規則の直上へ`仕様:`を付ける（第7節）
7. 仕様のその一文が破れたら落ちるテストを、そのCHANGEの範囲で足すか直す。製品全体のシナリオ拡充は`SPEC-049`であり、ここでやらない
8. 利用者が組織を指定しているときは、このチケット範囲のテストをデフォルト Org で回す。失敗したら確認待ちにしない（第3節）
9. チケットを更新する。残が無ければ確認待ちにする。`対応済.md`へは移さない。残があれば対応中のまま、備考へ残作業を1行書く
10. 残が無く確認待ちにしたら、第3.5節どおり「Push する内容」へ1行足してローカル commit する。残がある対応中ではしない。push は `!push` だけ
11. 残がある状態で次のCHANGEに入らない

### 3.1.1 実装（TEST）

TESTはテストクラスの過剰整理と追加だけである。機能と仕様には影響を一切及ぼさない。担保を充実するためのチケットである。旧`!test実装`は`!TEST実装`と同じ。

Goal はチケット内容である。地図の点数を上げることが Goal ではない。総合点は結果として書く。呼べただけの通過テストでカバー率や総合点を稼がない。75%は下限であり、通過で埋める許可ではない。

してよい／してはいけないは次である。

- Assertion: 仕様の結果の値で落ちる断言を残す。`assertEquals(null, エラー)` だけで緑にしない
- MECE: 同じ一文をダブらせない。落ちる断言が無い本線は足す。通過だけの重複は削る
- 汎用度: 顧客値は`ContractTestDataFactory`だけ。他の`*Test.cls`に Stage などを直書きしない
- 本線の多さは製品の量である。テストを増やして上げない
- 製品が仕様と違うときはテストを弱めない。TESTは対応中のまま、BUGまたはCHANGEを切る
- クラス単位の型は`SPEC-105`、横断シナリオは`SPEC-049`。名指しされていない特大は始めない

**Goal**（確認待ちにしてよい条件。全部満たす）。チケットの「内容」が作業範囲の正である。Org の成功とカバーは次の5〜7も Goal である。

1. 製品Apex、製品LWC、メタデータ、仕様本文、ToBe枠に差分が無い
2. チケット内容どおり、テストだけを足した／削った／直した。範囲外のクラスは触っていない
3. 残した断言は仕様の一文である。本文に無い結果をテストで正にしていない
4. 残作業が無い
5. デフォルト Org で、チケットの対象テストが成功している（全件 RunLocalTests は利用者が書いたときだけ）
6. その実行で Salesforce が出す対象Apexの行カバーが75%を超えている。Jest だけを触る TEST は6を課さない。対象バンドルの Jest が成功すればよい
7. `要対応.md`の「テストカバー」クラス表で、対象Apexの行の数値と評価（成功可否、カバー率、本線の多さ、Assertion、MECE度、汎用度、総合点）を今回の実行に合わせて最新化している

満たしたら第3.5節どおりローカル commit する。メッセージは `TEST-番号` と Goal の一行（チケット内容と同じ）。「Push する内容」の一言も Goal にする。Goal を満たしていない対応中では commit しない。失敗の原因が製品の仕様違反ならテストを弱めて緑にしない。TESTを対応中のままにし、BUGまたはCHANGEを切る。導入先の値だけなら`ContractTestDataFactory`だけ直す（第9節）。

手順は次とする。

1. 触ってよいのは `*Test.cls`、LWC の `__tests__`、チケットが書いた範囲の`ContractTestDataFactory`だけである
2. 製品Apex、製品LWC、メタデータ、仕様本文、ToBe枠は触らない。テストの断言で仕様を発明しない。本文に無い結果をテストで正にしない
3. チケット範囲のテストだけを足す・削る・直す。クラス単位の方針は`SPEC-105`、横断シナリオの方針は`SPEC-049`。名指しされていない特大は始めない
4. テストをデフォルト Org へデプロイして対象テストを回す。retrieve しない。製品コードはデプロイのために直さない
5. Goal の5〜7を地図へ書く。カバーが75%以下なら、仕様の一文で落ちる断言を足す（製品は触らない。通過だけで埋めない）。整理で75%を割るなら削りすぎである。戻すか断言を残す
6. チケットを更新する。Goal を満たせば確認待ち。`対応済.md`へは移さない。残があれば対応中のまま備考へ1行
7. 確認待ちにしたら第3.5節どおりローカル commit（メッセージに Goal）。地図の更新も同じ commit に入れる。push は `!push` だけ

### 3.2 仕様検討（SPEC）

SPECの流れは **検討 → 選択を備考へ → あとで本文転記** である。選択の直後に仕様本文へ落とさない。

1. `!SPEC検討`で開始する。現行仕様の該当節を第1.1節どおり読み、実装の現行挙動と突き合わせる。節の細目を読まずに推奨を出さない
2. 推奨を先に出し、選択肢（A/B/C等）ごとに結果とメリデメを短く書く。データの処理結果が変わるものと注意書きを分ける。すべての選択肢に「自明:」を付けない。自明に近い選択肢だけラベル（例: `自明`）を付ける
3. 利用者が選ぶまで、仕様本文もCHANGEも書かない。ステータスも変えない
4. 利用者がA/B/C等で答えたら、そのSPECを`確認待ち`にし、備考へ **選択（例: A）と決めた結果の要約だけ** を書く。仕様本文は直さない。ToBeも直さない。CHANGEも切らない。`対応済.md`へも移さない。第3.5節で台帳だけローカル commit。push しない
5. 仕様本文への反映とCHANGE作成は、利用者が`!SPEC転記`したときだけ行う。第12.12節
6. 利用者が「これは特大」と言ったSPECだけ規模を特大にし、表の末尾へ移す。その場の検討は止める。特大は検討順の最後である。指定なしの`!SPEC検討`では取らない。利用者がIDを名指ししたとき以外、特大の検討を提案しない。AIは規模を特大に上げない

### 3.3 完了の定義

| 状態 | 意味 |
| --- | --- |
| 未着手 | まだ手を付けていない |
| 検討中 | SPECの選択肢を出している途中。まだ選ばれていない |
| 対応中 | CHANGE/BUG/TESTで一部入れた。備考に残がある |
| 確認待ち | **CHANGE/BUG:** チケット範囲がコードにあり、ToBe枠と`仕様:`が一致し、残作業が無い。利用者が組織を指定しているときは、その範囲のテストがデフォルト Org で成功している。利用者の確認を待つ。<br>**TEST:** 第3.1.1節の Goal を満たし、製品と仕様本文は触っていない。デフォルト Org で対象テストが成功し、対象Apexの行カバーが75%を超えている（Jestだけなら Jest 成功）。地図の該当行が最新。残作業が無い。利用者の確認を待つ。<br>**SPEC:** 利用者が選択済み。備考に決定がある。仕様本文への転記とCHANGE作成はまだ。`!SPEC転記`を待つ |
| 保留 | 仕様の判断または前提条件を待って止めている。待っているSPEC番号を備考に書く |
| 完了 | 利用者が確認した。`対応済.md`へ移す |

骨格だけ入れて本線が無いCHANGE/BUGは確認待ちにも完了にもしない。TESTでチケット範囲のテストが無いのも同じ。確認前の完了も置かない。CHANGE/BUG/TESTの完了へ上げるのは利用者、または第12.6節である。`!完了`で仕様とずれていれば、その場修正せず差分を新しいBUG／TEST／CHANGEに切り、元は対応済にする。SPECの完了は第12.12節の転記のあとである。完了したら`対応済.md`へ移す。削除しない。完了行は`要対応.md`へ戻さない。章立ての組み替え、テストカバーの更新、並替でも同じである。チケット表を会話の記憶や古い写しで作り直さない。`対応済.md`にあるIDを要対応へ再掲しない。語彙の一覧は`要対応.md`のステータス表を正とする。

完了したCHANGE / SPEC / BUGに追加の差分が出たら、完了行を再開しない。新しいCHANGE（仕様が未決なら先にSPEC）を切る。完了したTESTの続きは新しいTESTにする。新チケットの備考に元IDを書く。識別子名を変える必要がなければ「新設するコード」は既存手続きへの追加とする。

### 3.4 作業中に仕様の問題を見つけたとき

実装やSPEC検討の途中で次を見つけたら、超貴重な情報である。推測で埋めない。仕様本文も実装方針も勝手に決めない。

- 仕様が不明瞭（どちらにも読める、条件が抜けている）
- 仕様の誤り（本文の結果が成立しない、他の確定節と両立しない）
- 仕様の矛盾（同一書の節同士）
- 文書間の食い違い（CoreとAccountingと共通基盤が、それぞれ明瞭でも結果が違う）
- 削除してよい仕様記載（死んだ節、廃止済みの残文、重複）
- 備考またはToBeにしか無い業務結果

手順は次とする。

1. 既存SPECに同じ論点が無いかを`要対応.md`と`対応済.md`で確認する。無ければSPECを新設する。採番は`要対応.md`の記載ルール
2. SPECの内容に、どの文書のどの節か、何が不明／誤り／矛盾／削除候補か、実装を止めた理由を書く。規模（小／中／大／特大）は`要対応.md`の記載ルールで付ける。特大は利用者が「これは特大」と言ったときだけ。推奨のBefore / Afterは出してよい。採用はしない
3. 判断待ちのCHANGE / BUG / 元のSPECを`保留`にする。備考に待っているSPEC番号を1行書く。完了行は保留にしない
4. 仕様本文は直さない。実装は進めない。次のCHANGEにも入らない
5. 利用者がSPECを選ぶまで保留のままにする。選択だけならSPECは`確認待ち`であり、待っているチケットの保留は解かない。`!SPEC転記`で本文へ落ちたあと、待っていたチケットの保留を解く

明瞭な仕様に実装が追いついていないだけなら、これはBUGまたは進行中のCHANGEである。SPECにしない。

### 3.5 ローカル commit と push

開発ルール.md、要対応.md、対応済.md、`docs/機能仕様書/` を直したら、その場でローカル commit する。確認待ちや信号の終わりまで残さない。force-app は混ぜない（実装・転記が同じ作業で触ったときを除く）。`docs/Old` は入れない。

ローカル commit するのは次だけである。製品コードを混ぜてよいのは、確認待ちまで終わった実装と転記だけである。

- `!CHANGE実装` / `!BUG実装` / `!TEST実装`で、残が無く確認待ちにしたとき。そのチケットが触ったファイルと、`要対応.md`の「Push する内容」
- `!SPEC転記`で本文・ToBe・台帳を直したとき。その転記が触ったファイルと、`要対応.md`の「Push する内容」
- 利用者が組織を指定したあと、`ContractTestDataFactory`の導入先差し替えだけを直したとき。そのクラスと、`要対応.md`の「Push する内容」（第3.6節・第9節）
- 利用者が組織を指定し、ローカルテスト一式の結果で「テストカバー」の計測列だけを埋めたとき。`要対応.md`だけ（製品は触らない。第9節）
- 台帳だけの作業。`docs/開発用/要対応.md`と`docs/開発用/対応済.md`だけ。force-app・仕様本文は入れない。「Push する内容」へ判定`大丈夫`・ID・一言を載せる。対象は次
  - 発掘（`!SPEC発掘` `!CHANGE発掘` `!BUG発掘` `!TEST発掘`）
  - 並替（`!CHANGE並替` `!BUG並替` `!SPEC並替`）
  - `!完了`の台帳移動（切った新チケットを含む）
  - `!SPEC検討`で利用者が選んで`確認待ち`にしたとき
  - `!精査`で台帳を変えたとき
- 利用者が手順または台帳を直すよう書いたとき。触ってよいのは`開発ルール.md`、`要対応.md`、`対応済.md`、地図の計測列。force-app・仕様本文は入れない。判定`大丈夫`。一言は触った節
- 上記4種（開発ルール・要対応・対応済・機能仕様書）を直したとき。直したファイルだけ。すぐ commit する
- `!push`で「Push する内容」を空にしたとき。その節だけ（第12.13節）。他差分は混ぜない
- `!push`で `docs/機能仕様書/` に未 commit があるとき。このディレクトリだけ。表には載せない。他差分は混ぜない

ローカル commit する直前に、`要対応.md`の「Push する内容」へ1行足す。空の`（なし）`行があれば消してから足す。行は表（判定／ID／一言）。判定は顧客依存（パッケージ標準ではない変更）で`大丈夫`／`怪しい`／`絶対だめ`。DataFactory の導入先だけは判定`大丈夫`・ID`ContractTestDataFactory`・一言`導入先差し替え`。地図埋めは判定`大丈夫`・一言`テストカバー計測`。機能仕様書だけの commit は表に載せない（第12.13節）。同じ ID は二重に積まない。`× N`で複数IDを1 commitにまとめてよい。そのときは ID ごとに1行。`絶対だめ`の差分は commit しない（第3.6節）。`怪しい`は利用者に判定を返す。

しない。対応中のまま終わった実装。秘密、作業用 JSON、`docs/Old`、Org retrieve の未追跡、クライアント専用の設定・CMDT行（導入先差し替えの唯一の例外は第3.6節・第9節の`ContractTestDataFactory`。地図の計測列だけの埋めは`要対応.md`のみ）。メッセージはチケット ID と一行（CHANGE／BUGは仕様のなぜか。TESTは Goal。第3.1.1節。台帳・手順は作業範囲。地図埋めは`テストカバー`と一行）。git config は変えない。force と履歴改変はしない。`git add -A` はしない。

この作業環境では husky の pre-commit が `npm` 不在で落ちる。第3.5節のローカル commit は最初から `--no-verify` する。失敗を待たない。利用者に聞かない。返答に「飛ばしてよいか」を書かない。`--no-verify` は利用者が常時許可した。Cursor の承認カードを出して待たない。lint や中身の検査で落ちたときは `--no-verify` しない。`!push` の空にする commit も同じ。force はしない。

push は `!push` だけである。実装・転記・完了・発掘・並替・検討・比較の信号では送らない。送る前のゲートは第12.13節。送ったら「Push する内容」は空にする。

### 3.6 パッケージと Org 資材

Git に載せるのは、Org やクライアントに依らないパッケージ自体の修正である。Org 専用の設定・資材は載せない。

唯一の例外は`ContractTestDataFactory`である。導入先ごとに変えるテストデータの組み立て（`TENANT_*`、商談の RT／Stage 候補、必須項目の describe 埋め、権限セット名、組織に存在する選択リスト値）はここに集約し、Git に載せてよい。他のクラス・LWC・メタ・retrieve へ顧客依存を置かない。詳細は第9節。

- パッケージの修正はローカルの `force-app` で行う。Org へは利用者が組織を指定したときの deploy だけである
- Org からの retrieve は `force-app` に直接入れない。`.gitignore` にある箱（`org-retrieve-`、`retrieved-` など）へ取る
- 箱から `force-app` へ移してよいのは、仕様または CHANGE がパッケージ同梱と書いた識別子だけである。retrieve 結果を `git add -A` しない
- CMDT は型（定義）と行を分ける。Git に置くのはパッケージが同梱する行（帳票キー、標準メール、仕様の見本ウィザード項目など）。その Org の追加項目行、科目割当、タグルール、コピー定義の顧客行、組織設定の値は Org に残す
- プロファイル、共有、他社 Apex、顧客の FlexiPage は Git に載せない。権限の正は `Loop_*`。Admin プロファイルは `.forceignore` のままである
- retrieve を指令にしない。比較は `!ORG比較` だけが箱へ取ってよい。箱の中身は `force-app` に移さない。`git add` しない。比較のあと箱を残してよい（載せない）

紐づけるのは次の2つだけである。

| 側 | 正本 | 辿る単位 |
| --- | --- | --- |

- コードコメントにCHANGE番号を書かない
- 削除だけで残る識別子が無い作業は、仕様枠にもコード注記にも載せない

## 8. 日付算法

日付に触れる変更の前に`共通基盤.md`の日付部を読む。コードと他文書の「日付仕様 第X節」は同義である。

1. 月は暦ではなくサイクルで数える。「1ヶ月」は開始日から1ヶ月後の前日まで。`addMonths(N).addDays(-1)`の一発計算は使わない。1/31開始の12サイクル終了は翌年1/27
2. 刻む算法は組織にひとつ。`MonthlyBillingPeriodUtil.cls`と`estimateLineItemUtils.js`の両方を同じ内容にする。どちらかを変えたら必ず両方変える。片方だけ直したら確認待ちにしない。残がある
3. sticky（月末を月末に貼りつける）は見積ウィザードの開始日±ボタンだけ。期間の刻みに持ち込まない
4. 日割りはしない。設定項目も作らない
5. 支払条件の入金予定日だけは暦月で計算する。商習慣であり例外ではない

## 9. テスト

テストの正は仕様の一文である。テストで仕様を発明しない。

CHANGE / BUGでは、直した手続きが仕様に反したら落ちるテストをその範囲で足すか直す。ASSERTメッセージまたはテスト名に、どの節の何が破れるかを書く。

専用`*Test.cls`が無い新設クラスでも、既存の呼出元テストか、最小の専用テストのどちらかでその一文を押さえる。製品横断のシナリオ追加は`SPEC-049`を待つ。

CHANGE / BUGの実装では、既存テストは本番変更で壊れるものだけ追随する。関係ない整理やカバレッジ目的の追記はTESTへ切る。TESTを切るのは`!TEST発掘`。TESTをさばくのは`!TEST実装`。地図から自動で切ることはしない。

導入先（テナント）に依存するテスト準備は`ContractTestDataFactory`に集める。`TENANT_*`、`applyTenantExtraOpportunityFields`、商談の RT／Stage 候補、必須項目の describe 埋め、権限セット名、組織に存在する選択リスト値だけを差し替える。他の`*Test.cls`に顧客のステージ名・RT・必須項目を直書きしない。製品コードに導入先の値を置かない。

Git に載せてよい顧客依存は、このクラスだけである。retrieve や他資材の Org 差分は載せない（第3.6節）。業務結果（拒否、代替、日付算法、状態遷移）はここで変えない。

初回のローカルテスト一式は地図の計測列を埋める作業である。`!TEST実装`と混ぜない。失敗の行き先は要対応の表（製品が本文どおりでテストだけ違う／余剰なら TEST。製品が本文に反するなら BUG。明瞭な仕様の未追随なら CHANGE。導入先の値なら Factory だけ）。一式の結果で計測列だけを埋めたときは第3.5節で`要対応.md`だけ commit してよい。製品は触らない。判定は`大丈夫`。一言は`テストカバー計測`。

`要対応.md`の「テストカバー」は地図である。成功可否とカバー率は別である。よしあしの点数は高いほどよい。総合点だけ1だめ〜5申し分なし。本線の多さ・Assertion・汎用度・安心度・MECE度は1〜3（3がよい）。失敗している行を先に並べ、成功している行を総合点の低い順に並べてよい。これは地図の見やすさであり、切る順ではない。切る順は第12.15節。チケット化の種類は要対応の行き先表。行から自動で CHANGE も TEST も切らない。`!TEST実装`は対象Apexの行カバー75%超を Goal にする。カバー率の数字だけを内容にした発掘はしない。クラス単位の充実とシナリオ拡充の方針は`SPEC-105`／`SPEC-049`が決まるまで始めない。`!TEST実装`が終わったら、対象Apexの行の数値と評価を今回の Org 実行で最新化する。他行は触らない。

## 10. 禁止

- 仕様の細目を読まずに解釈する。チケット要約・備考・現行コード・「普通こうする」で本文を補う
- 引用できないままコードを触る
- 仕様の不明瞭・誤り・矛盾・文書間食い違い・削除候補を見つけてもSPECに残さず、本文や実装を勝手に直す
- 明瞭な文書が食い違っているとき、近い方の文書に合わせる
- 仕様に無い業務結果を足す。空をマスタや既定値で埋めて処理を続ける（代替禁止）
- UPDATEの実装。SPECの実装先行
- 範囲外のリファクタ、改名、フォーマットだけ、取得ゴミの取り込み（`zqu__*`、tmp、関係ない retrieve）。Org retrieve を `force-app` へ直接入れること。クライアント専用の設定・CMDT行・プロファイルを Git に載せること（第3.6節）。顧客依存のテスト値を`ContractTestDataFactory`以外へ置くこと（第9節）
- 旧Accountingメタデータを現行仕様として読む。削除した空見出しを根拠にする
- `docs/Old/`と凍結アーカイブの編集・回収
- 残作業があるCHANGEを確認待ちまたは完了にする
- 確認前のチケットを`対応済.md`へ移す
- 完了したチケットを`要対応.md`へ戻して再開する。章立ての組み替えや地図の更新で、対応済のIDを確認待ちとして再掲することも同じ。差分は新しいCHANGE（テスト担保だけなら新しいTEST）にする
- 信号に無いコミット（第3.5節に書いたもの以外）。信号に無い push。`!push` 以外からの送信。force push。`git add -A`。`--no-verify` は第3.5節の npm 無し以外では使わない

## 11. 仕様本文との境界

業務ルールを変えるなら、利用者が選んだあと`!SPEC転記`で仕様本文を先に直す。作業中に見つけた不明瞭・誤り・矛盾・文書間食い違い・削除候補は第3.4節でSPECにし、転記まで本文を触らない。ToBe枠と`仕様:`コメントは地図である。地図を足しても本文の結果は変えない。

## 12. 信号の手順

信号の一覧と正規名は第0節。`× N`は第0節。どの信号でも第1.1節どおり本文を読む。解釈で埋めない。第3.4節に当たる発見はSPECにして保留し、勝手に決めない。完了チケットは復活させない。確認前に`対応済.md`へ移さない。各節の「1件」「次に入らない」は`× N`が無いときの既定である。`× N`があれば最大N件まで同手順を繰り返し、候補が無ければそこで終える（SKIP）。

### 12.1 `!CHANGE実装`

未完了のCHANGEを1件（`× N`なら最大N件）、仕様どおり実装する。旧`!実装`は同じ。

1. `要対応.md`のCHANGE表を上から見る。`保留`と`確認待ち`は飛ばす。最初の`未着手`または`対応中`を1件取る
2. 返答の先頭に、実装する結果を仕様本文の引用で1〜3行書く。書けないならまだ読めていない。コードに入らない。そのあと第3.1節どおり進める
3. 第3.4節に当たる発見はそのCHANGEを保留し、実装を止める
4. 終わったらチケットを更新する。残が無ければ確認待ち。`対応済.md`へは移さない。残があれば対応中のまま備考へ1行
5. 確認待ちにしたら第3.5節どおりローカル commit。push しない
6. `× N`が無ければ次のCHANGEには入らない。あれば候補がある限り最大N件まで繰り返す。候補が足りなければSKIP。結果（引用した本文、何をしたか、残、切ったSPEC、commit の有無）だけ返す

指定IDがあるときはその1件だけ。指定がBUGならそのBUGを第3.1節で直す。指定なしでBUG表を辿るのは`!BUG実装`である。TESTは`!TEST実装`である。UPDATEとSPECは実装しない。

### 12.2 `!SPEC発掘`

仕様の不明瞭・誤り・矛盾・文書間食い違い・削除してよい記載を探し、SPECにする。実装しない。本文を直さない。推奨は書いてよい。採用しない。`× N`なら切るSPECを最大N件。見つからなければSKIP。

1. 範囲指定がなければ、`要対応.md`の未完了CHANGE / BUGが指す節と、その本文が明示参照する節を読む。文書または章の指定があればそこを読む。指定なしの全書通読はしない
2. 既存SPECに同じ論点が無いかを`要対応.md`と`対応済.md`で確認する
3. 新規だけSPECを切る。どの文書のどの節か、何が不明／誤り／矛盾／削除候補かを本文に即して書く。規模（小／中／大）は`要対応.md`の記載ルールで付ける。特大は利用者が「これは特大」と言ったときだけ。AIは特大に上げない
4. その論点で止まっているCHANGE / BUGがあれば第3.4節どおり保留する
5. 明瞭な仕様に実装が追いついていないだけのものはSPECにしない。CHANGE化は`!CHANGE発掘`。ここでは候補として報告する。チケットは切らない
6. 実装しない。切ったら第3.5節で台帳だけローカル commit。push しない。結果は切ったSPEC、保留したチケット、切らなかった候補の一覧、commit の有無だけ返す

### 12.3 `!精査`

`対応済.md`の完了行を、仕様本文と実装と突き合わせる。完了行は戻さない。実装しない。`× N`なら最大N件。

1. 指定IDがなければ、対応済CHANGEを更新日の古いものから1件取る。SPEC完了やBUG完了の指定があればそれ
2. 第1.1節どおり本文を読む。ToBe識別子と`force-app`の現行を照合する
3. 判定は次のいずれか。完了行の本文は書き換えない。備考へ新IDを足してよい
   - **充足** … チケット範囲は仕様どおりコードにある
   - **差分** … 決まった仕様に未追随がある。新しいCHANGEを切る。備考に元ID
   - **仕様問題** … 不明瞭・誤り・矛盾・文書間食い違い・削除候補。第3.4節でSPECを切る。完了行は保留にしない
   - **誤完了** … チケット範囲の本線が無い。新しいCHANGEを切る。完了行は戻さない
4. `× N`が無ければ次の完了行には入らない。あれば最大N件まで繰り返す。候補が足りなければSKIP。判定と切ったチケットだけ返す。台帳を変えたら第3.5節で台帳だけローカル commit。push しない

### 12.4 `!BUG発掘`

明瞭な仕様に反する実装を探す。直さない。仕様を発明しない。`× N`なら切るBUGを最大N件。見つからなければSKIP。旧`!BUG`は同じ。新信号は作らない。

1. 利用者が実機の結果（画面・権限・保存後の値）を書いたら、それを範囲指定とする。AIは画面を操作したことにしない。「落ちそう」の推測は切らない
2. 範囲指定がなければ、パッケージ標準画面から行う操作に限る。見積保存、受注、差し戻し、請求確定、請求取消、入出金登録・取消、検収日変更、契約サービス編集。コードと本文の突き合わせはしてよい。Data Loader、API直打ち、画面外DMLは利用者が指定したときだけ
3. 対象操作が属する節を第1.1節どおり読む
4. 仕様の一文と、実際の手続き（AuraEnabled、Service、Trigger）を突き合わせる。実機結果があるときは、その値も突き合わせる
5. 仕様が明瞭で実装が反していればBUGを切る。どの節の何が、どの手続きで破れるかを書く
6. 仕様が不明瞭・誤り・矛盾・文書間食い違いならBUGにしない。第3.4節でSPECにする
7. 実装しない。切ったら第3.5節で台帳だけローカル commit。push しない。結果は切ったBUG / SPEC、commit の有無だけ返す

### 12.5 `!CHANGE並替`

`要対応.md`のCHANGE表を、着手順として正しい並びに直す。実装しない。仕様本文を直さない。チケットの内容・ステータスは変えない。表全体が単位のため`× N`があっても1回だけ行い、残りはSKIPする。

1. 未完了CHANGEの本文・備考と、「新設するコード」に書いてある先行だけを読む。書いていない依存は作らない。ROIや「画面が先」などの優先は、利用者が書いたときだけ使う
2. 上から先に着手する。同順位は元の相対順を保つ
   1. `対応中`（残がある続き）
   2. `未着手`のうち、依存するCHANGEが対応済または無いもの
   3. `未着手`のうち、未完了の先行CHANGEに依存するもの（先行の直後）
   4. `確認待ち`
   5. `保留`（SPEC待ち）
3. 「新設するコード」表（`対応済.md`）は並び替えない。完了チケット行は触らない
4. 結果は、動かしたIDと動かした理由（先行IDまたは保留）だけ返す。動かしたら第3.5節で台帳だけローカル commit。push しない

### 12.6 `!完了`

CHANGE、BUG、またはTESTの確認待ちを、利用者が認めたものとして完了にする。実装しない。SPECの確認待ちは対象外である（第12.12節）。`× N`なら最大N件。

指定は次とする。例: `!完了`、`!完了 CHANGE`、`!完了 BUG`、`!完了 TEST`、`!完了 CHANGE-160`、`!完了 CHANGE × 5`。

1. 取る行を決める
   1. 指定IDがあればその1件。`確認待ち`でなければ拒否する
   2. 指定が`CHANGE`だけなら、CHANGE表の最初の`確認待ち`を1件取る。他表は見ない
   3. 指定が`BUG`だけなら、BUG表の最初の`確認待ち`を1件取る。他表は見ない
   4. 指定が`TEST`だけなら、TEST表の最初の`確認待ち`を1件取る。他表は見ない
   5. 種類もIDも無ければ、CHANGE表・BUG表・TEST表を上から見て最初の`確認待ち`を1件取る。SPEC表の`確認待ち`は飛ばす
2. 指定がSPECなら拒否し、`!SPEC転記`を使うよう返す
3. 対応済へ移す前に確認する。第3.1節・第3.1.1節の実装はしない
   1. CHANGE / BUG: チケット範囲の実装が仕様本文どおりか。第1.1節の範囲で本文を読み、`force-app`の現行と突き合わせる
   2. TEST: 製品コードと仕様本文がこのチケットで変わっていないか。チケット範囲のテストがあるか。地図の該当行が埋まっているか。Apexならカバー率が75%を超えているか（再実行はしない）
4. ずれがあるとき。その場修正はしない。差分を新しいチケットに切ったうえで、元は対応済にする
   1. 仕様が明瞭で実装が追いついていない → 新しいCHANGEを切る
   2. 仕様が明瞭で実装が反している → 新しいBUGを切る
   3. 製品と本文はそのままで、テストだけ過不足・余剰 → 新しいTESTを切る
   4. 仕様がおかしい・不明瞭・矛盾・文書間食い違い、または本文を変えた方がよい → 新しいSPECを切る。第3.4節。本文は直さない
   5. 切ったIDを元の備考へ書く。残作業が無ければ元の確認待ち行を`対応済.md`へ移す。ステータスは完了
5. 残作業がある行は完了にしない。確認待ちのまま返す
6. 残が無く、ずれが無ければ元を`対応済.md`へ移す。ステータスは完了
7. コードは確認待ち時点の commit に載っている。製品は触らない。台帳（切った新チケットを含む）は第3.5節でローカル commit する。push しない
8. `× N`が無ければ次のチケットには入らない。あれば候補がある限り最大N件まで繰り返す。候補が足りなければSKIP。移したIDと、切ったBUG／TEST／CHANGE／SPECがあればそれだけ返す

### 12.7 `!SPEC検討`

未決SPECを1件（`× N`なら最大N件）、本文まで読んで **選択肢と推奨だけ** 出す。実装しない。仕様本文もCHANGEも書かない。ステータスも変えない。旧`!SPEC`・`!検討`も同じ手順である。

1. 指定IDがなければ、`要対応.md`のSPEC表を上から見て、次を飛ばして最初の1件を取る。飛ばすもの: `保留`、`確認待ち`、特大。特大は利用者がそのIDを名指ししたときだけ取る。次の検討として特大を提案しない
2. 第1.1節の範囲だけ読む。チケットが書いた節と、その本文が明示参照する節。見出しや隣の節へ広げない
3. 現行コードは突き合わせ用に見る。コードから仕様を発明しない
4. 返答の型は次に固定する。長い再説はしない
   1. 1行で論点（どの節が食い違う／何が未決か）
   2. **推奨**を先に出し、理由を短く
   3. 選択肢A/B（必要ならC）。各選択肢に選ぶと何が起きる／起きないを短く書く。処理結果が変わるものと注意書きを分ける。**すべての選択肢の先頭に「自明:」を付けない。** 自明に近い選択肢だけ、選択肢見出しにラベル（例: `A（自明）`）を付ける
   4. 「A / B で決まるまで本文もCHANGEも書かない」で閉じる
5. 利用者がこの返答のあとにA/B/C等で答えたら、第3.2節4どおり当該SPECを`確認待ち`にし、備考へ選択と結果の要約だけ書く。仕様本文・ToBe・CHANGE・対応済は触らない。第3.5節で台帳だけローカル commit。push しない。次のSPECには入らない
6. 第3.4節に当たる別論点は`!SPEC発掘`と同じくSPECを切ってよい。今回の推奨は採用しない
7. `× N`が無ければ`!SPEC検討`の1回で次のSPECには入らない。あれば最大N件まで選択肢を出す（各件の選択採用は利用者が答えたあと）。候補が足りなければSKIP。文中の「つぎ」「次」では起動しない

### 12.8 `!CHANGE発掘`

決まった仕様に実装が追いついていない箇所を探し、CHANGEにする。実装しない。本文を直さない。仕様を発明しない。`× N`なら切るCHANGEを最大N件。見つからなければSKIP。

1. 範囲指定がなければ、`要対応.md`の未完了CHANGE / BUGが指す節と、その本文が明示参照する節を読む。文書または章の指定があればそこを読む。指定なしの全書通読はしない
2. 既存CHANGE / BUGに同じ範囲が無いかを`要対応.md`と`対応済.md`で確認する
3. 仕様が明瞭で、実装が追いついていないものだけCHANGEを切る。どの文書のどの節か、何が未追随かを本文に即して書く。完了行の差分なら備考に元ID。新設識別子の名前はToBeにあるものだけ「新設するコード」へ書く。無い名前は作らない
4. 仕様が不明瞭・誤り・矛盾・文書間食い違い・削除候補ならCHANGEにしない。第3.4節でSPECにする
5. 明瞭な仕様に実装が反しているだけのものはCHANGEにしない。BUG化は`!BUG発掘`。ここでは候補として報告する。チケットは切らない
6. 実装しない。切ったら第3.5節で台帳だけローカル commit。push しない。結果は切ったCHANGE、切ったSPEC、切らなかった候補の一覧、commit の有無だけ返す

### 12.9 `!SPEC並替`

`要対応.md`のSPEC表を、検討順として正しい並びに直す。実装しない。仕様本文を直さない。チケットの内容・ステータスは変えない。仕様本文は並びのために通読しない。内容と備考だけを読む。表全体が単位のため`× N`があっても1回だけ行い、残りはSKIPする。

1. 特大は種別・後続の大きさに関係なく表の末尾。特大同士は元の相対順を保つ
2. 特大以外は第1段で種別。標準仕様を先、異常系に近いものを後にする。主たる対象で決める。書いていない種別は作らない
   1. 標準仕様 … 通常操作の本線、マスタ、設定、権限、保持体、項目、画面本線
   2. 異常系 … 競合、失敗、取消、Lock、再実行、拒否、移行、例外操作、テスト拡充
3. 同じ種別の中では、後続の仕様変更が大きいものを先にする。根拠は`要対応.md`と`対応済.md`に書いてある待ち・先行・「先に決める」だけ。書いていない影響は作らない。待ち件数が多い、決めると識別子・保持体・権限・共通方式が固定される、複数文書に効く、の順で大きいと見る
4. 同順位は元の相対順を保つ。対応済は触らない
5. 結果は、動かしたIDと動かした理由（特大、種別、または後続の大きさ）だけ返す。動かしたら第3.5節で台帳だけローカル commit。push しない

### 12.10 `!BUG実装`

未完了のBUGを1件（`× N`なら最大N件）、仕様どおり直す。

1. `要対応.md`のBUG表を上から見る。`保留`と`確認待ち`は飛ばす。最初の`未着手`または`対応中`を1件取る
2. 返答の先頭に、直す結果を仕様本文の引用で1〜3行書く。書けないならまだ読めていない。コードに入らない。そのあと第3.1節どおり進める
3. 第3.4節に当たる発見はそのBUGを保留し、実装を止める
4. 終わったらチケットを更新する。残が無ければ確認待ち。`対応済.md`へは移さない。残があれば対応中のまま備考へ1行
5. 確認待ちにしたら第3.5節どおりローカル commit。push しない
6. `× N`が無ければ次のBUGには入らない。あれば候補がある限り最大N件まで繰り返す。候補が足りなければSKIP。結果（引用した本文、何をしたか、残、切ったSPEC、commit の有無）だけ返す

指定IDがあるときはその1件だけ。CHANGEは`!CHANGE実装`である。TESTは`!TEST実装`である。UPDATEとSPECは実装しない。

### 12.11 `!BUG並替`

`要対応.md`のBUG表を、着手順として正しい並びに直す。実装しない。仕様本文を直さない。チケットの内容・ステータスは変えない。表全体が単位のため`× N`があっても1回だけ行い、残りはSKIPする。旧`!BUG並び替え`は同じ。

1. 未完了BUGの本文・備考と、備考に書いてある先行だけを読む。書いていない依存は作らない。ROIや「画面が先」などの優先は、利用者が書いたときだけ使う
2. 上から先に着手する。同順位は元の相対順を保つ
   1. `対応中`（残がある続き）
   2. `未着手`のうち、依存するCHANGE / BUGが対応済または無いもの
   3. `未着手`のうち、未完了の先行CHANGE / BUGに依存するもの（先行の直後）
   4. `確認待ち`
   5. `保留`（SPEC待ち）
3. 対応済は触らない。CHANGE表は並び替えない
4. 結果は、動かしたIDと動かした理由（先行IDまたは保留）だけ返す。動かしたら第3.5節で台帳だけローカル commit。push しない

### 12.12 `!SPEC転記`

SPECの`確認待ち`を1件（`× N`なら最大N件）、備考の決定どおり仕様本文へ落とし、CHANGEを切り、SPECを対応済へ移す。実装しない。決定の中身をやり直さない。

1. 指定IDがなければ、`要対応.md`のSPEC表を上から見て最初の`確認待ち`を1件取る。備考に選択結果が無い行は転記しない
2. 備考の決定だけを正とする。第1.1節の範囲で本文を直し、ToBe枠を同じ名前で置く。備考に無い結果は足さない
3. 実装追随が要るならCHANGEを切る。採番は`要対応.md`の記載ルール。不要ならCHANGEは切らない
4. このSPECを`対応済.md`へ移す。ステータスは完了。備考に転記した節とCHANGE ID（切った場合）を残す
5. このSPEC待ちで`保留`していたCHANGE / BUGがあれば保留を解く
6. 転記が触ったファイルを第3.5節どおりローカル commit。push しない
7. `× N`が無ければ次のSPEC転記・検討・実装には入らない。あれば最大N件まで繰り返す。候補が足りなければSKIP。結果（移したSPEC、直した節、切ったCHANGE、commit の有無）だけ返す

### 12.13 `!push`

たまった未 push のローカル commit を、現在ブランチの追跡リモートへ送る。仕様とコードの突き合わせはしない。実装しない。旧`!Push`は同じ。新信号は不要。信号に書き足す必要は無い。

`docs/機能仕様書/`（`仕様書_Core.md`、`仕様書_Accounting.md`、`共通基盤.md`、`ユーザ設定.md`）は「Push する内容」に載せない。送りのたびにワークツリーの最新を含める。本文はここで直さない。ある差分を載せるだけである。`docs/Old` は入れない。

送る前にゲートを見る。どれか欠けたら送らない（エラー）。作業の新規 commit は、空にする差分と、仕様書ディレクトリだけの commit 以外は作らない。

1. 「Push する内容」と未 push の commit が ID で対応する。表の各 ID は未 push のどれかの commit メッセージに含まれる。どの行にも載らない commit、どの commit にも載らない行はエラー。`× N`で1 commit に複数 ID があるときは、ID ごとに1行。例外: メッセージが `仕様書` で始まる commit は表に無くてよい
2. 作業ツリーに、第3.5節で載せてよい未 commit がある（実装・台帳・手順・地図の出し忘れ）はエラー。例外: `docs/機能仕様書/` の未 commit はエラーにしない（手順7で載せる）。明瞭に載せないものだけ残っていてよい。明瞭に載せないのは秘密、retrieve、顧客CMDT、プロファイル、`docs/Old`、`絶対だめ`、Goal 未満の製品差分である
3. 「Push する内容」に`絶対だめ`が1行でもあれば送らない。差分を外すよう返す
4. `怪しい`があり、利用者が了解していないなら送らない。判定を返す
5. 未 push が無く、節もすでに空で、`docs/機能仕様書/` にも載せる差が無ければ SKIP。送らない。仕様書だけ差があるときは送る（節は空のまま）
6. 行があれば空にする（判定`（なし）`の1行だけ残す）。空にして差分があれば、**その節だけの** commit を1つ作る。同じファイルの発掘・完了・地図・他節・仕様書は混ぜない。混ざるならエラー
7. `docs/機能仕様書/` に HEAD との差があれば、このディレクトリだけの commit を1つ作る。メッセージは `仕様書` と `最新を送る`。表には載せない。他ファイルは混ぜない。差が無ければ作らない
8. 追跡リモートが無ければ送らない。先を聞いて終わる。`origin` の URL は書き換えない
9. 通常の `git push` だけ。force はしない。`git add -A` はしない。空にした commit と仕様書 commit も含めて送る
10. `× N` があっても送る操作は1回。余りは SKIP
11. 結果は、送った先と commit の範囲、仕様書を含めたか、節を空にしたか、止めれば判定（無ければ SKIP）だけ返す。止めたときの文章は次に従う

止めたときは送っていない、と先に書く。SKIP はエラーではない（未 push も仕様書の差も無い）。Git の専門語だけ並べない。次の4段にする。

1. 結論。送っていない
2. 原因の種別。次のどちらか一方
   - **開発ルール**。第12.13節のゲート（手順1〜8、混在の禁止）に当たった。本書が送るなと言っている
   - **それ以外**。GitHub・認証・ネットワーク・フック（husky / npm）・権限など、手順の外で止まった
3. 開発ルールのとき。当たった手順の番号。足りないもの／余っているものを具体の ID とファイル名で書く。次に足す・消す・commit するもの。利用者が Git を自分で打たなくてよいこと。次の信号があればそれ（例: 表の行を直したあと再び `!push`。了解が要るならその判定を返すだけ）
4. それ以外のとき。何が起きたか（ログの要点1行）。推奨（例: 認証が切れている。ログインしてから再び `!push`）。npm が無くフックが落ちただけなら第3.5節（`--no-verify`。聞かない）。force はしない。`origin` の URL は変えない。聞かないと進めないことはここで聞く

ゲートごとの「次」の例は次である。ここに無い止め方でも、同じ4段にする。

- 手順1。表の余り → その ID を表から消すか、対応する commit があるか確認する。commit の余り → 「Push する内容」へ判定と ID と一言を足す。足したら第3.5節で台帳をすぐ commit し、再び `!push`
- 手順2。載せてよい未 commit → 第3.5節どおりそのファイルだけ commit して表へ載せる（仕様書は表に載せない）。出し忘れでなければ Goal 未満として残すか利用者が決める。再び `!push`
- 手順3。`絶対だめ` → その差分を commit から外す。外せるまで送らない
- 手順4。`怪しい` → 利用者が `大丈夫` か `絶対だめ` かを返すまで送らない
- 手順6。空にする commit に他節が混ざる → 混ぜずに節だけにする。混ざるなら送らない
- 手順8。追跡リモートが無い → 送り先を利用者が決めるまで送らない。推測しない

### 12.14 `!TEST実装`

未完了のTESTを1件（`× N`なら最大N件）さばく。機能と仕様は変えない。目的はチケット範囲のテストを直し、デフォルト Org で成功と対象Apexカバー75%超を確認し、地図の該当行を最新化して確認待ちにし、ローカル commit することである。

1. `要対応.md`のTEST表を上から見る。`保留`と`確認待ち`は飛ばす。最初の`未着手`または`対応中`を1件取る
2. 返答の先頭に、チケット内容を作業範囲として1行書く。書けないならまだ読めていない。コードに入らない
3. 第3.1.1節どおり進める。Goal を満たすまで確認待ちにしない
4. 第3.4節に当たる発見はそのTESTを保留し、作業を止める。製品コードは直さない
5. 終わったらチケットを更新する。Goal を満たせば確認待ち。`対応済.md`へは移さない。残があれば対応中のまま備考へ1行
6. 確認待ちにしたら第3.5節どおりローカル commit。メッセージは `TEST-番号` とチケット内容の一行。「Push する内容」の一言も同じ。地図の更新を含める。push しない
7. `× N`が無ければ次のTESTには入らない。あれば候補がある限り最大N件まで繰り返す。候補が足りなければSKIP。結果（作業範囲、Orgの成功、対象Apexのカバー率、地図を更新した行、残、切ったSPEC／BUG／CHANGE、commit の有無）だけ返す

指定IDがあるときはその1件だけ。CHANGEは`!CHANGE実装`、BUGは`!BUG実装`である。UPDATEとSPECは実装しない。製品コードを直す必要が出たらTESTを保留し、CHANGEまたはBUGを切る。Goal 未満では commit しない。retrieve しない。カバーを製品改変で稼がない。

### 12.15 `!TEST発掘`

テストの漏れとダブりを、`要対応.md`の地図から取り、TESTにする。実装しない。製品も仕様本文も直さない。仕様を発明しない。`× N`なら切るTESTを最大N件。見つからなければSKIP。

チケットの取り元は TEST表ではない。取り元は「テストカバー」である。切った先が TEST表である。コードを歩きまわって行を作らない。地図に無い対象Apexは切らない。

見るものは次に限る。指定なしの仕様全書通読はしない。

1. `要対応.md`の「テストカバー」（コード量の構成、クラス表、切ったチケット列、専用Apex行が無いテストクラス）
2. 行き先表（失敗が製品なら BUG／CHANGE／SPEC。テストだけなら TEST）
3. 候補行が指す `*Test.cls`（重複、呼べただけの通過、断言の有無）。Jest は後回し
4. 「テストだけが本文と違う」判定のときだけ、第1.1節でその節の本文

**持ってくる順**（上が残っているうちは下を取らない。`× N`は切る件数であり、下位へ進む許可ではない）

表の出現順・アルファベット順・対象Apex名の順は候補順ではない。同じ帯の中では優先が高い（点数の悪い、本線の多い）ものから取る。機械的に上からN件取らない。

クラス表の並べる順（失敗を先、成功は総合点が低い順）は地図の見やすさである。切る順は次の1〜4である。計測列が空の行は、優先1と4の候補にしない（まだ測っていない）。

1. 地図が失敗で、行き先が TEST（製品は本文どおり、テストだけ違う／余剰）。切ったチケットが空。同帯なら本線の多さが高い行を先
2. 対象テストが `※ 要追加`で、切ったチケットが空。同帯ならコード量の層が見積 Apex、次に請求 Apex、その中で本線の多さが高い行を先
3. コード量の構成で MECE度が低い層。先は見積 Apex、次は請求 Apex。その層のクラス表の行で、対象テストがあり、漏れまたはダブりなら整理・補充の TEST。同帯なら MECE度が低い、次に Assertion が低い、次に汎用度が低い行を先。横断シナリオと Jest の画面ゲートは後回し
4. 成功している行のうち総合点が低い（だめ）もの。切ったチケットが空。1件は対象Apex 1行。同帯なら総合点が低い順、同点なら Assertion・MECE度・汎用度の低い順

取らない。

- `※ 明確に不要`
- 切ったチケットがすでに埋まっている行（同じ範囲）
- 行き先が BUG／CHANGE／SPEC の行（報告だけ。ここでは切らない）
- 専用Apex行が無い表のシナリオ拡充（`SPEC-049`）。クラス単位の充実方針（`SPEC-105`）
- カバー率の数字だけを内容にした行
- 計測が空なのに優先1・4として切ること
- 表の出現順・アルファベット順だけで切ること

チケット化は次とする。

1. 1件は地図の対象Apex 1行に閉じる。専用Apex行が無い表から切るときは、明示したテストクラス1つ（寄せが要るときだけ。シナリオ拡充は切らない）
2. TEST表の**末尾**へ足す。着手順の後ろである。途中に挿さない
3. **内容は Goal の一文**である。誰の何を足す／削る／直すか。機能と仕様は変えない、と読めること。方法名は内容に書かない
4. 備考へ対象テスト、地図の列（成功可否・MECE度・Assertion・汎用度・総合点）。地図の「切ったチケット」へ ID
5. ステータスは未着手。規模は付けない
6. 実装しない。切ったら第3.5節で台帳だけローカル commit。push しない。結果は切った TEST（IDとGoal）、取らなかった行の理由、SKIP ならその旨、commit の有無だけ返す

### 12.16 `!ORG比較`

デフォルト接続の Sandbox と、ワークツリーの `force-app` を比べ、資材別の表だけ返す。実装しない。commit しない。push しない。チケットを切らない。デプロイしない。接続先を変えない。`× N` があっても操作は1回。余りは SKIP。仕様本文は読まない。

5. 更新日時・作成者だけの差は行にしない

### 12.17 `!GITHUB比較`

対象は次である。

- `docs/機能仕様書/`（`仕様書_Core.md`、`仕様書_Accounting.md`、`共通基盤.md`、`ユーザ設定.md`）

1. 追跡リモートが無ければ止めて返す。URL は変えない
2. 1行は資材パス（`force-app` なら種類＋API名にまとめてよい）
3. 本表の列は、資材、状態（`ワークツリーのみ` / `GitHubのみ` / `両方ずれ`）、層（`未 commit` / `commit済み未 push` / `両方`）、一言。差が無ければその資材は行にしない。全部差が無ければ表は空であることだけ返す
4. 照合は資材パスではやらない。返すのは次の2つである
   - 本表
   - 一行：`要対応.md`の「Push する内容」の ID 集合と、未 push の commit メッセージの ID が対応するか。第3.5節で載せてよい未 commit が無いか。一致なら`一致`、欠けまたは余りなら`不一致`と欠け／余り
5. 直し方、push、チケット案は書かない
