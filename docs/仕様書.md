## 設計の大前提

Salesforce 上では、**標準 UI・API・Data Loader・システム管理者権限による項目の直接編集を、すべて防ぐことはできない**（管理者／Modify All／整合バイパス等は抜ける）。これを前提に設計する。

本パッケージが守るのは次の2層である。

1. **正規ユーザーの導線を閉じる**  
   Dynamic Actions・ページレイアウト／読取専用・カスタム権限で、見積ウィザード／受注・差し戻しウィザード以外から「触ってほしくない項目・操作」を通常は出さない・させない。
2. **触られても請求事故にならないガードをサーバに置く**  
   権限・ステータス遷移・差し戻し順序・Change 打消し Fail closed・ロック・Archive 不可逆など、**壊れたまま Ordered／請求が通る**経路を Apex（主にトリガ）で止める。経路を問わず効かせる。

対象外の割り切り:

- システム管理者や意図的なデータ改変までを「絶対に触れない」ことは目標にしない
- 見積商品・契約履歴の期間／金額などをウィザード外でいじった結果の局所不整合を、項目ごとに全部検知して禁止することも目標にしない（入口が無数で、管理者には抜けられる）
- 管理者メンテが必要な場合の手順・監査は運用側の責任とする

個別仕様（§5・§6 等）の「経路不問で強制」「ウィザード限定でよい」「許容する」は、この大前提の下で書いている。

## 想定顧客とコア完了の定義

### 想定顧客

- 国内向け、**JPY（円建て）** が本流
- 年契または月次など、**継続課金＋一回課金**が中心の B2B
- すでに Salesforce を使う（または載せる）前提
- 会計・請求書の発行／送付／入金消込は **別システムまたは手運用**（本パッケージは契約〜請求の元データまで）

### 想定しない（非対象の目安）

- 日割りが商売の前提
- 従量課金・数量ティア／価格表エンジンが必須
- 外貨建て請求が本流
- 請求書発行から入金消込までを同一プロダクトで完結させたい

詳細な「できる／できない」の言い回しは [第9章](#9-bypass通貨パッケージ外) および [第11章](#11-導入時よくあるニーズへの答え) を参照。

### コア完了の定義

次を満たせば、本パッケージのコア導入は完了とする。

1. **新規**見積を作成し、受注すると契約期間明細（継続課金は月次行）と、それを集約した請求／請求明細が生成される
2. **Change**（現在期間内に課金変更があるとき。数量・単価・期中停止・商品追加など。期間終了の延長を伴ってもよい）が手順どおりに見積〜受注できる（日割りは含まない。種別判断は §4.4）
3. **Renew**（現在期間内に課金変更がなく単純延長するとき）／**Cancel**（満了翌日の Churn）が見積〜受注できる（Cancel は見積商品ゼロで受注可、期間明細・請求は作らない）
4. 請求（`Invoice__c`）のロック項目により、差し戻し・同一 Version の再生成、およびロック済み請求の直接更新・削除を **Apex** で止められる
5. 請求プレビューで端数調整・請求日変更・請求を分ける／明細を移す・同一請求内分割ができ、編集結果が請求正本として残る
6. **ARR／DeltaARR／AveARR／DeltaAveARR** が項目として確認できる（専用ダッシュボードは不要）

上記以外（帳票PDF送付、会計連携、電子契約、移行データ作成、受注前の請求ドライラン等）はコア完了の条件に含めない。

### 2.1 EstimateWizardField__mdt

- `Active__c = true` のみ表示・検証対象（無効レコードは無視）
- `TargetObject__c` は次の3種のみ: `ContractService__c` / `ContractHistory__c` / `ContractProduct__c`
- `ShowOnNew__c` / `ShowOnChange__c` / `ShowOnRenew__c` / `ShowOnCancel__c` は複数選択可。チェックのない種別では非表示
- 商品条件付き表示（`Visibility*`）は正式仕様（Product2 項目との照合。条件を満たすときだけ画面表示・必須判定・保存対象）
- 初期値（`DefaultValue__c` / `DefaultSource__c`）は正式仕様
- `Required__c = true` かつ **画面に表示されている**項目は **絶対必須**（未入力なら画面・Apex ともエラーで保存不可）。**Cancel も例外にしない**（ShowOnCancel で表示されていれば必須）。非表示（ShowOn*／Visibility 不一致）の項目は必須判定・保存対象にしない
- Visibility 非表示時の保存: **見積商品**の追加項目は値を **クリア（null）する**。種別（ShowOn*）で非表示の項目はマップから省略し、既存 DB 値は維持する（詳細は §4.7）
- **表示中**の追加項目の保存: マップにキーがあるときはその値、**キーが無い／空のときは null クリア**（契約サービス／履歴／商品とも同じ）。Change／Renew／Cancel で既存契約サービスを更新するとき、画面で破棄・空にしたサービス追加項目が DB に残留しない
- Visibility でいったん非表示になったあと**再表示**されたとき: 画面上はその項目の **DefaultValue／DefaultSource を毎回入れ直す**（直前の入力は保持しない）
- ShowOn* でいったん非表示になったあと**再表示**されたときも同様: 画面マップから prune したうえで **DefaultValue／DefaultSource を入れ直す**（契約サービス／履歴／商品とも同じ。直前の入力は保持しない）
- ShowOn*（`ShowOnNew` 等）が定義上**欠落／未設定**の場合は **非表示**。その種別に出すには明示 true が必要
- 保存時の Visibility 判定コンテキスト: **新規作成・Estimate 編集・Ordered 編集のいずれも、常に対象行の Product2 から再構築して判定する**。リクエストの `productVisibilityContext`（画面メモ）は **保存・必須検証・適用の正本に使わない**（空でも古くても無視。画面の出し分け用に送ってよいがサーバは信じない）

#### Visibility*（Product2 条件）

| 演算子                      | 意味                                                         |
| --------------------------- | ------------------------------------------------------------ |
| `IN` / `EQUALS`             | 実際値のトークンのいずれかが期待値に含まれる                 |
| `NOT_IN` / `NOT_EQUALS`     | 実際値のトークンが期待値に含まれない（空は一致しない＝表示） |
| `IS_BLANK` / `IS_NOT_BLANK` | 実際値が空／非空                                             |

- 条件フィールド（`VisibilityFieldApiName__c`）未設定 → **常時表示**。`VisibilityOperator` だけ入っている場合（CMDT ピッカーのデフォルト `IN` 含む）は未使用扱い
- `VisibilityValues` だけ設定して Field が空 → Active 定義エラー
- 条件フィールドはあるが、行の商品コンテキストが無い／該当キーが無い → **非表示**（必須・保存対象にもしない。ウィザード全体は止めない）
- Field を設定したうえで **演算子が未知** → Active 定義の検証で **エラー**（黙って非表示にしない。typo で項目が消えるのを防ぐ）
- Field 設定時、`IN` / `EQUALS` / `NOT_IN` / `NOT_EQUALS` では `VisibilityValues__c` 必須（空は Active 定義エラー）
- Visibility*（Field または Values）は **見積商品（ContractProduct__c）のみ**。サービス／履歴に書くと Active 定義エラー
- `VisibilityFieldApiName__c` は Product2 に実在する項目 API 名であること（存在しない／ドット付きは Active 定義エラー）
- 実際値の区切りは `;`（マルチセレクト想定）。期待値（`VisibilityValues__c`）の区切りは `,`
- 画面・必須・保存対象の判定は、ShowOn* と Visibility の**両方を満たす表示中項目**に限る（§4.7・§4.15.6）

#### ShowOn*（ウィザード種別）

- `ShowOnNew`／`ShowOnChange`／`ShowOnRenew`／`ShowOnCancel` など種別フラグ
- **未設定／空＝非表示**。その種別に出すには **明示的に true** が必要（未設定を表示扱いにしない）

#### DefaultSource__c（許可一覧）

| 値            | 意味                     | DefaultValue__c                                                           |
| ------------- | ------------------------ | ------------------------------------------------------------------------- |
| （空）        | 静的初期値               | 固定文字列など（そのまますす）                                            |
| `Opportunity` | 商談項目から取得         | 商談の項目 API 名（例: `Name`）。ドット不可                               |
| `Account`     | 商談の取引先項目から取得 | 取引先の項目 API 名（例: `Name`）。`Account.Name` 形式も可（正規化）      |
| `Product2`    | 商品項目から取得         | 商品の項目 API 名（例: `Family`）。**見積商品（ContractProduct__c）のみ** |

旧設定の互換: `DefaultSource=Opportunity` かつ `DefaultValue=Account.xxx` は `Account` + `xxx` として扱う。

#### Active 定義が不正なときの挙動

黙って無効化しない。次のいずれかに該当する **Active** 定義があると、見積ウィザードの項目取得・保存時にエラーとなり保存できない（請求商品コピー定義と同様の fail-fast）。

- `TargetObject` / `FieldApiName` 不正、またはウィザード非対応の項目型
- `DefaultSource` が上記以外
- `DefaultSource` に対する `DefaultValue`（参照パス）が存在しない／不正
- `Product2` を契約サービス／履歴向け定義に指定
- `VisibilityFieldApiName` または `VisibilityValues` を契約サービス／履歴向け定義に指定（Operator のみのデフォルト値は対象外）
- `VisibilityFieldApiName` が Product2 に存在しない／ドット付き
- Field 設定時に `VisibilityOperator` が未対応、または比較演算子なのに `VisibilityValues` が空
- `VisibilityValues` だけ設定して `VisibilityFieldApiName` が空

エラーメッセージには定義の DeveloperName を含める。

### 2.2 InvoiceProductFieldCopy__mdt（表示名: 請求項目コピー）

- Active フラグなし。レコードがあるものはすべて有効
- **適用タイミング: Insert 時のみ**（契約期間明細・請求・請求明細の新規作成。分割で生まれる新請求／新明細も含む）
- コピー先オブジェクト（`TargetObject__c`）: `InvoiceProduct__c`（契約期間明細） / `Invoice__c`（請求） / `InvoiceLine__c`（請求明細）
- コピー元: ContractHistory / ContractProduct / BillingAccount / Product2 / Opportunity / Account
- 定義不正時は受注・正本生成・分割の入口で検証し失敗させる
- **方針（シンプルさ優先）**: 上記3オブジェクトを新規作成するときは、常に有効な CMDT を読んで空欄へスタンプする。既存レコードは自動更新しない。請求プレビューの手修正は当請求のみ（マスタへは書かない／分割で生まれる新請求にも自動引き継ぎしない）

#### ハードコードと CMDT の境界

| 種類 | 内容 |
| --- | --- |
| **ハードコード（必須）** | 外すとロジックが狂う項目。期間明細の見積商品・数量・単価・単位・請求形態、請求の BA SnapShot（Id／宛名／メール／支払条件／請求日）と金額・日付、請求明細の商品参照・単位・金額など。**CMDT に置かない** |
| **標準サンプル CMDT（各オブジェクト1件）** | 書き方の見本。`Sample_Period_AccountName`（取引先名→期間明細）、`Sample_Inv_AccountName`（取引先名→請求）、`Sample_Line_ProductCode`（商品コード→請求明細）。削除して顧客定義に置き換えてよい |
| **顧客追加 CMDT** | レポート埋め込み等。**標準パッケージには含めない**。運用開始後に顧客が追加する |

- ハードコードの To 項目と CMDT の `TargetFieldApiName__c` が重複したら検証エラー（必須を CMDT に載せない）
- 顧客／サンプル定義も Insert 時の同じ経路で適用（空欄のみ。既存値は上書きしない）
- 請求の出力正本としての BA SnapShot は `Invoice__c` へハードコード。期間明細の BA 寄せ項目は標準では必須にしない（サンプル／顧客拡張用）

### 2.3 RenewOpportunityField__mdt（表示名: 更新商談項目）

受注後に作成する更新商談（Opportunity）へ、リレーション以外の項目をセットするための定義。見積ウィザード項目・請求コピーとは別 CMDT。

#### 項目

| API名 | 型 | 必須 | 意味 |
| ----- | -- | ---- | ---- |
| `Active__c` | Checkbox | - | 有効（デフォルト true） |
| `TargetFieldApiName__c` | Text(80) | ○ | 更新商談 Opportunity のセット先 API 名 |
| `ValueType__c` | Picklist | ○ | `Constant` / `Field` / `Template` |
| `Value__c` | Text(255) | ○ | 値（ValueType で解釈） |
| `DateFormat__c` | Text(40) | - | 日付→文字列時の書式（白リスト） |

#### ValueType

| ValueType | Value__c | 例 |
| --------- | -------- | -- |
| `Constant` | 固定値 | `Prospecting` |
| `Field` | `ObjectApiName.FieldApiName`（ドット1つ） | `ContractHistory__c.CurrentTermEndDate__c` |
| `Template` | 穴埋め（差し込みと日付書式のみ） | `{Account.Name} 更新` |

許可参照オブジェクト: `Opportunity`（元商談）/ `Account` / `ContractHistory__c`（今回受注）/ `ContractService__c`  
Template: `{Object.Field}` / `{Object.Field:日付書式}`。略称は略称項目を参照（エンジンは略さない）。  
日付書式白リスト: `yyyyMM` / `yyyy-MM-dd` / `yyyy/MM/dd` / `yyyy/MM` / `yy/MM`

#### コード固定のリレーション（CMDT 禁止）

| 項目 | 値 |
| ---- | -- |
| `AccountId` | 元商談と同じ |
| `PreviousOpportunity__c` | 元商談 |
| `SourceContractHistory__c` | 今回受注した契約履歴 |
| `Id` | 禁止 |

`OwnerId` は CMDT 可（契約履歴の数式が返すユーザIDを Field 参照する等）。

#### 作成 API（`RenewOpportunityCreateService`）

| メソッド | 意味 |
| -------- | ---- |
| `createFromOrderedHistory(Id)` | 更新商談を1件作成 |
| `findBySourceHistory(Id)` | 紐づく更新商談 Id（複数なら新しい方） |
| `deleteBySourceHistory(Id)` | 紐づく更新商談を削除 |
| `validateActiveDefinitions()` | Active CMDT の fail-fast 検証 |

- 契約履歴は **Ordered** かつ **Cancel 以外**。元商談・取引先必須
- 同一履歴に既に紐づく更新商談がある場合は **エラーにしない**。旧商談の `SourceContractHistory__c` を外し（商談自体は残す）、新規を作成して紐づけは新しい方だけにする
- Active 定義不正・作成失敗時は呼び出し元トランザクションをロールバック

#### パッケージ同梱サンプル（導入時に書き換え前提）

| DeveloperName | Target | ValueType | Value |
| ------------- | ------ | --------- | ----- |
| `Name` | `Name` | Template | `{Account.Name} 更新` |
| `CloseDate` | `CloseDate` | Field | `ContractHistory__c.CurrentTermEndDate__c` |
| `StageName` | `StageName` | Constant | `Prospecting`（組織のフェーズに合わせて変更） |

### 2.4 ContractValidationEnforce__c

- **OFF（デフォルト）**: 不特定クライアント向け汎用提供状態。申込日必須などの顧客固有 VR は効かない
- **ON**: 顧客固有の項目・ルールを組み込んだ状態
- テストは OFF 前提でよい

### 2.5 InvoiceLockExemptFields__c

請求（`Invoice__c`）のロック中更新許可項目を階層 CS で制御する。契約期間明細（`InvoiceProduct__c`）にロック項目・除外 CS は持たない（ロックの正は請求のみ。§6.9）。

| CS | 対象 | 未設定時の既定除外項目 |
| --- | --- | --- |
| `InvoiceLockExemptFields__c.FieldApiNames__c` | `Invoice__c` | `PaymentClearedAmount__c,PaymentClearingCompletedDate__c` |

- 値はカンマ区切りの項目 API 名（Text 255）
- ロック判定は「`isSet` された項目のうち、値が変わったものがすべて除外リスト内」のときだけ通す（部分更新で未ロード項目を誤検知しない）
- 連携未済の消込日クリア（エクスポート取り消し）は除外リスト外でも許可
- 金額・請求日など除外リスト外の変更は従来どおり拒否（§6.9）

### 2.6 顧客固有のサンプル

- `ApplicationDate__c`（申込日）は本番用 `EstimateWizardField.History_ApplicationDate` で **ウィザード追加項目として New / Change / Renew / Cancel すべてに表示し、`Required__c=true` で必須**（`Sample_*` は `.forceignore` 対象のため本番へは出さない）
- 受注（Ordered）遷移時の DB レベル必須は別系統: VR `Ordered_Requires_ApplicationDate` + `ContractValidationEnforce__c.Enforce__c`（OFF が標準提供）

#### 3.1 請求まわりの二層モデル

| 層 | オブジェクト | 正本か | 役割 |
| -- | ------------ | ------ | ---- |

- 契約期間明細と請求正本の合計が、手動調整により意図的にズレてよい（ズレ＝調整結果）。双方向同期はしない

契約種別: `New` / `Change` / `Renew` / `Cancel`  
通貨: **JPY のみ**（換算ロジックなし）

#### 4.0.5 見積ウィザード：確認ダイアログ（公式）

| 契機                                          | 動き                                                                         |
| --------------------------------------------- | ---------------------------------------------------------------------------- |
| 閉じる                                        | **保存成功まで毎回破棄確認**（入力有無は問わない）。**保存成功後は確認不要** |
| Change で同 Product2 を Type=New に載せた保存 | 確認のうえ続行可（§4.4）                                                     |
| 見積備考マスタ選択                            | 既存自由文があるとき上書き確認                                               |
| 見積備考マスタ解除                            | 備考テキストもクリアする確認                                                 |

**確認は同時に1種類だけ**（`close`／`remarks`／`sameProductNew`）。モードを混ぜない。

- 「続行」「キャンセル」は **いま開いている確認専用**の処理だけを実行する（閉じる確認中に保存確認へ差し替わって破棄される、備考確認の続行で保存が走る、等を禁止）
- 確認表示中は **次へ／前へ／保存／Step 移動を不可**（保存・次へはトーストで案内）。新しい備考確認が来ても拒否し、表示中の確認を優先する
- **閉じる**だけは例外で、他確認表示中に押されたら他確認をキャンセル扱いして破棄確認へ切り替えてよい（閉じる意思を優先）
- バリデーションエラー表示に切り替えるときは、開いていた確認をキャンセル扱いしてからエラーを出す

#### 4.0.7 Ordered の「見積編集」

- 触れるのは **ウィザード追加項目の編集・保存・閉じる** のみ（画面上は主に Step2＝詳細情報）
- Step1（基本情報）の標準項目（種別・契約名・請求アカウント等）は Readonly 確認
- 明細の追加／削除／コピー、期間変更、日付ショートカット等の明細操作は出さない

### 4.1 共通

- Step1（基本情報）では DB 保存しない。**Step2（詳細情報）の保存**で一括作成／更新
- 保存時の契約履歴ステータスは常に `Estimate`
- 編集時は契約種別変更不可
- 受注ウィザードに「履歴備考だけ編集する Step」は不要（請求先確認 → 受注確定でよい）。備考項目定義も持たない（§5.2）
- 見積は商談起点。契約履歴に商談必須、商談の取引先も必須
- **Change／Renew／Cancel**: 契約サービスの取引先（Account）と商談の取引先は**一致必須**。不一致なら**見積保存時点でエラー**（受注まで残さない）
- 商品選択は `Product2.AvailableForContract__c = true` のみ
- 見積商品の単位（`Unit__c`）: **商品マスタの単位をそのまま保存**する。継続課金だからといって保存時に「・月」等を付け足さない（画面もマスタ単位の表示でよい）
- **同じ項目を両 Step で編集しない**（特に契約履歴名・請求アカウント・契約サービス名／選択）

### 4.2 Step1（基本情報）

役割: **方針**（種別・契約の特定・請求アカウントの確認／選択）。サービス／履歴／明細の追加項目は置かない。

#### 共通（パネル「基本情報」）

- 取引先名・商談名を表示（編集不可）
- 契約種別（New / Change / Renew / Cancel）は **商談名の右に横並びの角丸ボタン**（編集モードでは変更不可。契約の特定内に重複表示しない）。**4種の横幅は均等**
- **基本情報パネルの入力行は1行**（取引先名｜商談名｜タイプ）
- **契約の特定パネルの主入力も種別問わず1行**
  - New: 契約サービス名｜**契約履歴名**｜作成 Version｜請求アカウント
  - Change／Renew／Cancel: 契約サービス｜**契約履歴名**｜ベース Version｜ベース契約履歴｜請求アカウント（サービス／履歴名／Version／請求の位置は New と揃える。ベース契約履歴は Version の右の参照枠）
  - 契約サービス未選択時の空メッセージ等は行下に出し、1行グリッドを崩さない
  - Change／Renew／Cancel の契約サービス候補は **読込完了まで空メッセージを出さない**（読込中表示）
  - **ウィザードを開いた時点の表示は常に最新**（§4.15.11）。候補・preset・明細ブートストラップをクライアントキャッシュの取り残しで見せない
  - 請求アカウント下の補助UI（選び直す／他取引先トグル等）は同セル内に続けてよい

#### New（パネル「契約の特定」）

- 必須（次へ）: 契約サービス名、契約履歴名
- 既存契約サービスの選択は不要（新規作成）
- 契約サービス名／契約履歴名が空のとき、**商談名を初期値として埋めてよい**（既入力は上書きしない）
- 作成 Version は表示のみ（常に 1）
- **請求アカウント**
  - 選択可（任意）。未選択でも見積の作成・保存は可。受注時は必須
  - 候補が1件だけのときは自動選択してよい
  - **選択後は Readonly 表示**（選び直す操作で再選択可）
  - 「他の取引先の請求アカウントも検索する」は正式機能。選んだ請求先で**受注してよい**（請求先だけ別取引先でも可）
  - 上記トグルを **OFF にしたとき**、現在の選択が自取引先の候補外なら請求アカウント選択を**クリア**する
- 請求アカウントの宛名・メール等の編集は見積ウィザードでは行わない。直すときはウィザードを閉じて請求アカウント側（標準レイアウト等）で行う

#### Change / Renew / Cancel（パネル「契約の特定」）

- 必須（次へ）: 既存契約サービス、前回契約履歴（自動確定）、**契約履歴名**
- 選べる契約サービスが **1件だけ**のときは自動選択してよい
- 契約履歴名が空のときの初期値: Change／Renew は **空のまま**（前回履歴名の自動コピーはしない）。Cancel は前回履歴名＋` Churn`（無ければ空）
- 契約サービスを切り替えたときは **契約履歴名をクリア**する（Cancel は新しい自動名で初期化し直す）
- ベース契約履歴・ベース Version は表示（種別は基本情報の角丸ボタンに一本化）
- 前回期間終了日まで届く継続課金が無い場合は作成不可。**カードは Term なら出す**（通常の候補では起きない想定。手修正／API で選んでしまった場合は、Step1 で操作を選んだ直後および次へでエラー）
- 継続／一回の判定は **見積商品明細 `BillingType__c` が正**（空のときだけ Product2）
- 前回が Cancel の場合は Change／Renew／Cancel 作成不可
- **請求アカウントは Readonly 確認のみ**（契約サービスに紐づく値を表示）。ウィザードで選び直さない。保存時も契約サービスの請求アカウントを上書きしない
- 請求アカウント未設定でも見積は可、受注時は必須

#### Step1 でやらないこと

- 期間・有効日・商品明細
- 契約サービス／契約履歴／見積商品のカスタム項目
- 備考

### 4.3 Step2（詳細情報）

役割: **内容**（期間・商品・属性）。保存はここだけ。

- 契約サービス名・作成 Version は **出さない**（Step1 側。期間入力に集中する）
- **契約履歴名・請求アカウントは出さない**（履歴名・請求は Step1 の契約の特定のみ）
- **期間・有効日・商品明細**: 規則は §4.4
- **カスタム項目（すべてここ）**
  - `ContractService__c` / `ContractHistory__c` / `ContractProduct__c`（明細行内）
  - **表示条件**（ShowOn*／Visibility）は種別ごとに適用する
  - **パネル表示**: 契約のカスタム項目は、商品明細がある種別では **備考と同じ条件**（商品明細が表示され、期間が確定し、明細が1行以上あるとき）。**Cancel は商品明細がないため、カスタム項目パネルのみ表示**（備考は出さない）。Ordered 編集は例外で表示する
  - **全種別（New／Change／Renew／Cancel）**: 契約サービス／履歴のカスタムは同じロジック（表示条件を満たすものを編集可・**Required なら必須検証**・保存反映）。Cancel も備考とは違い、表示中の必須カスタムは未入力エラー
  - **Ordered 編集**: 表示中のウィザードカスタムのみ編集可（§4.7）
  - 契約サービス／履歴のカスタム項目は独立パネル「契約のカスタム項目」。**1つの開閉トグル**（合計件数バッジ・**デフォルト開**）。中でサービス／履歴を分けて表示
  - 商品のカスタム項目も **デフォルト開**（明細内は小さめ表示）。トグルラベルは「商品のカスタム項目」。**商品データ行の縦密度は約 0.8 倍**（文字・入力・チップ・操作ボタンを一式）。商品カスタム項目グリッドはそれ以上縮めない
  - 商品明細ヘッダ: 左にタイトル「商品明細」、右に **商品のカスタム項目トグル → 行を追加**（この順）
  - 契約のカスタム項目／備考の開閉トグルは **ヘッダ左側**
  - Step2 のパネル順: **契約期間 → 商品明細 → 契約のカスタム項目 → 備考**
  - **パネル見た目**: 4セクションとも同一のパネル枠・ヘッダ行（タイトル左／アクション右）。タイトル字体・ヘッダ余白を揃える
  - **見積総額（集計行）**: 商品明細パネル**内**の**明細表の最下部**に表示。**明細数**（金額列の左）／**金額**（金額列の真下）／**税込金額**（その右）。青太字・同一サイズ、白枠なし。集計行のみ青系背景。税率は契約サービス `TaxPercent__c`（レコード未作成時のみ表示用に 10%。既存レコードの未入力は 0%。税額は切り捨て。§4.6・§6.10）
- **備考**（マスタ／自由文）。Cancel は出さない（§4.4）。パネルはカスタム項目と同様に **開閉トグル可**（デフォルト開。開閉状態は親状態に保持。トグルは左側）
- Cancel は商品明細 UI なし・備考 UI なし。**契約カスタム項目は表示**（ShowOnCancel／Visibility に従う）。**表示中かつ Required なら Cancel でも必須**（§2.1・§4.15.6）

### 4.4 期間・商品（詳細情報の業務規則）

#### 4.4.0 種別の判断ロジック（New / Cancel / Change / Renew）

見積種別は次の順で決める。**「延長＝必ず Renew」ではない**（よくある誤読。バグ報告対象にしない）。

```
新規の契約サービスを始める
  → New

既存の契約サービスについて
  ├─ 契約期間どおり満了したあと、解約（Churn）を確定したい
  │    → Cancel
  │      ・解約日＝前回 Ordered 終了の翌日のみ（開始＝終了の1日）
  │      ・期中に課金を止める操作は Cancel ではない（→ Change）
  │
  └─ 続けて使う（延長・条件変更・商品追加など）
       │
       現在の契約期間内（前回 Ordered の開始日〜終了日）に
       課金条件の変更があるか？
         │
         ├─ YES（数量／単価／請求設定／BillingType の変更、
         │       Remake 途中開始、期中停止、商品追加 など
         │       ＝前回期間内に課金イベントが1つ以上ある）
         │    → Change
         │      ・期間終了を前回終了より後ろへ延ばしてよい
         │        （数量変更＋終了延長など。延長区間に past が無いため
         │         新条件のフル課金になるのは洗い替えとして仕様どおり）
         │      ・期間終了の下限は前回終了以上
         │
         └─ NO（期間内に課金変更がなく、単純に期間だけ延ばす／更新する）
              → Renew
                ・開始＝前回終了の翌日
                ・「終了日だけ延ばす Change」は不可（Renew へ誘導）
```

| 種別 | 一言 | 典型例 |
| --- | --- | --- |
| **New** | 新しい契約サービスを始める | 初回受注 |
| **Cancel** | 満了後の解約（Churn）確定 | 6/30 満了 → 解約日 7/1 |
| **Change** | **現在期間内に**課金変更がある | 数量変更、単価変更、期中停止、商品追加。**変更に伴う終了延長も Change** |
| **Renew** | 期間内変更なしの**単純延長** | 条件そのままで翌期へ更新 |

実装のバリデーションもこの判断に合わせる: Change で「前回期間内に課金イベントが無い」または「有効日が前回終了より後ろ」だけになるケースは Renew 誘導する。**期間内に課金変更がある Change で終了を延ばすのは正規**であり不具合ではない。

| 種別   | 契約サービス | 期間開始                                                                      | 期間終了                             | 有効日                                                                                 | 商品                           |
| ------ | ------------ | ----------------------------------------------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------- | ------------------------------ |
| New    | 新規作成     | 任意（月途中可）。開始入力時、**終了が空なら**開始から12サイクル目の終了日を初期セット（手入力済み終了は開始変更でも上書きしない） | 開始以降（契約開始日起点の月次分割） | 期間開始と一致（日割不可）                                                             | New 等                         |
| Change | 再利用       | 前回開始と一致                                                                | 前回終了以上（※1）                   | 前回期間内。最早の課金イベント日に固定（手でずらせない）。継続課金イベントがあるときのみ請求期間開始日必須（日割不可）。**一回課金 New 追加のみのときは期中有効日可** | Original / Remake（+任意 New） |
| Renew  | 再利用       | 前回終了の翌日                                                                | 開始以降                             | 期間開始と一致                                                                         | Renew（+任意 New）             |
| Cancel | 再利用       | **解約日＝前回終了の翌日（固定）**                                            | **同上（開始＝終了）**               | **同上**                                                                               | **0件必須**                    |

※1 Change の期間終了「前回終了以上」は下限。**期間内に課金変更がある Change では前回終了より後ろへ延ばしてよい**（§4.4.0）。**終了だけ延ばして期間内変更が無い**場合は Change 不可 → Renew（単純延長）。

**共通ルール**

- 継続課金の期間は「**その明細の開始日**起点の月次分割」のみ許可。カレンダー月分割は不許可（画面・保存ともエラー）。**終了日も明細開始日起点の月境界に一致必須**。金額・回数表示のために終了日を長く正規化して通すことはしない。手入力で境界からずれている場合は **短い側の境界へフィールドを寄せる**（切り捨て）。エラー文言も「明細開始日起点」と揃える
- ヘッダー期間の月次分割（継続課金がある New／Change 等）は **ヘッダー期間開始日**起点（こちらも境界不一致は、画面では短い側へ寄せる／保存は厳密判定）
- **月数 N の終了日**は `endDateForMonthlyCycles(開始, N)`（開始から月次期間を N 回積んだ最後の終了日）を正とする。暦の「開始＋N年−1日」とは月末開始などで一致しない場合がある（例: 1/31 開始の12サイクル終了は翌年1/27）
- 日割りは不可。月途中開始は可（継続課金の有効日は期間開始／請求期間境界に一致。一回課金 New 追加のみの Change 有効日は期中可）
- **有効日は全種別で画面自動セット・手入力不可**（入力欄は読み取り専用）
  - New: 期間開始と一致
  - Renew／Cancel: 更新開始／解約日と一致
  - Change: 明細から求めた最早の課金イベント日。明細変更のたびに自動更新（下記 Change 固有）
- New で期間開始を入れると、終了が空なら **開始から12サイクル目の終了日** を自動セット（その後手動変更可）。明細開始を入れ終了が空／不正のときも同様
- New ではヘッダーの期間開始・終了が揃うまで明細編集不可。揃った時点で空の明細行を1行用意する（空行が複数あれば先頭1行に畳む）。**すでに商品が入った行があるときは空行を自動追加しない**
- **アクティブ明細**（商品あり・数量>0。Original 以外）:
  - **単価は必須**（未入力／null は「単価を入力してください」）。**0円は明示入力したときのみ可**（空欄を 0 扱いしない）
  - 請求設定必須。課金種別と合わない請求設定は **エラーで止める**（選択を黙って戻す／自動置換しない）
  - **課金種別（継続課金／一回課金）の正は見積商品明細 `BillingType__c`**（空のときだけ Product2）。ウィザードで新規に商品を選ぶときの初期値はマスタ。保存時のマスタ一致は従来どおり（New の継続→一回上書きのみ許可）
- Type=New 明細（Change／Renew／新規見積共通）:
  - 開始・終了必須、開始≦終了、ヘッダー期間内、数量>0、請求設定必須
  - **商品未選択の空行（下書き）は検証・保存対象外**（無視してよい）
  - **同一 Product2 の期間重複は不可**（画面・保存ともエラー）。対象はアクティブ行同士（数量>0・商品あり）。Change では Original 行を重複判定から除外し、Remake／New など編集対象同士で判定する
  - **期間が重ならなければ同一 Product2 の複数行は許可**（空白期間を挟んだ再開・期間分割を含む）
  - 継続課金は明細開始日起点の月次分割必須。一回課金は月次分割対象外かつ月次分割不可
- 新規見積で継続課金がある場合: ヘッダー期間もヘッダー開始日起点の月次分割必須、期間開始・終了に届く継続課金が必要
- Renew は継続課金1行以上必須（一回課金のみの Renew は不可）
- 前回履歴は選択した契約サービスの **最新 Ordered かつ Type=New／Change／Renew**（最新 Estimate ではない。**Cancel Ordered は前回に使わない**）。画面文言「Estimate以外」は誤りで、上記に揃える
- **保存時も同じ制約をサーバで強制**する（古い Ordered／Estimate を previous に指定した保存はエラー。「最新の受注を指定してください。画面を開き直してください」）
- **編集保存**では `PreviousHistory__c` をクライアント値で書き換えない（DB の値を正とし、それが最新 Ordered でなければ保存エラー）

**Change 固有**

- 課金イベントが**前回期間内**に1つ以上必須（前回終了より後ろにしかイベントが無い場合は不可 → **意図的に Renew 誘導**）
  - 差分の比較対象: **商品（Product2）／数量／単価／BillingType／請求設定**
  - 上記に加え、Remake 途中開始・系統なし追加行（Type=New 等）の開始も課金イベント
  - **契約期間の延長だけ**（Remake／ヘッダー終了を Original＝前回終了より後ろへ延ばすのみ、期間内に数量・単価・BillingType・請求設定の変更なし）は課金イベント日が前回期間外になり、**Change では保存できない**（エラーで Renew へ誘導）。**仕様どおりの遮断**であり不具合ではない
  - **非対象**: 単位のみの変更、カスタム項目のみの変更（金額・請求日が変わらないもの）
  - 単位だけ変えた Change は課金イベントなし扱いとなり、Renew 誘導になる（表示用の単位修正だけでは Change にならない）
  - **BillingType（継続／一回）だけ変えた Remake** も課金イベントあり（API／手修正データの防御。正規ウィザードは Product2 マスタ一致のため通常起きない）
- 有効日は最早の課金イベント日に固定する（画面・保存とも手でずらせない）
  - 課金イベントが複数ある場合も、有効日はそれらのうち最早の1日に揃える
  - 有効日をイベントごとに分けたい場合は、Change 見積を分ける（1見積＝1有効日）
  - 運用例: 5/1 数量変更と 7/1 単価変更を同一 Change にまとめると有効日は 5/1 固定。7/1 の単価変更だけ別タイミングにしたいなら、数量変更の見積と単価変更の見積に分ける
  - **請求期間開始日（日割不可）制約**: 継続課金由来の課金イベント（Remake 内容差分・途中開始、継続課金の Type=New）があるときのみ適用。**課金イベントが一回課金 New 追加のみのときは期中有効日を許容**（一回課金は月次分割・日割り対象外）
- **Original／Remake のカバー義務の対象**は、前回 Ordered の **継続課金・数量 > 0** の見積商品のみ（Type が Remake／New／Renew、または空）。**継続課金かどうかは明細 `BillingType__c` が正**（空なら Product2）。**一回課金は対象外**（自動では載らない。必要なら Type=New で手追加）
- Original 期間は、数量 > 0 の Remake 群で隙間なく埋める（Remake 終了 ≥ Original 終了）。**「終了だけ延ばして契約を更新する」用途には使わない**（それは Renew）
- Remake の開始日は Original 開始日以降のみ可（途中開始は可）。**Original より前への前倒し開始は不可**（業務上そのケースは想定しない）
- 有効日は請求切替日であり、Remake による Original 全期間カバー義務の免除条件ではない
- **Original／Remake の意味（洗い替え）**: Change は「古い状態（Original＝前回の打消し）を、Remake が表す新しい状態で **期間ごとに完全洗い替え**」する。Remake の期間・数量・単価がそのままその区間の新条件になる。起動時のデフォルト（Original 全期間を Remake 1本で覆う）は「全期間を同じ新条件に置き換える」形
- **全期間 Remake 1本を単価0にしたとき**: それは期中停止ではなく、**Original 全期間を単価0へ洗い替え**（契約開始からの遡及的な全打消し）である。見積ネットが前回年額のほぼ全額マイナス・有効日が期首になるのは **入力どおりの正しい結果**であり不具合ではない
- **期中解約相当（期中停止）の正しい入力**: Remake を **2本以上に分割**する。停止前は有料 Remake、停止後だけ単価0（金額0）Remake。Remake 群全体で Original 全期間を隙間なく充足する。数量は運用上 Original 維持が望ましいが、**バリデーション上は数量>0 なら Original と異なっても可**。Remake 終了を Original より前に切る表現は不可。**ヘッダー Type=Cancel ではできない**（Cancel は満了翌日のみ。使い分けは下記 Cancel 固有）
  - 例（契約 2024/4/1〜2025/3/31・月額2万・2025/1/1 から停止）:
    - Original: 4/1〜3/31・2万（打消し -24万）
    - Remake①: 4/1〜12/31・2万（+18万）
    - Remake②: 1/1〜3/31・単価0（0）
    - 見積ネット **-6万**・有効日 **2025/1/1** が期待結果
  - 対比: Remake 1本（4/1〜3/31・単価0）だけ → ネット **-24万**・有効日 **4/1**。これは「4/1 からの全期間0洗い替え」であり、期中停止の入力ではない（バグ報告対象にしない）
- Original／Remake は `PreviousContractProduct__c` で前回の見積商品系統を保持する
- Original 行は**完全読み取り専用**（削除・Product2 差し替え・数量／単価／金額／期間／請求設定／金額入力モードすべて不可）。編集は Remake／New のみ
- **Original 行にはウィザード追加項目を出さない**（表示しない・初期コピーしない・保存時も載せず、設定済みの追加項目は null クリア）。追加項目は Remake／New のみ
- Original 行の `Amount__c` は符号反転（打消し）。画面表示も同様
- Change 起動時の初期金額: Original = `-(前回Amount)`、Remake = `前回Amount`（符号付きのまま。値引きの負 Amount を絶対値化しない）
- **Original が前回明細と一致必須の項目**: 商品／数量／単価／請求設定／開始日／終了日（**単位は一致必須にしない**）
- Remake は「変更後行を追加」で同一系統に追加できる。Remake も Product2 変更不可（数量・単価・請求設定・期間は可）
- 同一系統の Remake 同士で数量・単価・BillingType・請求設定・期間を変えてよい（その差分が課金イベント）
- **有効な継続課金明細のうち少なくとも1行の終了日＝ヘッダー終了日**であること
- Type=New は Original／Remake 系統のカバー規則の対象外。ただし Type=New のバリデーションは必要
- **同一商品の New 追加方針（Change）**:
  - 条件変更・数量増減の正規経路は Remake（既存明細の編集）。**単純延長だけなら Renew**（§4.4.0）。期間内変更ありの終了延長は Change で行う
  - Original／Remake 系統と同じ Product2 を Type=New に載せることは **禁止しない**（期間非重複なら保存可。空白期間後の再開などを含む）
  - ただし誤って更新・条件変更を New で表現しないよう、保存前に **確認ダイアログ**を出す（「既存契約と同じ商品が新規明細に含まれています…追加購入の場合はそのまま続行できます」）。ユーザーが続行すれば保存する
  - Remake と New で同一 Product2 の期間が重なる場合は、上記の期間重複エラーで弾く（確認では通せない）

**Renew / Cancel 固有**

- **単純延長（期間内に課金変更なし）の正規経路は Renew**（§4.4.0）。期間内に課金変更があるときの終了延長は Change（下記 4.4.1）
- Renew の商品引継ぎ:
  - **自動で載るのは継続課金のみ**（明細 `BillingType__c` が正。空なら Product2）。現在の最新 Ordered の期間終了日に届いている（明細終了日＝期間終了日）継続課金だけを、期間開始＝前回終了の翌日・期間終了＝開始から12サイクル目の終了日で引き継ぐ（いわゆる1年延長）
  - **単価0／Amount0 の明細も数量>0 なら引継ぎ対象**（手動 Renew・自動 Renew とも同じ）。**Amount≠0 での除外はしない**
  - **理由（意図的）**: 単価0は「期中停止後の残区間」にも「無料提供」にも使われる。見た目はどちらも数量>0・単価0・期末到達で区別できない。単価0を一律除外すると **無料提供の延長まで落ちる**ため、安全側として 0円も載せる
  - **期中停止した商品が翌年に単価0で載ること自体は不具合ではない**（仕様どおりの引継ぎ）。不要なら手動 Renew のゴミ箱で削除する。0円だけの Renew も保存・受注は可能（金額>0 は必須条件ではない）
  - **ARR は金額0を除外するが Renew 引継ぎは除外しない**。ARR（ランレート集計）と更新明細の候補は目的が違うため、この非対称は仕様（バグ報告対象にしない）
  - **一回課金は自動引継ぎしない**（初期費用など）。更新時にもう一度取る場合は Type=New で手追加する
  - 引き継いだ Type=Renew 行: **Product2 差し替え不可**（商品名は読み取り専用表示）。数量・単価・請求設定・期間の編集と **ゴミ箱（×）削除は可**
  - 引継ぎ行の期間初期値: **開始＝ヘッダー期間開始（前回終了の翌日）、終了＝開始から12サイクル目の終了日**。商品・数量・単価・請求設定は前回からコピー
  - Renew 画面で手追加した Type=New 行: 商品選択可・削除可（通常の New 明細と同じ）
  - Renew 行と同じ Product2 の Type=New も、**期間非重複なら許可**（Change のような同商品確認ダイアログは出さない）。期間重複は共通ルールどおりエラー
- Renew は継続課金1行以上必須（一回課金のみの Renew は不可）。ゴミ箱で継続課金をすべて消すと保存時に弾く
- Cancel の詳細情報は商品明細 UI なし（常に空）。**備考（マスタ／自由文）の編集 UI も出さない**。保存時も **`EstimateNoteMaster__c` / `Note__c` は常にクリア**（§4.11）
- **Cancel の解約日は前回 Ordered の期間終了日の翌日に固定**（開始＝終了＝その1日のみ）。画面ラベルは「解約日」だが、任意日は入れられない（例: 6/30 満了なら入れられるのは 7/1 のみ。7/15 はエラー）
- Cancel は契約満了後のステータス確定（Churn）向け。請求商品は作らない
- **最終利用日までは契約中、解約は翌日扱い**（例: 6/30 満了 → 解約日 7/1）。受注後の契約サービス `ServiceEndDate__c`（最新契約終了日）が 7/1 になるのは仕様どおり（§5.5）。最終利用日に戻す修正対象ではない
- **期中の停止・途中解約は Cancel ではなく Change（Remake 分割＋停止後単価0）**。満了を待たずに止める操作を Cancel の解約日で表現しない。全期間 Remake1本の単価0は全期間洗い替え（§4.4）

#### Cancel と Change（金額0）の使い分け

| やりたいこと                                  | 使う種別                   | 日付                                                      |
| --------------------------------------------- | -------------------------- | --------------------------------------------------------- |
| 契約期間どおり満了し、翌日で解約（Churn）確定 | **Cancel**                 | 解約日＝前回終了の翌日のみ                                |
| 期中に課金を止める／未経過分を金額0にする     | **Change**（**Remake 分割**＋停止後だけ単価0） | 有効日は課金イベント規則に従う。全期間 Remake1本を0にするのは全期間洗い替え（§4.4） |
| 契約開始から条件を全期間0に洗い替える         | **Change**（全期間 Remake1本・単価0）          | 満額打消し・有効日期首になるのは仕様どおり。期中停止と混同しない                   |

#### 4.4.1 Change で正式対応するパターン

1. 内容変更（数量／単価／請求設定）。ただし **請求設定だけの Change は受注不可**（下記）
2. 途中開始の Remake（有効日以降から条件変更）
3. 期中解約相当＝期中停止（**停止前有料 Remake ＋ 停止後単価0 Remake** などで Original 全期間を充足）。**Cancel では不可**。全期間 Remake1本の単価0は期中停止ではなく全期間洗い替え（§4.4）
4. 全期間の条件洗い替え（デフォルトの Remake1本のまま数量・単価等を変える。単価0なら契約開始からの全打消し）
5. 商品追加（Type=New）。別 Product2 の追加購入のほか、既存系統と同じ Product2 でも **期間非重複なら可**（空白期間後の再開など）。同 Product2 の New は保存前確認あり（§4.4 共通の同一商品方針）
6. **期間内の課金変更に伴う終了日延長**（例: 数量変更しつつヘッダー／Remake 終了を前回終了より後ろへ）。延長区間は past が無いため新条件のフル課金になる（仕様どおり。§4.4.0）
7. 上記の組み合わせ

**単純延長だけ**（前回期間内に課金イベントが無い）は Change の対象外 → **Renew**（§4.4.0・§4.4.2）。

#### 4.4.2 Change でやらない／できないこと

1. **単純延長のみ**（Remake／ヘッダー終了だけを延ばす、または前回期間内に課金変更がなく延長期間にしかイベントが無い Change）。**正規経路は Renew**。画面・保存とも「ChangeではなくRenewで作成してください」等で遮断する（不具合ではない）。※期間内に数量変更などがあるうえでの終了延長は §4.4.1 の正式パターンであり、ここには含めない
2. **請求設定だけの Change の受注**（数量・単価・BillingType・途中開始・終了延長・Type=New 追加が無く、課金イベントが請求設定差のみ）。見積の下書き保存は可。**受注はエラー**（`ContractOrderValidationService`）。理由: 金額が同じだと請求スケジュール差分が出ず、未請求なら **差し戻して元見積（V1）の請求設定を編集して再受注**するのが正。請求後に設定だけ変える運用は想定しない
3. 日割りでの条件変更
4. Remake の Product2 差し替え（別商品へのスイッチ）
5. 期間開始日そのものの変更（前回開始と不一致）
6. Remake を Original より短く切って短縮する（金額0充足なしの短縮）
7. Remake を Original 開始日より前から始める（前倒し開始）
8. 課金イベントなしの Change
9. 同一 Product2 の Remake／New 同士などの **期間重複**（Original 除外。画面・保存エラー）

### 4.5 Version 採番

- New = 1
- Change／Renew／Cancel = **最新 Ordered の Version + 1**
- 既存の未受注 Estimate と Version が重複してもよい
- 同一契約サービス上に複数の未受注 Estimate（同 Version 含む）が並存してよい。受注した方が勝ち、Version 以下の他 Estimate は Archive
- **Ordered は契約サービス × Version で一意**（`ContractOrderValidationService`）。既に同じ Version の Ordered がある、または同一 DML で同 Version を複数 Ordered にする場合は受注不可。ウィザードの楽観ロック（§4.17）に加え、API／一括／交差受注の保険

### 4.6 税率

- **正の税率の置き場**は契約サービス `TaxPercent__c`（Percent 項目）
- **項目初期値（メタデータ）は `0.1`**＝画面上 **10%**（Percent の数式初期値は小数表記）
- Apex/SOQL で読むと **表示％（10）** のことも、初期値由来で **小数（0.1）** のこともある。計算前に必ず `fromPercentFieldStorage` で表示％へ揃えてから `resolveTaxPercent` する（見積 PDF・請求生成・マージとも同じ）
- `fromPercentFieldStorage`: `0 < x < 1` なら ×100、それ以外（表示％）はそのまま
- 見積保存時に「未設定なら税率を明示セット」する処理は持たない
- **未入力（null）は 0% 扱い**。10% など別値への置換・フォールバックはしない（混乱を避ける）
- **null になり得る経路**: 項目にデフォルト（10%）があるため、通常の新規作成では入る。null は **意図的にクリアしたとき**（または移行データで空のとき）に限る。受注時に税率必須にはしない（0% 請求を許容する仕様）
- **例外（画面の見積総額税込のみ）**: 契約サービスレコードがまだ無い New 作成中は、表示用に **10%** で税込を出す（保存時に税率をセットする処理は持たない。§4.3）
- **請求商品の `TaxPercent__c` は生成時点のスナップショット**（契約サービスからコピー）。契約サービスの税率を後から変えても、既存の請求商品は変わらない。以降に新規生成される請求商品だけ変更後の％が入る
- **表示％として**負・100超・`0 < x < 1` を `resolveTaxPercent` に直接渡すのはエラー（項目値は先に `fromPercentFieldStorage`）

詳細（税額の切り捨て・インボイス）は [§6.10](#610-税)。

### 4.7 編集

- **Estimate**: 種別固定のまま、基本情報＋詳細情報（期間・商品・カスタム項目など）すべて編集可
- Change／Renew／Cancel の編集保存では **`PreviousHistory__c`（ベース履歴）は DB 値を維持**し、ペイロードでの差し替えを受け付けない。かつその値が **最新 Ordered** であること（§4.4）。古くなったベースの見積は開き直して作り直す
- **Ordered**: ウィザード追加項目（`EstimateWizardField__mdt`）のみ更新可（期間・商品・ステータスは不可）
  - 追加項目の入力 UI は **詳細情報（Step2）** に集約する
  - ただし **画面に出るのは、その時点で表示条件を満たす項目だけ**（Active・ShowOn*・商品 Visibility）
  - 編集・必須・保存の対象も「表示中の項目」に限る。条件を満たさない追加項目は Ordered でも出ない／触れない
  - 見積商品の Visibility 非表示項目は保存時にクリアされ得る（§2.1）。「Ordered は追加項目だけ触れる」＝定義済み項目が常に全部見える、ではない
  - Ordered 保存でも Visibility は **常に Product2 から再構築**して判定する（新規作成保存と同じ。クライアントの空／古い context で条件付き項目を誤クリアしない）
  - 表示中のサービス／履歴追加項目は、画面マップに無くても **null で上書き**する（§2.1）。ShowOn 非表示だけ省略して DB 維持
- **Archive**: 編集不可

### 4.8 コピー

- 元は Estimate のみ（Ordered からは不可）
- 「別レコードを裏で複製する」のではなく、**見積ウィザードを開き、元見積の内容を画面の初期値（デフォルト）としてセットする**操作
- 初期セット対象: 種別・期間・商品明細・金額・備考・カスタム項目・請求アカウントなど、ウィザードで扱う項目すべて
- 版番号（Version）はコピー元を引き継がず、**通常の新規作成と同じ採番**（New=1、それ以外は最新 Ordered+1）
- New コピー: 契約サービスを新規化（Lifecycle は載せない。再受注で再判定）
- Change／Renew／Cancel／Add コピーおよび編集: 同一契約サービスを維持し、preset にその `Lifecycle__c`（Term / Spot）を載せる。画面 Step1 の操作制限に使う

### 4.9 更新商談の自動 Renew 見積

- 商談 `RenewEstimateAutoCreateCheck__c` を **OFF → ON に更新したときだけ**自動作成する
- **商談の新規作成時には作らない**（作成時点からチェックONでも、このトリガでは作らない）
- 元は前回商談（`PreviousOpportunity__c`）の **Ordered** 履歴。Estimate／Archive は不可
- 前回の最新 Ordered が **Cancel** の場合は作らない（手動 Renew と同じ。Cancel 起点の更新見積は不可）
- **都度契約（Spot）および Type=Add のソースでは作らない**（手動の更新商談作成と同じ。チェック OFF→ON はエラー）
- 同じ商談にすでに Renew の Estimate があっても、再度 OFF→ON すれば **もう1件作る**（スキップしない）
- 商品も手動 Renew と同じ: Ordered 期間終了日に届く継続課金・**数量>0**・Type が Remake／New／Renew（または空）だけを1年延長で作成。**継続課金かどうかは明細 `BillingType__c` が正**（空なら Product2）。**Change の Original（打消し行）は引き継がない**。一回課金は載らない（必要なら後から New で追加）。対象明細が0件ならチェック OFF→ON はエラー
- **単価0／Amount0 も数量>0 なら載せる**（§4.4 Renew 引継ぎと同じ。無料提供を落とさないための意図的仕様）。期中停止後の単価0が自動 Renew に出ても不具合ではない。不要行の削除は見積を開いてゴミ箱（自動作成だけでは削除 UI が走らない）
- 期間終了 = 開始から12サイクル目の終了日（`endDateForMonthlyCycles(開始, 12)`）
- 自動作成時点で見積商品 `Amount__c` に **数量×単価×月数（整数円）** をセットする（ウィザード未保存のまま受注しても見積正本が空にならない。単価0なら Amount0）
- **受注自体は手動**（自動更新＝自動受注ではない）。0円行を残したくない場合は受注前に見積編集で削除する
- 受注前ガード: 数量 ≠ 0 なのに `Amount__c` が null の見積商品がある見積は受注不可（「見積ウィザードで保存してから受注してください」）

### 4.10 見積 PDF

- **Estimate のみ**表示・発行可（Ordered／Archive は Dynamic Actions 非表示に加え、`EstimateDocumentService` でも拒否。URL 直叩き不可）
- Change 明細のうち課金イベントがない系統は除外して出力
- 合計は契約履歴の発生金額（`DeltaAmountSum__c` = 見積商品 Amount の積み上げ）を用いる
- **税込の正**はウィザード詳細情報・請求ヘッダと同じく、**PDF 掲載明細の税抜合計 × 税率を1回切り捨て**（グループごと切り捨て→合算はしない）。御見積金額＝その税込
- **カテゴリ／商品グループの税込**は、上記総額税を税抜比で按分した表示（最後のグループで端数吸収）。グループ税込の合計＝御見積金額
- **税率は契約サービス `TaxPercent__c` のみ**（§4.6。`fromPercentFieldStorage` → `resolveTaxPercent`）。`EstimateSetting__c.Tax__c` はレイアウト文言用であり税率計算に使わない
- 発行時は PDF を契約履歴に Files として保存する。可視性は **AllUsers** でよい
- **発行操作で見積日・発行日を自動セットしない**（空なら空のまま。手入力またはテナント側自動化に任せる）
- 会社名・住所・プライバシーポリシー URL はテナント別カスタム（コア業務ロジック外）

### 4.11 見積備考

- 見積備考は `EstimateNoteMaster__c` 選択が基本。マスタなしの自由文（`Note__c`）だけでも保存可
- Step2（詳細情報）でマスタ選択／備考テキストの編集あり（マスタ選択時の上書き確認など）
- **最大長**: `ContractHistory__c.Note__c` の項目長（現行メタデータ **32768** 文字。項目長変更時は Describe に追随）。超過分は保存時に**黙って切ってよい**（エラーにしない）
- **自由文のクリア**: 保存ペイロードの備考テキストが空／未指定のとき、`Note__c` は **null クリア**する（画面で消して保存したのに残らないようにする）
- **Cancel では備考編集 UI を出さない**（§4.4）。保存時も **`EstimateNoteMaster__c` / `Note__c` は常にクリア**（ペイロードにマスタ ID や文言があっても書かない／残さない。Cancel に備考マスタは登録されない）

### 4.12 見積商品金額

#### 桁数・丸め（全層共通）

| 項目 | 桁 | 丸め | 適用箇所 |
| ---- | -- | ---- | -------- |
| **数量** | 小数第2位まで | 四捨五入（Apex `RoundingMode.HALF_UP` と同一。LWC は十進文字列／整数スケールで実装し、`Math.round(n×100)` は使わない） | ウィザード入力・見積商品／請求商品 `Quantity__c`（scale=2）。画面計算・保存前に必ず丸める。数量 input は `min=0.01` / `step=0.01`（時間単価などの小数数量を入力可能にする） |
| **単価** | 小数第2位まで | 同上（`HALF_UP`） | ウィザード入力・金額からの逆算、見積商品／請求商品／商品マスタ `UnitPrice__c`（いずれも scale=2） |
| **金額（税抜）** | **整数円** | 四捨五入（同上。数量×単価×月数は浮動小数乗算せず、数量・単価を小数2桁の整数化してから乗算し整数円へ `HALF_UP`） | ウィザード金額入力・数量×単価（×月数）の計算結果、見積商品／請求商品 `Amount__c`（scale=0）、請求プレビューの金額表示 |
| **税額** | 整数円 | **切り捨て**（`RoundingMode.DOWN` / `Math.trunc`） | 見積表示・請求マージ単位（§6.10） |

- 海外レート換算などで単価に小数が必要な場合は単価側に持たせる。金額（総額）を小数にする運用はしない
- **IEEE754 対策（ウィザード）**: `15×33.3` や `1.005` のように2進浮動小数で境界がずれる値でも、十進の `HALF_UP` 結果（例: 500 円・単価 1.01）になること。実装は `estimateLineItemUtils`（`roundHalfUp`／`yenFromQuantityUnitPrice`）
- `Amount__c` は **見積ウィザード Step2（詳細情報）でユーザーが見て確認した金額をそのまま保存**する（画面表示と DB が一致すること。いずれも整数円）
- 画面計算: 継続=数量×単価×月数／一回=数量×単価／Original=符号反転。結果は整数円に四捨五入（**一括丸め**）
- **請求再生成**: 継続は各月 `roundYen(数量×単価)` を月数回足す（**月次丸め**）。一括丸めと月次丸めは小数単価で一致しないことがある（例: 単価 33.33・12ヶ月 → 見積 400／請求 396。単価 33.3・数量 15・12ヶ月 → 見積一括 5994／月次 `round(499.5)×12`=6000）
- **端数警告（請求プレビューに載るずれのみ）**: 見積確定金額 ≠ 請求再生成見込み（月次丸め合計）でも、**この Version の受注後に請求プレビューへ載り得る明細**だけを警告する。金額列下に「請求時」合計と差分を出し、該当行が1件以上あるときヘッダでも案内する。計算自体は変えない。請求の正は単価
  - **New / Renew**: ギャップがある明細は従来どおり警告
  - **Change**: **New（追加行）** と **課金イベントあり Remake** のみ。**Original** および **据え置き Remake**（内容同一・途中開始なし・終了延長なし）は差分請求が生まれないため警告しない（行単体の一括/月次ギャップがあっても出さない）
- **請求基準（Step2 明細表示）**: 請求設定ごとの請求基準日（または月次分割の回数表示）を明細に出す。**請求書の請求日そのものではない**（受注後に請求先の請求日ルールで請求日が決まる）。算出定義は保存時 Apex `InvoiceAnchorDateUtil` と同定義（LWC `resolveInvoiceAnchorFields`）
  - **New / Renew**: 請求設定があれば表示
  - **Change**: **New（追加行）** と **課金イベントあり Remake／Original** のみ表示。**据え置き Original／Remake**（内容同一・途中開始なし・終了延長なし＝端数警告と同じ課金イベント定義）は **表示しない**（一回課金 New 追加のみの期中 Change などで、据え置き継続課金に有効日が載って違和感が出るのを防ぐ）
- **数量 ≠ 0 なのに Amount が null／計算不能**の明細は、**画面・Apex とも保存エラー**（「金額を計算できません…」相当）
- **Change の Original 行は単価・金額・数量・期間・請求設定などすべて変更不可**（金額入力モードにもしない。表示用の符号反転のみ）
- 手入力金額（`amountEntryMode`）は **Original 以外**の正式仕様。詳細は次のとおり（§4.15.4 も参照）
  - **金額入力に切替**: 単価欄をロックし、表示金額から単価を逆算する
  - **逆算の除数**: 継続課金 = 数量 × 月数／一回課金 = 数量のみ。結果は **小数第2位まで四捨五入**
  - 金額入力値は **整数円に四捨五入**してから保持する（小数の総額入力はしない）
  - 数量・期間など構造が変わっても手入力金額は維持し、単価だけ再計算する
  - 逆算できない（数量またはサイクル数が 0 等）場合は保存エラー
  - **単価入力に戻す**: 手入力金額は破棄し、通常の単価→金額計算に戻る
  - 手入力金額を `Amount__c` に保存しても、請求商品は常に数量×単価（月次行は整数円四捨五入）で再計算する（§6.5）。端数警告は上記「請求プレビューに載るずれのみ」ルールに従う
- Apex／Trigger による数量×単価への再計算上書きはしない（ウィザード保存の Amount を残す）。保存時に数量・単価 scale=2・金額 scale=0 へ四捨五入する防御のみ行う
- 発生金額 `DeltaAmountSum__c` は Amount の積み上げ要約

### 4.13 見積商品の取引先

- `Account__c` は契約サービス（＝商談取引先）から Trigger で自動セットする

### 4.14 契約履歴の削除

- 標準 UI 等からの Estimate 削除は許容する
- **ロック済み請求がある履歴は削除不可**（行単位。`InvoiceLockUtil`）
- ロックが無ければ、紐づく請求（`Invoice__c`）・期間明細を先に削除してから履歴を削除する（請求は契約履歴の Master-Detail でも明示削除し、ロック判定と掃除順を制御する）
- **一括削除**でロックあり／なしが混在しても、ロック行だけ拒否し、**未ロック行の請求掃除は続ける**（部分成功時に履歴だけ消えて請求が残るのを防ぐ）
- （通常、未受注の Estimate に請求は無い。受注後は Ordered。防御的ルール）

### 4.15 クライアント処理（見積ウィザード）

画面（LWC）側の状態管理・同期・自動セット・操作補助。業務ルール本体は §4.0〜§4.14。ここでは **画面がどう動くか** を正本化する。

#### 4.15.1 状態の単一ソースと破棄集合

- ウィザードの業務データは親コンポーネントの **単一状態** に集約する。子 Step は表示・入力を担い、変更は親へ通知する
- 書き換えは名前付き遷移のみ（呼び出し側での場当たりマージはしない）
- **種別変更で初期化する項目**: 契約サービス名／ID、契約履歴名／ID、期間・有効日、Version 関連、前回期間、商品明細、備考、請求アカウント、サービス／履歴の追加項目、追加項目パネル開閉 など（商談名・取引先名は商談由来のため残す）
- **契約サービス変更で初期化する項目**: **契約履歴名**、期間・有効日、前回期間、商品明細、備考、履歴追加項目、**サービス追加項目**、契約履歴 ID／Version／renewEligible など。追加項目パネルは **開いた状態**で開始する
- **契約履歴だけ変わったときも同様に契約依存は全部消す**（**サービス追加項目・契約履歴名も含む**。§4.0.3）
- 契約サービス選択時は **選択の瞬間に**上記を破棄し、履歴読込を開始する。読込応答には連番を付け、**古い応答は捨てる**（画面と内部状態の食い違い防止）
- 切替直後は契約履歴 ID が一時的に空になる。詳細情報パネル（非表示中含む）は **履歴読込中は「契約履歴未設定」エラーにせず待ち**、読込完了（連番一致の SUCCESS／FAILURE）後に明細を再ブートストラップする
- **契約履歴名の編集元は Step1（契約の特定）のみ**。詳細情報は履歴名を親へ書き戻さない

#### 4.15.2 Step のマウント維持と離脱禁止

- Step1 では基本情報パネル（種別＋契約特定）を表示する。一度到達した **詳細情報パネル**は DOM を破棄せず **CSS 非表示で保持**する（戻っても入力・明細編集状態を維持する。§4.0.2）
- 表示中でなくても、種別・契約サービス・契約履歴・履歴読込中フラグの身元（`種別|サービスID|履歴ID|loading|ready`）が変わると詳細情報は **裏で再初期化**し、親へ明細・期間を書き通す（次に詳細情報を開いたときは新しい中身）
- 次のいずれかの間は「次へ」「保存」および前方 Step 移動を不可とする
  - 編集／コピーのプリセット読込中
  - 契約履歴読込中
  - 詳細情報の明細／期間ブートストラップ中
  - 保存中
- **プリセット読込中の入力ロック（必須）**: 編集／コピーの preset 読込中は、次へ／保存だけでなく **本文フォームの入力も不可**（読込完了時の無言上書きを防ぐ。閉じるは可）
- **読込中フラグの解除（必須）**: 詳細パネルが DOM から外れるとき（種別変更で `step3Mounted=false`、コンポーネント disconnect 等）は、親の「詳細情報更新中」フラグ（`loadingStep3`）を **必ず false に戻す**。読込中に「前へ→種別変更」しても次へ／保存が永久に不可にならないようにする
- 告知バナー（公式）:
  - 契約履歴読込中: 「契約履歴を読み込んでいます。完了するまで次のステップへ進めません。」
  - 詳細情報更新中: 「商品明細を更新しています。完了するまで『次へ』『保存』はできません。表示内容が確定したあと、その内容が保存されます。」
  - 編集／コピー preset 読込中: 「見積内容を読み込んでいます...」

#### 4.15.3 保存・確認の順序

- 詳細情報から戻る／保存する直前に、画面上の値を **親状態へ強制同期（flush）** する。送る範囲: **期間開始／終了／有効日、前回期間、備考マスタ／備考文、全明細行、契約サービス／履歴の追加項目**（金額モード含む業務フィールド。見た目専用は送らない。**契約履歴名は送らない**）
- 保存の順番: **flush →（Change の同 Product2 New 確認）→ 詳細情報の検証 → 保存**
  - 確認で続行したあとも同じ経路
  - flush の同期イベントで確認スキップが落ちないこと（続行後に同じ確認が再表示されないこと）
  - 明細内容が変わったら確認スキップはリセットする
- Step1→2: 種別・契約の特定・履歴名などを検証。**追加項目の必須は見ない**
- Step2 保存: 期間・商品に加え、**表示中のサービス／履歴／明細追加項目の必須**を検証（**Cancel も契約カスタムの必須は検証**。備考・商品明細は Cancel では対象外）
- 備考マスタの上書き／解除確認は子が親の確認 UI に依頼し、続行／取消で解決する（§4.0.5）。親は確認モードを排他管理する
- Ordered の見積編集（§4.0.7）: 検証・保存対象は **表示中のウィザード追加項目のみ**（実質 Step2）。期間・商品ルールの検証は走らない

#### 4.15.4 金額入力モード（画面）

§4.12 の補足。**Original 行には出さない**（単価・金額とも変更不可）。

| 操作                           | 動き                                                                    |
| ------------------------------ | ----------------------------------------------------------------------- |
| 金額入力に切替                 | `amountEntryMode=true`。単価ロック。表示金額から単価逆算                |
| 逆算                           | **継続**: 金額 ÷（数量×月数）。**一回**: 金額 ÷ 数量。小数第2位四捨五入 |
| 金額変更                       | 入力値を整数円に四捨五入したうえで単価を再逆算                          |
| 数量／期間変更（金額モード中） | 手入力金額（整数円）は維持し、単価だけ再計算                            |
| 単価に戻す                     | 手入力金額破棄。通常の単価→金額                                         |
| **商品差し替え／クリア**       | **金額入力モードを必ず解除**（`amountEntryMode=false`・`manualAmount` 破棄）。新単価から金額を再計算する。旧手入力金額を残さない |
| 単価手入力                     | 小数第2位まで四捨五入（海外レート換算などを想定）                       |
| 数量手入力                     | 小数第2位まで四捨五入（`parseQuantityInput`／`roundQuantity`）。計算・保存前に必ず正規化。入力 UI は `min=0.01` / `step=0.01`（整数 `step=1` に固定しない） |
| **商品選択の非同期適用**       | 行ごとに選択リクエスト連番を持ち、**より新しい選択／クリアが始まったあとに返ってきた古い `getProductDefaults` 応答は捨てる**（遅い応答の後勝ちで別商品・単価が載らない） |

- `amountEntryMode` と手入力金額は **親のウィザード状態に残す**（基本情報⇔詳細情報の往復でもモード維持）。見積商品の DB 列にはしない。**ただし商品選択の変更時は上記のとおり必ず解除する**
- **請求時差分表示（請求プレビューに載るずれのみ）**: 見積確定金額 ≠ 請求再生成見込み（継続は `roundYen(数量×単価)×月数`）のとき、**請求プレビューに載り得る明細**について金額列下に **請求時合計と差分**を表示する。金額入力（例: 入力 9,657,000 → 請求時 9,657,050・+50）だけでなく、単価入力の小数単価による一括丸めギャップ（例: 単価 33.33・12ヶ月 → 見積 400／請求時 396・−4）も対象。Change の Original／据え置き Remake は対象外（§4.12）。見積の保存額は画面確認値のまま、請求・プレビューは数量×単価（月次）側になることを明示する
- バッジ・可否フラグ・表示用ラベル等の見た目専用プロパティは親／保存ペイロードに送らない（§4.15.10）

#### 4.15.5 日付ショートカットとコピー

- **±1年／±1ヶ月**
  - **ヘッダー**: **期間終了日だけ**動かす（期間開始日は動かさない）。終了が空なら期間開始を基準にして埋めてよい
  - **明細**: 開始日用・終了日用それぞれに効く
  - 対象欄が空のときの基準（フォールバック）:
    - 明細開始: `開始 → 終了 → ヘッダー開始 → ヘッダー終了`
    - 明細終了: `終了 → 開始 → ヘッダー終了 → ヘッダー開始`
  - **開始日**の ±: 元日が**月初（1日）なら結果も月初、月末なら結果も月末**に寄せる（sticky）。例: 1/31 → +1ヶ月 → 2/28（または 2/29）→ +1ヶ月 → 3/31
  - **終了日**の ±: 暦 sticky ではなく、**開始日起点のサイクル数 ±N**（±1ヶ月=+1サイクル、±1年=+12サイクル）。`adjustMonthlyEndByCycles`
- デフォルト「1年」および金額・回数の月数は `endDateForMonthlyCycles` / `countMonthlyCycles` のみ。終了日を長く正規化して回数を作らない
- 「上の行から日付コピー」: 直上の**編集可能行**（読み取り専用をスキップ）から開始／終了／両方をコピー
- 「ヘッダー期間を明細へ」: 契約ヘッダーの開始日／終了日を当該明細へ流し込む（開始・終了は別操作でよい）

#### 4.15.6 カスタム項目（画面）

- 契約サービス／契約履歴／見積商品のカスタム項目は **すべて Step2（詳細情報）** に置く（Step1 には出さない）
- パネル表示名は「契約のカスタム項目」「商品のカスタム項目」（明細側トグル）
- 契約サービス／履歴カスタムは **New／Change／Renew／Cancel で同じロジック**（ShowOn*／Visibility に従い編集可・**Required なら必須検証（未入力エラー）**・保存）。パネル表示は商品明細がある種別では備考と同じ条件。**Cancel はカスタムのみ表示**（備考なし）。Ordered 編集は例外
- 契約サービス／履歴の画面値同期も商品と同じ `sync`（ShowOn* 非表示は prune、再表示は Default 再投入）
- 契約サービス／履歴のカスタム項目パネル開閉は親状態に保持する（**1トグル・合計件数**）。備考パネル開閉も同様。明細行のカスタム項目一括開閉は詳細情報ローカルのみ（保存ペイロード外）。トグルは各パネルヘッダ左側
- Visibility／ShowOn* の解釈は §2.1。**表示中かつ Required__c の項目は Cancel を含む全種別で絶対必須**

#### 4.15.7 請求設定の画面正規化

- 明細の請求設定候補は課金種別で絞る
- 一回課金で月次分割は選べない
- **商品差し替え時**は新商品マスタのデフォルト請求設定へ差し替える（§6.6）
- 不整合な選択は **エラーで止める**（候補先頭などへ黙って置換しない。ユーザー変更・行再描画・商品選択いずれも同じ）
- 請求設定が空のときだけ、課金種別に合うデフォルトを埋めてよい

#### 4.15.8 編集／コピーのプリセット読込

- 同一の編集元／コピー元キーについて、成功済み・失敗済みなら **自動再読込しない**（`renderedCallback` ループ防止）
- 失敗時は初期状態に戻し、エラーを表示する。画面に **「再読み込み」** を出し、手動で失敗キーをクリアして再取得できる
- 業務内容の初期セット範囲は §4.7／§4.8
- Change／Renew／Cancel／Add の編集・コピーでは preset に `serviceLifecycle` を含める。画面の操作制限（Spot=Add のみ等）はこれを正とする。候補一覧 wire からも空のときだけ補ってよい（サービス再選択はしない）

#### 4.15.9 Change 起動時の明細生成（画面）

- 前回 Ordered の**継続課金**（カバー対象）ごとに、**変更前（Original・完全読取専用）＋ 変更後（Remake・編集可）の2行セット**を生成する。継続課金かどうかは明細 `BillingType__c` が正（空なら Product2）
- 画面では商品名（または「新しい商品」）のグループヘッダーのみ。但し書きは出さない。種別バッジは **Original／Remake／New**。セット間は縦罫線ではなく、ヘッダー背景・Original行の帯色・余白で区別する。行番号は Original も含めて連番
- 初期値（商品・数量・単価・期間・請求設定）はセット内で同じ。**カスタム項目は Remake のみ前回からコピー**（Original には載せない・UI も出さない）
- **系統は DB に永続**する（`PreviousContractProduct__c`／source）。画面の `pairId` はグループ表示用の一時キーでよいが、保存・再編集後も同じ系統として再構成できること
- 照合元（前回明細）は画面内に保持し、Original 一致検証等に使う
- 一回課金は自動では出さない（必要なら Type=New で追加）
- 引継ぎ不可（`renewEligible=false` または継続課金ゼロ）のときは明細を空にし、作成不可を示す

#### 4.15.10 表示専用フィールドと画面持ち越し

- バッジ・可否フラグ・表示用金額ラベル等は詳細情報の表示専用。親状態および Apex 保存ペイロードには **業務フィールドのみ**送る
- `productVisibilityContext` は **画面の出し分け用**に持ってよい（保存リクエストに含めてもよい）。見積商品の DB 列としては保存しない
- 保存・必須検証・適用では Apex が **常に Product2 から再構築**する（§2.1・§4.7）。画面メモが空でも古くても信じない。条件を満たす項目を誤ってクリア／必須スキップしない
- `amountEntryMode`／手入力金額は親状態に残してよい（§4.15.4）。DB 列にはしない

#### 4.15.11 オープン時は常に最新内容

見積ウィザード（新規／編集／コピー）は **開いた瞬間のサーバ最新** を表示する。ページをリロードしなくても、直前の操作や他ユーザー更新を取りこぼさない。

| 対象 | 方針 |
| --- | --- |
| 契約サービス／請求アカウント候補 | `@wire` + `cacheable` だが、パネルマウント時に **必ず `refreshApex`**。種別変更時は契約特定パネルを **作り直す**（自動選択フラグ等のローカル状態も捨てる） |
| Edit／Copy preset、前回履歴・商品、商品デフォルト、備考マスタ文言 | Apex を **非 cacheable**（imperative 都度サーバ）。オープン時はウィザード状態を初期化し preset を再読込 |
| 請求設定マスタ・追加項目定義・商談デフォルトコンテキスト | `@wire` をオープン時に `refreshApex` |
| `getRecord`（商談／契約サービス／税率等） | オープン／パネルマウント時に `getRecordNotifyChange` |
| 商品 record-picker の検索候補 | UI API／検索インデックス依存。開き直しで最新に近づける（インデックス遅延までは保証外） |

- オープン処理（`beginFreshContentSession`）: 確認ダイアログ・保存成功フラグ・検証アラートをクリアし、契約特定パネルを remount する
- 古い preset 応答はセッション連番不一致なら捨てる

### 4.16 パッケージ LWC 全体の表示鮮度

パッケージ内の **すべての画面 LWC**（見積／受注／請求プレビュー／差し戻し／請求オペレーション等）は、**開いた・表示した時点のサーバ最新** を正とする。クライアント Apex キャッシュや同一 recordId の再利用ロードで古い候補・一覧・プレビューを出さない。

| 画面 | 方針 |
| --- | --- |
| 見積ウィザード | §4.15.11 |
| 受注ウィザード | 接続のたびにロード状態をリセットして `getOrderContext` を再取得。請求ステップの wire はマウント時 `refreshApex` |
| 請求プレビュー | 接続のたびにプレビュー／請求先候補を再取得。業務読取 Apex は **非 cacheable** |
| 差し戻し | 接続のたびにコンテキスト／手修正有無を再取得。判定 Apex は **非 cacheable** |
| 請求オペレーション（`invoiceOpsPanel`） | `getInvoices` は **非 cacheable**。recordId 変更・再表示でも一覧再取得。**操作日の初期値はブラウザローカル暦日**（UTC の `toISOString` は使わない。JST 早朝に前日が入るのを防ぐ）。**recordId 変更時は選択をクリア**し、操作対象 ID は表示中行に限定（別履歴の請求を誤操作しない） |
| 設定系 `@wire`（CMDT／項目定義等） | `cacheable` 可だが、画面マウント時に `refreshApex` |

保証外: `lightning-record-picker` 等の UI API／検索インデックス遅延。

### 4.17 同時編集ガード（楽観ロック）

複数ユーザーが同じ契約履歴／請求を開いたまま保存すると、**後勝ちで内容が消える**のを防ぐ。開いた時点の `LastModifiedDate` トークンを画面が保持し、保存直前にサーバ実値と突き合わせる（`ContractOptimisticLockUtil`）。

| 操作 | トークンの対象 | 不一致時 |
| --- | --- | --- |
| 見積編集保存 | `ContractHistory__c.LastModifiedDate`（preset / 保存結果で更新） | エラー。開き直し |
| 受注確定 | 同上（`getOrderContext.lastModifiedToken`） | エラー。開き直し |
| 差し戻し | 同上 | エラー。開き直し |
| 請求プレビュー更新（金額／日付／分ける・移す・分割等） | 契約サービス配下 Invoice の `MAX(LastModifiedDate)`（`contentVersion`） | エラー。プレビュー再読込 |

- トークン未指定（Apex 直呼びテスト等）は互換のためスキップ可。**LWC からは必ず送る**
- 同刻保存は先勝ち・後は拒否（両方成功して混ざることはない）
- 文言例: 「他のユーザーが先に更新しました。画面を開き直してから再度操作してください。」

## 5. 受注・差し戻し・ステータス

### 5.1 権限

- **受注**: カスタム権限 `Contract_09_Can_Order`（PS `Contract_09_Order`）が必須
- **差し戻し**: カスタム権限 `Contract_10_Can_Revert`（PS `Contract_10_Revert`）が必須
- **強制箇所（正）**: `ContractHistoryTrigger`（before insert / before update）
  - `historystatus` が **Ordered になる**（Estimate→Ordered、Ordered のまま insert 等）→ `Contract_09_Can_Order` が無ければエラー
  - **Ordered → Estimate** → `Contract_10_Can_Revert` が無ければエラー
  - ウィザード／標準 UI／API／Data Loader など **更新経路を問わず**同じ
- 受注・差し戻しウィザード（`OrderCreateController`）でも同じカスタム権限を事前チェックする（UX 用）。最終ガードはトリガ
- **請求Ops（連携・消込）**: カスタム権限 `Contract_13_Can_Manage_Invoice_Ops`（PS `Contract_13_Manage_Invoice_Ops`）が必須。`InvoiceOpsController` / `invoiceOpsPanel` の入口で強制。今後の消込・連携運用も 13 に寄せる
- 整合性バイパス `Contract_99_Can_Bypass_Integrity_Guards` は **09 / 10 / 13 を解除しない**。**99 は例外処理専用**（通常業務の連番には使わない）
- 加えて `#99` でも **解除しない**ステータス遷移（トリガで常時拒否）:
  - **Ordered → Archive**（差し戻しは Estimate へ。Archive 直変は請求 purge と First/Latest ずれの事故元）
  - **Archive からの離脱全般**（Archive → Ordered / Estimate 等。Ordered へ戻しても請求は再生成されない）
- `#99` が外せるのは主に **ロック済み請求の更新・削除**など。**通常は付与しない**
- **請求プレビューでの例外編集**には `Contract_12_Can_Edit_Invoice_Preview`（受注権限とは別）
- オブジェクト CRUD／FLS の付与は導入先の権限設計に従う。パッケージが保証するのは上記カスタム権限の業務ガード

### 5.2 受注（Estimate → Ordered）

前提（`ContractOrderValidationService`。**受注ボタンもステータス直接変更も同一**）:

- 契約サービスに請求先が紐づいていること
- 請求先マスタ上、必須項目（宛名・メール To・支払条件・請求日ルール）が埋まっていること
- New／Change／Renew は見積商品1件以上が必要。数量 ≠ 0 なのに `Amount__c` が null の行があれば受注不可
- Cancel は見積商品ゼロのままで受注可（契約期間明細・請求は作らない）。請求先必須は Cancel も同じ
- **強制箇所（正）**: `ContractHistoryTrigger`（before insert / before update）で `historystatus` が Ordered になるとき
  - ウィザード（`OrderCreateController.confirmOrder`）も同じサービスで事前チェック（UX 用）
  - 標準 UI／API／Data Loader で直接 Ordered にしても同じエラーで止まる
  - 商品・Amount 検証は履歴 Id 確定後に行う（通常の受注は Estimate→Ordered 更新）。before insert 時点では請求先検証のみ
  - `Contract_09_Can_Order` が無い場合は権限エラーを優先し、受注前提検証は走らせない（二重 addError による文言上書き防止）
- 受注ウィザードは請求先を **参照のみ**。任意表示: メール Cc／Bcc、土日を営業日にずらす（編集不可）
- 必須項目が不足している場合: 受注不可。取引先の関連リストで請求アカウントを編集するか、新規作成して見積で付け替える
- **受注ウィザードに履歴備考（`Note__c`）は出さない**。項目定義にも持たない
- **Cancel の受注 UI** は差し戻し／Archive と同型の小さい確認ポップアップ（`confirm` サイズ）。請求アカウント設定・更新商談作成チェックは出さない（サーバ側の請求アカウント必須検証は維持）
- 画面起動時: **Archive は受注不可**。すでに **Ordered** の履歴も受注不可（請求プレビュー／差し戻しへ誘導）

#### 5.2.1 請求アカウントの編集導線

- 作成・編集の正は取引先関連リスト／標準レイアウト
- 受注ウィザードに「保存して閉じる」は持たない（請求先マスタは更新しない）
- 受注確定時も BillingAccount マスタは更新しない。その時点のマスタ値を **請求（`Invoice__c`）の SnapShot** にコピーする

#### 5.2.2 共有マスタ更新ガード

- BillingAccount は共有マスタ。複数契約サービスから参照され得る
- 参照先契約サービス配下に Ordered 履歴が1件以上ある状態で、確認チェック（`ConfirmSharedUpdate__c`）以外の項目を変更して保存する場合、確認チェック必須
- エラー文言: 「受注済み契約で使用中です。上書きすると今後の請求先が変わり、他契約にも影響します。同じ請求先として更新する場合は確認チェックを入れて再保存、契約ごとに分けたい場合は新規作成してください。」
- 保存成功後、確認チェックはクリアする（次回も再確認）
- 標準編集・関連リスト・API など、保存経路すべてでサーバ側（before update）が効く

処理（受注確定）:

1. 受注前提を検証（`ContractOrderValidationService`。請求先・商品・Amount、**同一契約サービスに同じ Version の Ordered が無いこと**、および Change の **請求設定だけ変更の受注禁止**（§4.4.2）。不足なら受注不可）
2. ステータスを Ordered（トリガでも同検証・09 権限を再強制）
3. **二段生成**（Cancel は行生成をスキップ。既存孤児があれば削除し空の正本 rebuild のみ）:
   1. 契約期間明細を生成（期間分解・Change 差分）※Cancel はここを通らない
   2. 現行プレビューと同じ集約ロジックで `Invoice__c` / `InvoiceLine__c` を生成し、その時点の BillingAccount を請求ヘッダへ SnapShot
4. 同一契約サービス上、Version が今回以下の他 Estimate を Archive（勝ち残った Ordered 以外。同 Version の二重 Ordered は手順1で既に拒否）
5. First／Latest Ordered を同期
6. 「更新商談を作成する」が ON のとき（Cancel では非表示）、`RenewOpportunityCreateService.createFromOrderedHistory`（§2.3）。失敗時は受注全体ロールバック

#### 5.2.3 更新商談作成チェック（受注ウィザード）

- Cancel 以外で表示（Cancel 画面自体が確認ポップアップのため非表示）。**初期値は常に ON**
- ヘルプ文言: 「受注後、期間終了に向けた更新商談を自動作成します。」（Cancel 向けの括弧注記は出さない）
- 既に紐づく更新商談があっても ON なら **作り直し**（旧紐づけ解除＋新規。旧商談は残す）
- 入口: `OrderCreateController.confirmOrder(..., createRenewOpportunity)`（**フラグは呼び出し側で必須**。省略して false になる旧 overload は持たない）

### 5.3 差し戻し（Ordered → Estimate）

- 起動すると確認画面を表示する（`orderRevertRecordAction` / `orderRevertWizard`）。文言を確認のうえ **「Estimate に差し戻す」** で確定、**「キャンセル」** で閉じる（Archive と同様、システム Confirm ダイアログには依存しない）

前提:

- **最新 Ordered であること**: 同一契約サービス上の Ordered のうち **`Version__c` が最大**であること（Apex がその場で集計して判定。後続 Ordered がある場合は差し戻し不可）
  - 判定の正は Version 実体。`ContractService__c.LatestOrderedHistory__c` ポインタは使わない（ポインタずれで古い Version を誤って差し戻したり、最新が差し戻せなくなったりするのを防ぐ）
  - `LatestOrderedHistory__c` は First／Latest 同期の表示・参照用キャッシュとして維持する
- 同一契約サービスに、**自分より新しい Version の Estimate がない**こと（Apex 判定。こちらも Version 比較）。ある場合は差し戻し不可。先に後続見積を Archive してから差し戻す
- 当該契約履歴（Version）にロック済み請求（`Invoice__c`）が1件でもある場合は差し戻し不可（Apex）
- カスタム権限 `Contract_10_Can_Revert` 必須（§5.1。トリガで強制）
- 手動調整済みの請求があっても差し戻し自体は可。ただし画面内に **「手動調整した請求も削除されます」** を表示し、文言確認のうえ **「Estimate に差し戻す」** で確定する（Archive と同様、システム Confirm ダイアログには依存しない）

処理:

- ステータスを Estimate
- その履歴の契約期間明細・請求・請求明細を **すべて削除**（ロックなし前提。ロックがあれば before で弾く）
- First／Latest Ordered を再同期
- 紐づく更新商談があり「更新商談を削除する」が ON なら削除（失敗時は差し戻し全体ロールバック）
  - **更新商談の削除は差し戻しウィザード（`OrderCreateController.revertOrder`）限定**。トリガでは行わない
  - 標準 UI・Data Loader・Anonymous Apex 等で `historystatus__c` を直接 Estimate に戻した場合は、請求 purge / First・Latest 再同期はトリガで走るが **更新商談は残してよい**（意図的。請求誤生成のような致命影響はない。再受注時に作成 ON なら §5.2.3 の作り直しで紐づけを付け替える）

#### 5.3.1 更新商談削除チェック（差し戻しウィザード）

- 紐づく更新商談があるときのみ表示。**初期値は常に ON**
- OFF なら商談・紐づけとも残す。その後再受注で作成 ON なら作り直し（§5.2.3）
- 入口: `OrderCreateController.revertOrder(..., deleteRenewOpportunity)`（**フラグは呼び出し側で必須**。省略して false になる旧 overload は持たない）
- ウィザード以外の Ordered→Estimate では本チェックは出ない／削除もしない（§5.3 処理の注記どおり。許容）

後続 Estimate を残したまま差し戻すと、中間 Version を飛ばした受注になり得るため、差し戻し側で止める。

### 5.4 Archive

- 手動 Archive（契約履歴の **Archive** ボタン）: **Estimate → Archive のみ**許可
- 起動すると確認画面を表示する（`estimateArchiveRecordAction`）。文言を確認のうえ **「アーカイブする」** で確定、**「キャンセル」** で閉じる（システム Confirm ダイアログには依存しない）
- 確定時のみ `EstimateArchiveController.archiveEstimate` でステータス更新（ステータス値は `Archive`）
- Ordered／Archive からは手動アーカイブ不可（Apex で弾く。ボタンも Dynamic Actions で非表示）
- 受注時の自動 Archive: 受注した Version 以下の他 Estimate を Archive（§5.2）
- Archive からはどのステータスへも復活不可（`Contract_99` バイパスでも不可。§5.1）
- **Ordered → Archive** も `Contract_99` バイパスでも不可（差し戻すなら Estimate へ）
- Archive 後は編集・受注・コピー・見積書発行・差し戻し不可（Dynamic Actions でも非表示）

### 5.5 契約サービス同期

- FirstOrderedHistory = Ordered のうち Version 最小
- LatestOrderedHistory = Ordered のうち Version 最大
- **Ordered の契約履歴が1件でもある**契約サービスは削除不可（判定の正は実レコード。`LatestOrderedHistory__c` ポインタが空でも Ordered が残っていれば削除不可）
- 加えて、配下にロック済み請求が残る契約サービスも削除不可（防御。通常は受注しないと請求が無いため実運用では稀）
- New で作った契約サービスの取引先（Account）は、以後の Change／Renew／Cancel で変更しない
- 契約サービスの開始日〜終了日（数式）:
  - `ServiceStartDate__c`（表示名: サービス開始日）= First Ordered の期間開始日
  - `ServiceEndDate__c`（表示名: **最新契約終了日**）= **最新 Ordered の期間終了日**
  - **Cancel 受注後も数式は変えない**。Cancel の期間は解約日1日（前回終了の翌日）なので、本項目は **解約日（Churn 日）** になる
  - **最終利用日／契約満了日は直前履歴の終了日**であり、本項目とは別。Cancel＝翌日扱い（最終日まで契約中）の仕様どおりで、日付が1日先になるのは不具合ではない
  - 解約済判定の正は `Status__c = Cancelled`（LatestOrdered の Type=Cancel）。終了日の当日比較では解約済にしない
- `Status__c` は LatestOrdered と Lifecycle／終了日からの数式（未受注は空 / Spot=`SPOT` / Cancelled / OutOfTerm / InTerm。開始前も InTerm）
- `Lifecycle__c`（Term / Spot）:
  - **V1 受注時**に First Ordered の継続課金有無で確定（継続あり=Term、一回のみ=Spot）。継続／一回は **明細 `BillingType__c` が正**（空なら Product2）
  - **Ordered が1件も無いとき**（V1 差し戻し）はクリアする。再受注で再判定する
  - Term↔Spot の直接切替は不可（VR）。空→確定、確定→空のみ可
  - **未設定の既存サービスはウィザード候補に出さない**（Change/Renew/Cancel/Add の保存も拒否）。先に `ContractServiceLifecycleService.backfillAllBlankLifecycles` で埋める
  - Spot は Add のみ。Term は Change/Renew/Cancel。Spot に Cancel は無い（候補から外す終了操作は持たない）

### 5.6 ステータスパス（表示用）

契約履歴レコードページで、見積〜入金までを **1本線** で見せる。業務の正は引き続き `historystatus__c`（Estimate / Ordered / Archive）。請求以降は積み上げから自動算出する。

#### 5.6.1 パス値（`StatusPath__c`）

| API 値 | 表示ラベル | 意味 |
| --- | --- | --- |
| `Estimate` | 01_見積 | 未受注の見積 |
| `Ordered` | 02_受注済み | 受注済。請求がまだ無い（件数 0） |
| `Invoicing` | 03_請求中 | 請求が1件以上あり、まだ全件は請求済でない（一部請求済を含む） |
| `Invoiced` | 04_請求済 | 全請求が請求済。まだ全件は入金完了でない（一部入金を含む） |
| `Paid` | 05_入金完了 | 全請求が入金完了 |
| （未設定） | — | `historystatus = Archive` のとき。Path 本線外のため `StatusPath` は null（選択肢 `99_アーカイブ` は定義のみ・RT／Path 非表示） |

本線の見た目（Path コンポーネント）:

```
01_見積 → 02_受注済み → 03_請求中 → 04_請求済 → 05_入金完了
```

- **Archive は本線に出さない**（商談の失注に相当）。`Default` RT の `StatusPath` 選択肢からも外す。Archive 時は Path を隠し、グレーの案内バナーのみ表示する
- 本線各段の案内文は **Path の Guidance for Success（`info`）に集約**する。レコードページにステータス別リッチテキストは置かない（Archive のみ例外）

#### 5.6.2 算出ルール

契約履歴の積み上げ（請求＝`Invoice__c` 子）:

| 項目 | 定義 |
| --- | --- |
| `InvoiceCount__c` | 請求件数（COUNT） |
| `InvoicedCount__c` | `SystemIntegrationDate__c != null` の件数 |
| `PaidCount__c` | `PaymentClearingCompletedDate__c != null` の件数 |

`StatusPath__c` の決定（`ContractHistoryStatusPathService`）:

1. `historystatus__c = Archive` → `StatusPath` = null（Path 非表示）
2. `historystatus__c = Estimate` → `Estimate`
3. `historystatus__c = Ordered` のとき:
   - 請求件数 = 0 → `Ordered`
   - 請求済件数 < 請求件数 → `Invoicing`（一部請求済もここ）
   - 入金完了件数 < 請求件数 → `Invoiced`（一部入金もここ）
   - それ以外（全件入金完了）→ `Paid`

- **混在は前の段に留める**。「全部そろったときだけ」次へ進む
- 請求の作成・更新・削除、および履歴ステータス変更で再計算する
- `StatusPath__c` は **自動更新のみ**。画面・API・Path からの手動変更は Apex で拒否する（`Contract_99` でも解除しない）

#### 5.6.3 画面（標準 Path）

- 契約履歴レコードページ（`FlexiPage122`）に標準 Path（`runtime_sales_pathassistant:pathAssistant`）を配置する
- Path の対象項目は `StatusPath__c`
- **Hide path update button = true**（パス上からフェーズを進めない）
- Path Settings: `ContractHistory_StatusPath`（項目 `StatusPath__c`、Record Type `Default`）
- 契約履歴にはレコードタイプ `Default`（デフォルト）を付与する。Path はこの RT 向け。既存レコードにも RT を割り当てる

#### 5.6.4 リレーション（請求）

- `ContractHistory__c` → `Invoice__c` は **Master-Detail**（親付け替え不可。共有は親従属）
- `Invoice__c` → `InvoiceLine__c` は従来どおり Master-Detail
- これにより契約履歴へ請求件数の標準積み上げを載せる

## 6. 契約期間明細・請求正本

### 6.0 二層の役割

| オブジェクト | 表示名 | 役割 |
| --- | --- | --- |
| `InvoiceProduct__c` | 契約期間明細 | 期間分解された数量・金額の事実。請求生成の素材。API 名は当面維持。契約履歴の Master-Detail 子 |
| `Invoice__c` | 請求 | 請求書単位の集約正本（請求日・BA SnapShot・税・ロック）。**契約履歴の Master-Detail 子** |
| `InvoiceLine__c` | 請求明細 | 明細単位の集約正本。`Invoice__c` の Master-Detail 子 |

- 受注時: ①契約期間明細を生成 → ②現行プレビューと同じ集約ロジックで請求／請求明細を永続化
- 以後の請求の正は `Invoice__c` / `InvoiceLine__c`
- 契約期間明細と請求合計のズレ（手動調整）は許容。双方向同期しない
- Change 差分は契約期間明細ベース。過去の請求手動調整は考慮しない
- 契約期間明細上の請求日・BA／宛名／メール等の請求寄せ項目は **削除済み**。期間明細は数量・金額・期間と `InvoiceBucketKey__c` を持ち、請求ヘッダ正本は `Invoice__c` のみが持つ

### 6.1 スナップショット原則

- BillingAccount マスタを更新しても、**既存請求**の SnapShot は再計算・上書きしない
- **新しく作られる請求**（受注生成・バックフィル・請求プレビューの分割で生まれる新請求）は、作成時点の BillingAccount 値を SnapShot としてコピーする（`Invoice__c`）
- 必須の BA SnapShot・商品／単位等は **ハードコード**。契約期間明細・請求・請求明細のいずれも Insert 時に CMDT（サンプル／顧客追加）で空欄へ追加スタンプする。既存更新では動かない（詳細は §2.2）
- 請求明細の商品／単位は新規作成時のみハードコードでセット（受注生成・分割とも作成時の見積商品マスタ）
- **請求情報編集**で直した宛名・メール・税率は **その請求レコードだけ**に残る。BillingAccount マスタには反映しない。分割で新しく作られる請求には引き継がず、作成時点のマスタ値でスタンプし直す（仕様。バグではない）
- 分割明細のうち、表示名・単価・数量・金額は分割元明細を引き継ぎ、商品参照（`Product__c`）・単位は作成時の見積商品を正とする

### 6.2 生成タイミング

- 契約履歴が Ordered になったとき（受注）
- Cancel は生成しない
- New／Renew: should-have 全量の契約期間明細 → 集約正本
- Change: 過去 Ordered との period key 差分の契約期間明細 → 集約正本
- 生成単位は **契約履歴（Version）**
- **不変条件**: 契約期間明細（`InvoiceProduct__c`）・請求（`Invoice__c`）・請求明細（`InvoiceLine__c`）は **`historystatus = Ordered` の契約履歴にのみ存在する**。Estimate／Archive には作らない・残さない（差し戻し・Archive・履歴削除で掃除。生成／rebuild／バックフィルは Ordered 以外を拒否または無視）
- 対象 Version にロック済み請求が1件でもあれば削除も再生成もしない（エラー）
- ロックがゼロなら、当該 Version の契約期間明細・請求正本を **全削除してから全作り直し**（手動調整済みでも上書き可。差し戻し再受注時は確認ダイアログ）
- 既存受注で請求正本が無い場合: プレビュー表示時に契約期間明細からバックフィルする（Ordered のみ）
- **Change** の生成前に、見積保存と同じルールを Apex で再検証する
- Ordered → Archive は不可（差し戻しは Estimate へ。`Contract_99` でも不可）。Archive からのステータス変更も不可（`Contract_99` でも不可）

### 6.3〜6.8 契約期間明細の生成ルール

継続課金の月次分割・一回課金・金額（数量×単価の整数円）・請求設定プリセット・請求日アンカー・入金予定日の算出は、従前の請求商品生成ルールを契約期間明細に対して適用する（詳細ロジックは実装 `InvoiceProductGenerationService` を正とする）。

要点:

- 継続課金は請求設定に関係なく月次行を作る（**明細開始日起点**の月次分割。カレンダー月分割はしない。生成コードもカレンダー月分岐を持たない）
- 一回課金は期間1行
- 各月税抜 = 数量 × 単価を整数円四捨五入
- 請求日・入金予定日の初期値は生成時に算出し、集約時に請求正本へ載せる
- 生成時の土日補正は BA 設定に従う。手動で請求日を直したあとは自動補正しない
- **Change × 据え置き系統（課金イベントなし）**: Original／Remake の内容（商品・数量・単価・BillingType・請求設定）が同一で途中開始・終了延長もない系統は、有効日で月次グリッドを切り直さない。明細開始日起点のまま should-have を出し、過去 period key と突合する（一回課金 New 追加のみで有効日が期中でも、据え置き継続課金に偽差分を出さない）。見積ウィザード Step2 でも据え置き系統の **請求基準は表示しない**（§4.12）
- **Change × 課金イベントあり**: 有効日前は Original、有効日以降は Remake。有効日以降の開始も **明細開始日起点の月次境界へスナップ**し、有効日そのものを新しい月次アンカーにしない（period key ずれ防止）
- **Change 差分の打消し（Fail closed）**: `past ≠ 0` の**継続課金** period key で差分が出るとき、過去条件の打消し行（`-past`・Original 紐づけ）は必須。次のいずれかで打消しを作れない場合は **静かにスキップせず受注／再生成をエラーで失敗**させる（プラス行だけ残して過大請求になるのを防ぐ）
  - 過去の契約期間明細サンプルが無い
  - 過去の数量・単価と一致する Original へ紐づけられない
  - Original／Remake 不整合などで打消し行を組み立てられない
  - 実装は「Original+Remake が揃っているときだけ打消しを試す」ゲートを置かず、継続課金の差分なら **常に打消しを試して失敗時は例外**とする（念のための安全弁）
  - ウィザード正規操作では通常起きない。Data Loader 等で Original／過去期間明細を改変した不整合データ向け
- **一回課金は打消し対象外**（意図的）。月次 past / should-have 突合での `-past` は継続課金のみ。一回課金を再度取る場合は Type=New で手追加する（Original／Remake カバー義務も一回課金は対象外。§4.4）

### 6.9 ロック（請求正本）

- ロック項目は `Invoice__c` の `SystemIntegrationDate__c` / `PaymentClearingCompletedDate__c`
- **入金消込額／消込完了日は手動前提**。消込日の付与・クリアで消込額を自動セット／クリアしない。Ops「消込日クリア」も消込日のみ外し、消込額は残す
- **入金消込額**は `Invoice__c.PaymentClearedAmount__c`（税抜）。部分入金は完了日なしで金額のみ更新可
- **請求プレビューフッタのステータス金額は排他バケツ**（税込換算して表示。合計＝その請求の税込）
  - **請求前**: 未連携の残り（税抜合計 − 入金消込額。連携後は 0）
  - **請求済（未消込）**: 連携済みかつ未消込の残り（税抜合計 − 入金消込額。未連携は 0）
  - **入金消込**: `PaymentClearedAmount__c`（未設定は 0。消込完了日があっても金額は自動補完しない）
  - **正は請求ヘッダ**。Version フィルタの有無に関わらず、**当該請求の明細が画面上すべて残っているとき**はヘッダの排他バケツ（請求前／請求済／入金消込）をそのまま使う。明細への HALF_UP 按分を足し戻さない（標準構成では `ContractHistory` 必須のため 1請求＝1 Version で、Version 絞り込みでも全行残る）
  - **一部明細だけのとき**（端数ドラフト中、または同一 `Invoice__c` に異なる Version の明細が混在し Version フィルタで行が間引かれたとき）だけ、表示中行の按分金額を足し戻してフッタを出す。この HALF_UP 端数ずれ（例: 消込 ¥1 が行按分で全部 0）は **許容**する。標準の `InvoiceMergeKeyPart__mdt`＋必須部品では混在しない。CMDT／必須部品を変えて混在させうる構成にした組織向けの例外規定
- ロック中の更新許可項目は階層 CS（§2.5）
  - 請求: `InvoiceLockExemptFields__c`（未設定時は入金消込額・消込完了日）
  - 金額・請求日・宛名など除外リスト外は拒否
- **請求プレビュー編集は請求書単位**: 対象 Invoice がロックならその請求だけ編集不可（端数・請求日・宛名／税率・各種分割）。同 Version の未ロック請求は操作可
- **差し戻し・再生成は Version 単位 all-or-nothing**: ロック請求が1件でもあれば、その Version の差し戻し・再生成は不可
- ロック済み請求の更新・削除は Trigger で拒否。バイパスは `Contract_99_Can_Bypass_Integrity_Guards`（通常付与しない）
- 契約期間明細に連携日／消込完了日は持たない（旧期間明細ロックは廃止）

### 6.10 税

- 税率は契約サービスからスナップショットし、請求（`Invoice__c.TaxPercent__c`）に保持
- **税額は請求ヘッダに保存**（税抜合計 × 税率を1回切り捨て）。明細に税額は持たない
- 明細金額変更時は請求ヘッダの税抜合計・税額を再計算して書き戻す
- 税率 null は 0%（§4.6。デフォルト 10% があるため通常は入る。意図的 null のみ想定。受注時必須にはしない）。Percent 項目は `fromPercentFieldStorage` 経由

### 6.11 マージキー

| 用途 | キー | 変更 |
| --- | --- | --- |
| 請求書／明細の集約キー構成 | `InvoiceMergeKeyPart__mdt`（組織1セット） | 部品の Active / SortOrder で動的に構成。受注・再生成時のみ適用 |
| 期間明細への保管 | `InvoiceBucketKey__c` / `LineBucketKey__c` | 生成時に Textでスナップショット（旧数式 `ExportMergeKey` / `ExportLineMergeKey` は廃止） |
| 請求正本 | `Invoice__c.MergeKey__c` / `InvoiceLine__c.LineMergeKey__c` | 集約時に期間明細キーを保存。プレビューは正本キーを表示。期間明細の `InvoiceBucketKey__c` 欠落は **FALLBACK せずエラー**（生成不備の Fail closed） |
| Change 差分（period key） | 契約サービス + Product2 + 開始日 + 終了日 | 固定。マージキー CMDT に連動しない |

必須部品（`InvoiceMergeKeyConfigService` で強制。CMDT で Active を外しても受注時に失敗）:

- 請求書: `BillingAccount` + **`ContractHistory`** + `InvoiceDate`
  - `ContractHistory` を必須にする理由: 同一請求先・同一請求日でも **別契約履歴（Version）の明細が同一 `Invoice__c` に衝突しない**ようにする
- 明細: `ContractProduct`
- 任意部品の例: 請求書の `PaymentScheduledDate`、明細の `UnitPrice` / `Quantity` など（Active / SortOrder で構成）

- `Invoice__c.MergeKey__c` は **受注生成／正本再生成で付与**する。請求プレビューの日付変更・請求情報編集・**明細を移す**では `null` にする（手動調整済みの印）
- 分割で生まれる新請求の `MergeKey__c` も付与しない（`null`）。明細の `LineMergeKey__c` は分割元／移動元明細からコピーする
- 連携・突合は手動調整後／分割・移動後を含めて **レコード Id ベース**を正とする。MergeKey が無い請求を欠番扱いしない

## 7. 請求プレビュー

- **受注済み請求の確認＋例外編集**。受注前ドライランではない
- 契約サービス配下の **請求正本**（`Invoice__c` / `InvoiceLine__c`）を表示する
- 未受注の見積で開いても、これから生成される予定行は出ない
- **Version フィルタの初期値**は、画面を開いた（クリック元の）契約履歴の Version。候補にその Version が無いときだけ「全バージョン」。ユーザーがフィルタを変えたあとの保存・再取得では選択を維持する。「全バージョン」への切替は従来どおり可能
- Version フィルタで絞り込んだとき: 該当 Version の明細が1行以上ある請求カードだけ表示（明細0は非表示）
- **カードフッタ（税抜・税・ステータスバケツ）**: 「全バージョン」専用ロジックは持たない。**その請求の明細がフィルタ後も全部残るなら請求ヘッダを正**（§6.9）。標準構成（マージキーに `ContractHistory` 必須）では Version 絞り込みでも全行残るため、消込額などは常にヘッダを見る
- 端数ドラフト中など一部行だけのとき、または **CMDT 等で同一請求に異なる Version 明細が混在しフィルタで間引かれたとき**は表示中行で再集計する。後者の HALF_UP 端数ずれは **許容**（§6.9）

### 7.1 権限

- 閲覧: Ordered の契約履歴から利用可（既存どおり）
- 編集: カスタム権限 `Contract_Can_Edit_Invoice_Preview`（PS `Contract_Invoice_Preview_Edit`）。受注権限とは別

### 7.2 例外編集（初期スコープ）

| 操作 | 対象 | 内容 |
| --- | --- | --- |
| 端数調整 | 請求明細 | ±1 / ±10 円ボタンのみで税抜金額を調整。親請求を手動調整済にし税を再計算 |
| 請求日調整 | 請求 | 請求日・入金予定日を人が別々に編集（入金予定の自動再計算なし。土日自動補正なし） |
| 請求を分ける | 請求 | ヘッダ入口。選択明細を**全額**新しい請求へ移す（`splitInvoiceByDate`／BA 変更時は `splitInvoiceByBillingAccount`）。新請求日・入金予定日・請求アカウントを指定。**全明細移動時は確認のうえ元請求を削除** |
| 明細を移す | 請求 | ヘッダ入口。選択明細を**全額**同じ Version（同一契約履歴）の**既存未ロック請求**へ移す（`moveLinesToExistingInvoice`）。請求日・BA・税率は移動先ヘッダに従う。同じ商品でも合算せず別行。Master-Detail のため付け替え不可（行き先へ新規明細→元削除）。**全明細移動時は確認のうえ元請求を削除**。Version 跨ぎ不可 |
| 分割 | 請求明細 | 行ホバーの **「分割」**。**同一請求内**で選択明細を2つに分ける（`splitLinesInPlace`）。種類は **期間**（継続課金かつしきい日候補あり）／**単価**／**数量**。新請求は作らない。端数・手動調整はクリア |
| 請求情報編集 | 請求 | **請求日・入金予定日・宛名・メール（To/Cc/Bcc）・税率**を同一パネルで手修正（当請求の SnapShot）。**保存は 1 Apex・Invoice__c 1 DML**。支払条件は BA マスタ側。マスタへは書き戻さない。失敗時は編集パネルを維持 |
| 受注直後の請求に戻す | 最新 Ordered Version | Version フィルタが**最新受注 Version**に絞られ、その配下請求が**すべて未ロック**のときだけヘッダに表示。確認後、当該 Version のみ期間明細・請求正本を受注直後相当へ作り直し（`InvoiceProductGenerationService.generateForHistories`）。**過去 Version は変更しない**。全バージョン表示時・過去 Version 選択時は出さない |

- 手動調整フラグは請求・明細の両方（どちらか触ったら親も立つ）
- **`Invoice__c.PeriodLineAmountTotal__c`（調整前請求額）**
  - 受注生成時は税抜請求額と同額。端数調整（±1/±10）後も据え置き、金額との差が調整幅
  - 同一請求内分割（期間／単価／数量）では端数クリア後、調整前＝税抜合計に揃える（分割UIでの事前警告は出さない。結果の端数あり／なしは行表示で分かる）
  - **請求を分ける／明細を移す**では、移した金額比で `PeriodLineAmountTotal__c` を元・先へ按分（端数ギャップを比率で引き継ぐ）。移動先・移動元（残存時）とも `MergeKey__c = null`・手動調整済
  - 値引き・Change Original 等の **負の単価／金額** も単価・数量・請求分割・明細移動の対象（入力に `min=0` を付けない。合計保全・端数配分は正と同じ）
  - **分割の合計保全（サーバ強制）**: `splitInvoice*`／`splitLinesInPlace` で `remainAmount` を渡すとき **`moveAmount + remainAmount == 元明細 Amount`** 必須。不一致はエラー（クライアント指定の残額で税抜合計を水増し／目減りできない）。未指定時はサーバが `元 − move` を残額とする
- **ロック**: 連携済／消込済の請求カードだけ編集不可（分ける／移す／分割ボタン非表示）。同 Version の未ロック請求は分割・移動・端数などを継続可（§6.9）。差し戻し・再生成は Version 単位のまま。端数ドラフト中は分ける／移す／分割を無効化
- **分割・移動 UI**
  - **請求を分ける**（ヘッダ）: 新請求作成。明細はチェックで全額移動。`invoiceSplitState`。全明細移動時は確認ダイアログのうえ元請求削除
  - **明細を移す**（ヘッダ）: 既存請求へ全額移動。`invoiceMoveState`。行き先は同一 Version・未ロックのみ（同じ Version に移せる請求が無いときはボタン無効）。請求日・BA・税率は移動先ヘッダ固定。同じ商品でも合算せず別行。全明細移動時は確認ダイアログのうえ元請求削除。Version 跨ぎ不可
  - **分割**（行ホバー）: 同一請求内の期間／単価／数量分割。常時表示しない。`lineSplitState`。選択中のみ薄い実行バー
  - 期間: Apex `getSplitThresholdDateOptions` のしきい日。単価／数量: 「残す」側を入力し、もう一方は元 − 残すで算出
  - 実行は選択行が1件以上かつ入力妥当なときのみ（`splitLinesInPlace`／`moveLinesToExistingInvoice`）
- **見積額 vs 請求額（ずれ）**
  - 見積額 = Ordered 見積商品 `Amount__c` を、**請求に載った月数で按分**した値（Archive / Estimate は混ぜない。月次 `InvoiceProduct` 金額の合算ではない）
  - 継続課金: `Amount × (そのCPの InvoiceProduct 件数 / CP月数)`（整数円・四捨五入）。一回課金: 期間明細が1件以上あれば `Amount` 全額
  - 明細のずれ = 請求明細金額 − 上記見積按分（同一 CP が複数明細に分かれる場合の配分）:
    - **期間 ID が明細間で1つでも重複**（請求日／BA／単価／数量分割のコピー）→ **明細金額比**（片方だけしきい日分割した混在でも行の偽ずれを出さない）
    - **期間 ID が排他的**（しきい日分割後など）→ **由来 InvoiceProduct 金額比**
    - 一回課金は明細金額比。最終行で残り吸収。期間金額がすべて0の排他配分時だけ月数均等
  - Change の Original などで CP 全期間 Amount と、実際に生成された月だけが請求に載る場合でも、按分により偽の「端数」は出さない
  - 見積 Amount（一括丸めまたは手入力）と数量×単価の月次再計算の差（数円〜数十円）は、全月請求済みなら従来どおりずれとして残る。見積ウィザードでは **請求プレビューに載り得る差分だけ**を事前表示する（§4.12。Change 据え置きは出さない）
  - 端数調整実績（±1/±10）は別指標。**由来付き請求明細の金額合計 − 由来 InvoiceProduct 金額合計**（期間 ID は重複排除）

### 7.3 再生成・差し戻しとの関係

- 未ロックなら再生成（差し戻し再受注）で請求正本は作り直し可（調整も消える）
- **請求プレビューの「受注直後の請求に戻す」**: ステータスは Ordered のまま、**最新 Ordered Version だけ**を受注生成と同じ経路で作り直す（過去 Version 非対象・ロックありは不可）。確認文言で分ける／移す・分割・端数・請求日などの手直しが消える旨を出す
- 差し戻し時、手動調整ありなら画面内警告を表示してから実行（システム Confirm は使わない）

### 7.4 請求アカウント

- 契約サービス多 BA 化・按分マスタは作らない
- 請求プレビューの **「請求を分ける」** で別請求を作り、必要なら BA スナップショットを差し替える（§7.2）。**「明細を移す」** で同じ Version の既存請求へ寄せる（手動マージ相当）。行ホバーの **「分割」** は同一請求内のみ
- 連携・消込操作は請求正本向け `InvoiceOpsController` / `invoiceOpsPanel`（旧 InvoiceProductExport 後継）
- **権限**: カスタム権限 `Contract_13_Can_Manage_Invoice_Ops`（PS `Contract_13_Manage_Invoice_Ops`）必須。画面表示とサーバ入口の両方で強制
- **13 でできること（業務）**: 請求Ops一覧の閲覧、連携済の付与、消込済の付与、消込日クリア。今後の部分入金・消込額更新・連携結果反映なども 13 に寄せる
- **13 ではやらないこと**: 見積／受注／差し戻し、請求プレビュー編集（11/12）、ロック無視の緊急対応（99）
- `invoiceOpsPanel` の操作日初期値・選択状態は §4.16 に従う（ローカル暦日／recordId 切替で選択クリア）

## 8. ARR／AveARR

### 8.1 ARR（期末ランレート）

- 対象: `Product2.IncludeInARR__c = true` の商品のみ
- さらに: 継続課金、数量 > 0、**Amount ≠ 0**、Original 以外、明細終了日が期間終了に届くもの
- 計測時点: 契約履歴の期間終了日の翌日時点
- **計算: 見積商品 `Amount__c`（ウィザード Step2 でユーザーが見た税抜金額）÷ 明細月数 × 12**
  - 月数は開始日〜終了日の月次サイクル数（`countMonthlyBillingCycles`）
  - 請求商品（月次 InvoiceProduct）の合算は使わない
  - `Amount__c` が null の旧データのみ、互換で数量 × 単価 × 12
- **金額0は ARR に含めない**（期中停止の金額0 Remake など）。Amount があれば単価逆算の端数は ARR に載せない
- **ARR は Estimate 段階でも計算・保存してよい**（見積時点の試算を含む。Ordered 専用の確定値に限定しない）
- **DeltaARR（△ARR）は数式項目が必須**。Version1 は当履歴 ARR、それ以外は当履歴 ARR − 前回履歴 ARR。**Apex では絶対に書き込まない**（書き込み可能項目としてのフォールバック更新もしない）

### 8.2 AveARR（期間平均ランレート）

- 対象・除外は ARR と同じ（`IncludeInARR`・継続課金・数量 > 0・**Amount ≠ 0**・Original 以外）。**期末到達条件だけ外す**（期中開始・期中停止の明細も分子に含める）
- **計算: 対象明細の期間金額合計 ÷ 契約期間月数 × 12**
  - 契約期間月数は `CurrentTermStartDate__c`〜`CurrentTermEndDate__c` の `countMonthlyBillingCycles`
  - 期間金額は見積商品 `Amount__c`。null の旧データのみ数量 × 単価 × 明細月数
  - 請求商品合算は使わない
- フラット満了（全対象明細が期間全体）では AveARR ≒ ARR。同一履歴内で期中に中身が変わると差が出る
- **AveARR も Estimate 段階で計算・保存してよい**
- **DeltaAveARR（△AveARR）は数式項目が必須**。Version1 は当履歴 AveARR、それ以外は当履歴 AveARR − 前回履歴 AveARR。**Apex では絶対に書き込まない**

## 9. ByPass・通貨・パッケージ外

管理者権限や整合バイパスで「触れてしまう」こと自体は排除しない（[設計の大前提](#設計の大前提)）。ここでの ByPass は、導入・移行のための限定スイッチである。

### 9.1 ByPass

パッケージ標準の ByPass は次のみ。

| 手段                               | 用途                     |
| ---------------------------------- | ------------------------ |
| `ContractValidationEnforce__c` OFF | 顧客固有 VR をスキップ   |
| データ移行等の運用余地             | 物理削除などの制約を外す |

Trigger／請求生成／ウィザード検証を一括スキップする専用 ByPass オブジェクトは持たない。

### 9.2 通貨

- **JPY のみ**対応。多通貨・為替換算・通貨別請求はパッケージ対象外
- 運用回避: 元通貨・換算レート日・換算レートをカスタム項目で保持可（パッケージは換算しない）

### 9.3 契約パターン早見

| 対応する                                                              | 対応しない                                 |
| --------------------------------------------------------------------- | ------------------------------------------ |
| 新規・Change（期間内課金変更。終了延長を伴っても可）・Renew（単純延長）・Cancel（満了翌日 Churn）。判断は §4.4.0 | 日割り／**単純延長だけの Change**（→ Renew） |
| 継続課金の月次期間＋一括前払／後払／月次分割                          | トライアル／無償期間の専用モデル           |
| 期中解約相当（金額0 Remake。Cancel ではない）                         | 稼働ベース未確定請求・従量課金             |
| 値引き（マイナス単価）                                                | 数量ティア／価格表／ボリューム割引自動適用 |
| 一回課金の別期間                                                      | 複数請求先への金額按分                     |
| 更新商談チェック OFF→ON での Renew 見積自動作成（作成時 ON では不可） | 自動受注・自動更新完了                     |

詳細な顧客向け言い回しは [§11](#11-導入時よくあるニーズへの答え)。

| 同じ商品を空白期間のあと再開したい         | 可。同一 Product2 でも期間が重ならなければ Type=New で追加可（Change では保存前確認あり）。期間重複は不可。期中の条件変更は Remake。種別判断は §4.4.0 |
| 途中解約・未経過分の停止／返金相当         | **Change で Remake を分割**し、停止後区間だけ単価0。Cancel は使わない。**全期間 Remake1本を単価0にすると全期間洗い替え（満額打消し）になり、それは入力どおりで不具合ではない**（§4.4）。日割り返金の自動計算なし |
| 期中停止後の単価0が Renew に載る           | **仕様どおり**。単価0は無料提供にも使うため引継ぎから除外しない（§4.4・§4.9）。不要なら手動 Renew のゴミ箱で削除。ARR が0円を除外することとの差も仕様 |
| 契約満了後に解約（Churn）確定したい        | **Cancel**。解約日＝前回期間終了の翌日のみ（例: 6/30 満了 → 7/1）。期中の任意日は不可（§4.4）                                                            |
| どの種別を使うか（New/Change/Renew/Cancel） | **§4.4.0 の判断ロジック**。期間内に課金変更あり→Change（終了延長可）。単純延長のみ→Renew。満了後 Churn→Cancel。新規サービス→New |
| 契約の単純延長・更新                       | **Renew**（前回終了の翌日から。期間内に課金変更なし）。数量変更などとセットで延ばすなら **Change**（§4.4.0・§4.4.1） |
| Change で数量変更＋終了延長した延長分がフル課金 | **仕様どおり**（延長区間に past が無い洗い替え）。「延長＝必ず Renew」ではない（§4.4.0） |
| 月途中開始の日割り請求                     | 不可。月途中開始は可だが、金額は日割りせず請求期間単位                                                                                                   |
| トライアル後の自動有償化                   | 専用機能なし。0円期間や終了後の別見積／Change で運用回避可                                                                                               |
| 1契約金額の複数請求先按分                  | 自動按分は不可。請求プレビューの「請求アカウント分割」で手動分割可（§7.4）。契約／見積を分ける運用も可                                                   |
| 契約終了時の自動更新（自動受注）           | 不可。受注は手動。更新商談の `RenewEstimateAutoCreateCheck__c` を **OFF→ON に更新したときだけ** Renew 見積の自動作成は可（作成時にONでも作らない。§4.9） |
| ボリューム割引・段階料金の自動適用         | 不可。単価は見積で手入力（またはマスタ単価のコピー）                                                                                                     |
| 請求書 PDF の顧客自動メール送信            | 不可。個別開発または会計システム連携が必要。見積 PDF の発行・添付は可                                                                                    |
| クレカ決済・振込の自動入金消込             | 不可。入金予定日・消込完了日の記録と請求ロックはある。決済／消込は個別連携                                                                               |
| ARR／DeltaARR／AveARR／DeltaAveARR の契約単位確認 | 可。ARR は期末到達明細の Amount÷月数×12。AveARR は対象明細 Amount 合計÷契約期間月数×12（期中明細含む。Amount0・数量≦0は含めない）。△は数式。専用ダッシュボードUIなし |
| 複数通貨での契約・請求                     | JPY のみ。元通貨・換算レート日・換算レートをカスタム項目で持てば運用回避可（パッケージは換算しない）                                                     |
| 従量課金（使用量×単価）の自動請求          | 不可。数量・単価は見積時点で固定。使用量取込・メーター請求はない                                                                                         |
| 見積の社内承認フロー（金額帯別など）       | 不可（パッケージ専用UIなし）。Salesforce 標準承認プロセスをテナント側で組む                                                                              |
| 適格請求書（インボイス）PDF 発行           | 不可。発行に必要な元データは持つが発行機能なし（会計連携または個別開発前提）                                                                             |
| 電子契約（CloudSign / DocuSign 等）連携    | 不可。個別開発が必要                                                                                                                                     |
| freee 等への請求データ自動連携             | 不可。個別開発が必要                                                                                                                                     |
| 顧客向けポータルでのセルフサービス         | 不可（社内ユーザー向け）。個別開発で拡張は可能                                                                                                           |
| 親商品＋構成品のバンドル展開               | 不可。見積商品はフラットな明細行                                                                                                                         |
| 複数見積の横並び比較UI                     | 不可。複数 Estimate 並存・コピーは可。横比較専用UIなし                                                                                                   |
